# 0.2026249.2024 — fix(loaderkit): the in-body member scan fires only where member nesting is meaningful — the parent-disc guard

## Summary

Fixes the parse regression sdk #221 introduced in the member-tree cutover: `discEntityPairs`/`isEntityValue` scanned EVERY disc-value body for kind words, so a schema block key whose mapping carries a member-disc word classified as an IN-BODY member. The live corpus shape (distro-arch `check-agent-live`, caught by charly's `TestCueKinds_Corpus`): a GROUP body's `iterate:` block carries an `agent:` key — an external structural kind WORD colliding with a group-schema FIELD name — so `parseNode("iterate")` classified `agent` as its disc, the remaining iterate fields became member pairs, and the scalar `sandbox: check-agent-pod` hard-failed with `node sandbox: expected a mapping value, got yaml kind 8`.

The design intent of Cutover C: **member nesting = substrate bodies**. The guard makes the in-body member scan parent-disc-aware — it fires ONLY when the parent disc is a DEPLOY SUBSTRATE (`t.DeploySubstrates`) or an external STRUCTURAL kind (`t.StructuralKinds`):

- **Substrate/structural bodies** (vm/pod/local/android/kubernetes, external structural plugin kinds) keep scanning — the authored-depth channel (in-substrate vs deploy-level members) works exactly as #221 shipped it, recursively.
- **Arbitrary resource-kind bodies** (group/check/candy/box — host-threaded kinds whose closed schemas define fields that can collide with kind words: `agent:`, `sandbox:`, ...) no longer scan — their body travels untouched as data and the closed-schema gates own it; their members are DEPLOY-LEVEL siblings only (the `memberPairs` loop, unchanged).
- The dead in-body error branch (unreachable under the guard: every scan kind is a `memberDisc` kind) is removed in the same commit — nothing else changed.
