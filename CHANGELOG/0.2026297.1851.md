# 0.2026297.1851 — feat(kit): a step's process environment carries the host's values as DATA

## Summary

**A host's resolved values could reach a command only as shell SOURCE.** The kit had exactly one channel for them: `kit.ExpandOpVars` substitutes a value into the step's command TEXT, and the shell then parses that text. A value that is DATA therefore becomes SOURCE — a `$(…)` inside a value EXECUTES, and a value carrying a space arrives as two words. This is the seam opencharly/plugin-task#34 names, and the mechanism belongs in the kit, where the plan walk lives.

**The fix: a second channel, into the step's PROCESS ENVIRONMENT.** A host hands the walk the values a step's environment should carry (`kit.RunnerConfig.StepEnv`); the walk merges them into the step's `env:`, and the command verb applies them as a shell-QUOTED export — so the value arrives as ONE WORD, whatever it contains. The two channels are not equivalent in kind, and that difference is the whole point:

| channel | the value is | the shell sees |
|---|---|---|
| text (`kit.ExpandOpVars`) | SOURCE — it is parsed as shell text | `$(…)` runs, `;` splits, a space splits |
| environment (this change) | DATA — it is one word | one word, whatever it contains |

**The consumer is already shipped; this change is the missing producer.** The `command` plugin's verb reads the step's `env:` and renders it as shell exports — the version charly builds against is v0.2026277.738, and its source is pasted in *How tested* below. The kit fills `op.Env`; the verb exports it. One implementation each, and the consumer needs no change for the channel to work.

**The seam is optional, and a host that does not implement it changes nothing.** `kit.StepEnvExporter` is a separate OPTIONAL interface, not a method on the public `kit.PlanContext` — that interface's implementors live outside this repository, so a new method on it would break every consumer of the kit. A host that does not implement the seam exports nothing, and every verdict is unchanged.

**A name the shell cannot export is disclosed, not dropped.** `export HOST_PORT:6379=…` is a shell SYNTAX ERROR that would fail the whole step, so such a name is not exported — and the name is named in the step's message, because a value that vanishes silently reads exactly like a host that never supplied it. That is a NOTE, never a verdict: the step itself still runs.

**The diff is four files** — `kit/stepenv.go` (the channel), `kit/planrun.go` (the walk merges it), `kit/runner.go` (the host's seam), `kit/stepenv_test.go` (the coverage). Head `9070ab4d9af6980d422a466f2cf2b9d9db2939c5` — 4 files changed, 302 insertions(+), 0 deletions(-).

```
func envExports(env map[string]string) string {
	if len(env) == 0 {
		return ""
	}
	keys := make([]string, 0, len(env))
	for k := range env {
		keys = append(keys, k)
	}
	slices.Sort(keys)
	var b strings.Builder
	for _, k := range keys {
		fmt.Fprintf(&b, "export %s=%s\n", k, shellquote.ShellQuote(env[k]))
	}
	return b.String()
}
```

## Filed issues

- opencharly/sdk#474 — should the TEXT channel be closed for params (may a param's value ever reach a command as SOURCE)? The mechanism's owner is this repo and the param surface's owner is opencharly/plugin-task, and the answer changes what the sdk guarantees, so it is an operator decision rather than a library author's preference. The RCA and the evidence are in the issue.
- opencharly/charly#1060 — the check engine's own variable vocabulary (`HOST:web:8080`, `HOST_PORT:8080`) is not the shell's, so a resolved peer value has no spelling the new channel can export. The naming contract between the check side and the kit is the decision, and the issue names the pair of owners.

Both are genuinely separable from this change: the tree is correct and this PR's claim is true without them, and neither is touched by the diff.
