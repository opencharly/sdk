# 0.2026262.1218 — cleanup(sdk): drop the redundant ProtocolVersion re-export

## Summary of changes

Sibling of `opencharly/spec#138`. Removes the `sdk.ProtocolVersion` re-export, whose only purpose was feeding the removed `Capabilities.protocol_version` field, and sweeps the stale README claims that named it as a protocol gate.

RDD established the field was dead (full analysis in the spec PR): `transport.ProtocolVersion` was never bumped (const `2` since the initial import; a REAL proto field `CLISubcommand.hidden` was later added with no bump), the IN-PROC comparison was a tautology, and the OUT-OF-PROC gate was unreachable (go-plugin's handshake already rejects before Describe).

Concrete edits (5 files, +49/−17):

- `sdk.go` — drop `const ProtocolVersion = transport.ProtocolVersion`. No consumer remains (grep-clean below).
- `schema.go` — stop setting `ProtocolVersion` in the `Capabilities` literal.
- `schema_capabilities_test.go` — `TestBuildCapabilitiesDropsProtocolVersion`, a NEW gating test that asserts the emitted `Capabilities` carries no `protocol_version` on the wire. It FAILS without the change (pre-change FAIL output pasted in block 2) — the coverage B12 requires.
- `loaderkit/scan_orchestrate.go` — correct the stale comment naming "ProtocolVersion 1 against a v2 client" (R5 claim-keyed sweep).
- `README.md` — drop `ProtocolVersion` from the serve/handshake surface and replace the "plugin PROTOCOL gates" paragraph: the wireframe contract is the plugin's served CUE schema spliced onto the host base; the go-plugin handshake version is owned by `spec/transport`.

**What is KEPT:** `sdk.Handshake` (the magic-cookie + the frozen go-plugin transport version). Removing the handshake version refuses already-built plugins whose wireframe is compatible (measured in the spec PR: `incompatible API version with plugin. Plugin version: 2, Client versions: [0]`).
