# 0.2026322.1827 — fix(kit): delete the retired acme_email use — the contract field is gone

## Summary

`opencharly/spec#379` **retired** `acme_email` from the schema — not deprecated, deleted.
`sdk` still read it in four places, so every sdk tag at or after that merge fails to compile
against the released contract (`meta.AcmeEmail undefined (type *spec.BoxMetadata has no field or
method AcmeEmail)`). This change deletes every reference and adopts the tag that retired it.

**What breaks for consumers — the behaviour change, named.** `ACME_EMAIL` is **no longer populated
from a box's metadata**. It cannot be: the contract has no field to carry it, so there is nothing to
copy into the variable map. Concretely, for a `charly` plan step or deploy template that used
`${ACME_EMAIL}`:

- **charly's own plans never used it.** The claim-keyed sweep below finds no `run:`/`check:` step
  anywhere in this repo, charly's candies, or the boxes that expands `${ACME_EMAIL}` from charly's
  variable map.
- **The one live consumer is Traefik's own expansion**, `pod-traefik/traefik.yml:27`
  (`email: ${ACME_EMAIL:-admin@example.com}`). That `${…}` is expanded by **Traefik inside the
  container**, from the container's process environment — not by charly's variable map — so it is
  unaffected by this change *as long as the operator supplies the value the way that surface always
  worked*: a deploy `env:` / `env_file:` entry. What is gone is the second, implicit source: putting
  `acme_email:` on a box/deploy and having charly hand it to the variable map. That authoring
  surface was already gone with `spec#379`; this PR is where the code catches up, so the fallback
  `admin@example.com` is what a Traefik deploy that relied on the metadata path will now use —
  silently, which is why it is stated here rather than left to be discovered.
- **Nothing else read it.** `deploykit`'s overlay→metadata copy and the `DeployOnlyCapabilityFields`
  exemption existed only to carry the field from the overlay to the metadata; both go with it.

**The producer-first ordering defect — this PR is the repair.** `spec#379` retired the field
*without the consumer moving first, and not in the same cutover*. The rulebook's relocation
invariant is explicit: the replacement must be merged at its new home **before** the removal, or
both land in **one** change — otherwise, at the commit where the producer drops the field, the
consumer is broken on `main` and every sdk release until the repair lands. That is exactly what
happened: `spec v0.2026322.1356` (which carries `#379`) cannot be consumed by any sdk tag, so the
sdk had to follow the spec tag rather than precede it. The order is recorded here so the next
reader sees why this leg is a repair and not a cleanup.

Files: `kit/checkvars.go` (the `ACME_EMAIL` map entry), `kit/checkvars_test.go` (fixture +
expectation), `deploykit/deploy_file.go` (the `overlay.AcmeEmail` copy + the schema-v4 note),
