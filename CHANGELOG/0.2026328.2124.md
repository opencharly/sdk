# 0.2026328.2124 — fix(deploy)!: never run a unit as container root

## Summary

The quadlet emitter had one branch that ran a deployment's workload as **container root**: a unit that carried the CDI GPU device *and* had a host-owned bind mount was emitted `UserNS=host` + `User=0:0`, because crun cannot apply the CDI spec's file mounts under `keep-id` (opencharly/plugin-deploy-pod#81). The measurement behind that branch was right; the remedy was not. It made container root the emitter's **default** for a whole class of deployments, which is privileged by any reading of the requirement that governs it — D-HW-10: *"A deployment is rootless unless a need in its stack is `privilege: rootful`: its kind's grant runs it on the driver's rootless mode … with the box's workload as the box's user, and no other field, setting or default makes it privileged."* A bind mount is not a `privilege: rootful` need.

The emitter now has no root branch: a unit with a bind mount runs `UserNS=keep-id:uid=<uid>,gid=<gid>` as the **image user**. Under keep-id that user *is* the invoking host user, so a host-owned volume (a bind, or a gocryptfs plaintext directory) is writable as-is, with no chown.

**CDI stays.** The device is emitted for every GPU unit, bind or not. The measured wall is the CDI **spec's `mounts` section**, not the device: a *devices-only* spec (same device name, `deviceNodes` only) applies normally inside keep-id. So the split of responsibility is:

- the emitter says which device the unit gets (`AddDevice=nvidia.com/gpu=all`) and how the unit runs (keep-id, image user);
- the caller — `plugin-deploy-pod` — points the engine at a devices-only spec and supplies the driver libraries as read-only binds to their SONAME paths (both derived from the host's CDI spec, never baked into the image).

The second commit on this branch adds the two inputs that caller needs and the emitter could not express: `QuadletConfig.PodmanArgs []string` (rendered as ONE `PodmanArgs=` line — quadlet splits that line into argv words, so `--cdi-spec-dir <dir>` is one flag and its value together) and `ResolvedBindMount.ReadOnly bool` (rendered `:ro`). Both are internal library inputs of the config-to-unit path; no wire type, CUE schema or CLI flag changes.

Measured (podman 6.2.0, crun 1.31, rootless, `/etc/subuid` `atrawog:100000:65536`, image `ghcr.io/opencharly/immich-cdi`):

| arm | result |
|---|---|
| `--userns=keep-id:uid=1000,gid=1000 --user 1000` + host bind | uid **1000**, write **ok**, host owner **1000:1000** |
| same + `--device nvidia.com/gpu=all` resolved from the stock `/etc/cdi/nvidia.yaml` (it carries `mounts`) | `crun: mount_setattr /usr/bin/nvidia-cuda-mps-control: Operation not permitted`, exit **126** |
| same + `--device nvidia.com/gpu=all` resolved from a **devices-only** spec + `libcuda.so.1`, `libnvidia-ml.so.1`, `libnvidia-ptxjitcompiler.so.1` bound to their SONAME paths | `user`/uid **1000**, device node present, `cuInit= 0` on the **RTX 4080 SUPER** (ONNX `MatMul` profiled on `CUDAExecutionProvider` in the same shape) |
| `--userns=host --user 1000` + `:idmap` volume (both `-v src:dst:idmap` and `--mount …,idmap`) | **denied** — idmap is a no-op under `userns=host` |
| gocryptfs plaintext without `-allow_other` | container does not start (`crun: cannot stat …: Permission denied`); with `-allow_other`, uid 1000 writes, file `1000:1000` |

## Change classification

The `!` marker is correct: the unit generated for one class of deployments changes shape.

**Breaking change + rollback:** a GPU deployment that also has a host-owned bind mount was generated `UserNS=host` + `User=0:0`; it is now generated keep-id as the image user, with the same CDI device. Its GPU then requires the consumer leg — `plugin-deploy-pod` pointing the engine at a devices-only CDI spec plus the driver-library binds — before it is regenerated, because the stock spec's mounts fail under keep-id (exit 126). **No pin moves in this PR**, so nothing in production changes until that consumer PR bumps this sdk tag; an operator who regenerates a bind+GPU deployment against this sdk alone gets a non-root workload whose container fails to start until the spec is devices-only. Rollback: revert the branch and re-run `charly config` on the affected deployments — the previous units regenerate byte-identically.

**Consumer leg (order):** this sdk PR → sdk tag → opencharly/plugin-deploy-pod#94 (devices-only spec + library binds, proven end-to-end on top of #93) → tag → charly's plugin pin → umbrella pin wave. The skill/documentation legs (`/charly-distros:cdi`, `/charly-automation:enc`, `/charly-internals:xdg`) and the umbrella rulebook are updated to this rule in their own repos.
