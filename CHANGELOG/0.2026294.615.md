# 0.2026294.615 — refactor(workflowkit): delete the dead LobsterArgsEnv arg projection

## Summary

**Decision: DELETE** `workflowkit.LobsterArgsEnv` — with the two helpers that existed only to serve it (`LobsterArgEnvVar`, `LobsterArgName`) — and their tests. Leg 1 measured its only reference as its own test, so this was a widen-or-delete question either way; deletion is the answer for three measured reasons, in the order they decided it.

**1. No caller I can reach.** Org-wide GitHub code search (which covers repositories not checked out here), the Go module cache on this host (every dependency of every module built here), and every checkout under the umbrella agree: the hits are `opencharly/sdk`'s own definition and its own test, and nothing else. Commands and their output are pasted in the How tested section.

**2. The projection it duplicated already exists, in the code that actually runs workflows.** `plugin-lobster`'s `mergeEnv` (`engine.go:1162`) takes `args map[string]any`, emits `LOBSTER_ARGS_JSON` plus one `LOBSTER_ARG_<NAME>` per arg, and JSON-renders a non-scalar through `argEnvValue` (`engine.go:1194`). So the list case this leg was told to handle explicitly is already handled — in the one place that sees the values. Widening the sdk copy would have produced the second arg-transport mechanism R2 forbids, and would have forced it to invent a rendering decision that already has an owner.

**3. The copy had already drifted from the engine it claimed to mirror.** Measured on the pre-change tree: `LobsterArgName("a..b") = "A__B"`, `LobsterArgName("_x") = "_X"`. The engine's `normalizeArgEnvKey` (`engine.go:1138`) collapses a run of non-`[A-Z0-9]` to one `_` and trims both ends, i.e. `A_B` and `X`. Its doc comment ("upstream lobster's env-var spelling") was therefore false against the engine that ships, so widening it would have pinned a rendering no engine produces.

The pin bump is the leg's other half: `github.com/opencharly/spec` `v0.2026289.611` -> `v0.2026294.550`, where `#WorkflowArgVal: #StrVal | [...#StrVal]` lives. `go doc` at the new pin shows the widened fields and `go build ./...` proves the module compiles against them; nothing in `sdk` referenced the four arg maps before, so nothing needed changing — that is the finding, not an obstacle.

What this leg does not do: it does not change the wire (leg 1's `spec#262` stands as merged) and it adds no lane primitive (legs 3 and 4).
