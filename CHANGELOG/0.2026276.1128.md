# 0.2026276.1128 — fix(sdk): fetch the init runtime the init vocabulary depends on, and match a ref-shaped depends_candy

Fetches the init runtime an init's `depends_candy:` names, so a composition that only declares a `service:` gets its init installed instead of an image that stamps `ai.opencharly.init="supervisord"` with no supervisord binary to run.

Relates to opencharly/charly#764 (the umbrella issue for automatic init injection + the `require: layer-supervisord` cutover).

**This revision answers the second review's three blocks** (head `e3fc4b3`, run 37118911153): (1) the two `deploykit` behaviour changes now have **live proof on the committed tree**, not only on a back-port; (2) the duplicated op-context predicate is **extracted** into one shared `sdk/internal/spectest` helper rather than conceded; (3) the body accounting is corrected below — `deploykit/init_unit_files.go`'s actual diff is described as what it is (the reworded `unsatisfiedInitDepends` warning), and the Rulebook section answers every applicable rule.

## Summary

`charly/charly.yml`'s `init:` vocabulary declares, per init system, the candy that **installs that init's own runtime** (`supervisord:` → the supervisord candy; `systemd:`/`openrc:` → none — they install with the OS). Declaring a `service:` in a candy is what *selects* an init and assembles its config — but **nothing ever fetched the selected init's runtime candy**. `deploykit.InjectInitDependsCandy` resolved `depends_candy` only against the project's **already-scanned** set, so a box that never happened to compose the init candy built and validated clean, baked `ai.opencharly.init="supervisord"` plus an assembled `/etc/supervisord.conf`, and then died inside podman on the render stage's COPY of the init candy's own template:

```
[image-build] FAIL after 1m58.942s
copier: stat: "/templates/supervisord.header.conf": no such file or directory
```

The field workaround is target-blind: 40 candies carry `require: layer-supervisord` and boxes list it by hand, which drags supervisord onto systemd/openrc venues.

**What changed** — 11 files, `+969/−100`:

- **`loaderkit/init_depends_seed.go`** (new, +98) — `initDependsSeeds(scanned, initCfg)` returns, for each init the scanned set actually triggers, its remote `depends_candy` as a fetch coordinate: `RepoPath`, `Version` (the authored `:version`; empty ⇒ resolved to the repo's default branch by the caller), the bare `Ref`, and a `layer=init:<name>` scope. Only a **REMOTE** (`@`-prefixed) `depends_candy` is seeded; a bare `depends_candy: supervisord` names no repo and is left to the scan set exactly as before.
- **`loaderkit/finalize_candy.go`** (+43/−29) — extracts `candyTriggersInit(sc, def)`, the ONE "does this candy trigger this init" predicate, out of `PopulateCandyInitSystem`'s inline loop so the seed and the finalizer cannot drift (R3). Behaviour-preserving: the same `IsPackaged`/`SupportsPackaged`/`ServiceTemplate` routing and the same `candy_file` glob arm.
- **`loaderkit/scan_orchestrate.go`** (+104/−5) — runs the seed (a) over `localScanned` BEFORE the `len(downloads) == 0` early return (a fully-local project must fetch too) and (b) after EVERY fix-point round over everything materialized so far — essential, because a distro service candy is itself remote, so its `service:` trigger only becomes visible once round 1 has fetched and scanned it. The seed is idempotent (the `seeded` map) so the fix-point drains instead of re-adding forever.
- **`deploykit/init_depends.go`** (+32/−28) — normalize a ref-shaped `depends_candy` through `spec.BareCandyRef` before every presence check, so `@github.com/opencharly/layer-supervisord:v2026.271.1817` matches the scanned set exactly as the bare name does, and ask the tolerant name rule before injecting a duplicate. The "not in the scanned set" branch's comment is re-based: with the fetch seed in place, reaching it means the **fetch** failed, not that the project forgot to list something.
- **`deploykit/graph.go`** (+17/−1) — `PruneContainerInitForSystemd` stops comparing to the literal `"supervisord"` and asks `orderSatisfiesInitDepends` instead, against a new named `const containerInitCandy = "supervisord"`. That is the ONE change that is **not** conditional on the vocabulary flip: a resolved order carrying the candy under its **ref key** (`github.com/opencharly/layer-supervisord`) is now pruned on a machine venue where before it survived onto a systemd guest. Intended, and covered by the live bed's second assertion.
- **`deploykit/init_unit_files.go`** (+12/−5) — the **reworded `unsatisfiedInitDepends` warning**. Its text previously taught the pre-fix workaround verbatim ("Reference the candy directly in the box's `candy:` list, or pull it in via a composed candy's `require:`"); it now names the actual cause — the fetch that should have materialized the candy did not — and points at the vocabulary's `depends_candy` ref. The message also no longer interpolates `depends_candy` into the slot naming the missing **binary** (that slot read correctly only while the field was spelled bare, and the ref form would have printed `... with no @github.com/opencharly/layer-supervisord:v2026.271.1817 binary`); it names the init's own runtime there instead. The dedupe key `(box, init, candy)` and the hook-swap contract are unchanged, and no test pinned the old text.
- **`internal/spectest/opincontext.go`** (new, +53) — the ONE canonical port of the pure op-context classifier (`spec.OpInContext` / `spec.OpEffectiveContexts`), plus `Install()` to wire the DI hook. Two sdk test binaries need it (`deploykit`'s compiler tests and `loaderkit`'s live bed); under `internal/` it stays unimportable from outside the module, so the published surface and the placement test are untouched.
- **`deploykit/plan_compile_test.go`** (+9/−29) — its own verbatim copy of that classifier is **deleted**; the file now calls `spectest.Install()` in `init()`. (The copy in the `plugin-fleet` repo at `candy/plugin-fleet/deploy_test_helpers_test.go` stays: that package is out-of-module and cannot import `sdk/internal`.)
- **`loaderkit/scan_live_bed_test.go`** (+195/−3) — the live-or-skip beds below, plus a **new** bed (see "How tested") and two things a *real* `layer-supervisord` materialization forced, both confined to that test file: the shared `liveBedParse` fixture now threads a hand-built, production-modelled `spec.Threaded` snapshot and drops a legacy top-level `version:` before parsing (the real cached manifest carries `version: 2026.261.1747` at `~/.cache/charly/repos/github.com/opencharly/layer-supervisord@v2026.271.1817/charly.yml:1`, which production's `command:migrate` reshapes away before the parse; `ParseCandyManifest`'s node-form branch — the only branch that desugars authored verb sugar — rejects a scalar top-level `version:`, so without the strip the bed would fall back to a decoder that does not desugar the manifest's `command:` verb sugar).
- **Tests** — `loaderkit/init_depends_seed_test.go` (new, +317): local-only project fetches; remote trigger seeds on the next round; termination; no `depends_candy` ⇒ no fetch; `use_packaged`-only ⇒ no supervisord; bare `depends_candy` ⇒ no fetch; a project's own pin is NOT overridden, in both the root-repo and pre-cutover sub-path shapes. And `deploykit/init_depends_ref_test.go` (new, +89): the ref-shaped `depends_candy` matches the scanned key and the machine-venue prune drops it.

The seed is a **fallback, never a version override**: it adds nothing when the composition already names the init runtime, so `PickCandyVersion`'s newest-wins rule can never move a project's own explicit pin.
