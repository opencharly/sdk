Three decisions worth naming, each taken from a live read rather than an assumption:

1. **The systemd timer lives in `deploykit`, not in the new plugin.** `GenerateSystemdUnit`
   emits `Type=simple` with a conditional `ExecStop`, and its argv escaper is **unexported**.
   A timer-triggered job needs a oneshot with no stop. Putting `GenerateSystemdTimer` in
   `deploykit` reuses that escaper **without exporting an escaping primitive into the public
   API**.
2. **The lowered `charly.yml` flat-imports the project's `charly.yml` BY FILE PATH.** The
   loader reads a flat (non-`@`) import entry straight with `os.ReadFile` and never joins it
   against a directory, so a flat import pointing at a **directory** silently fails; only an
   `@`-namespaced entry is stat'ed and joined with the unified file name. A file path is the
   one form that works. The generated file carries that reasoning as a comment.
3. **The lowering emits `--output`, never plugin-task's internal `--json`.** `--json` is
   plugin-task's user-facing **listing** shape; `--output` (added by W3) is the final step's
   raw stdout, which is what lobster's `$id.json` must parse. W1's own goldens assert
   generated **text** only, so no live flag is needed at this gate.

`Lower` produces the `env: {REF_n: $id.path}` + `-p REF_n="$REF_n"` pair so a lobster ref
reaches the charly step shell-safely, and quotes `charly:` argv with `spec.ShellQuote`
(no hand-rolled quoting).

2. **A silently WRONG lowering at cron's divergence from systemd.** `0 3 1 * 1` lowered to

   through — fires when EITHER field matches** when both are restricted, while **systemd's

   correct-looking and wrong, and the doc's blanket claim that "every cron form lowers correctly"

   when both fields are restricted; an unrestricted field is not a restriction, and the
   single-restriction forms are pinned byte-for-byte in the table:

   ```
   "0 3 1 * *"  -> "*-*-01 03:00:00"        (DOM only — unchanged)
   "0 3 * * 1"  -> "Mon *-*-* 03:00:00"     (DOW only — unchanged)
   "0 3 1 * 1"  -> ERROR (the message names both values and the cause)
   ```

   New test **`TestCronToOnCalendarRejectsRestrictedDomAndDow`** — asserts an error, that it quotes

### Review round 5 — BLOCK, and the finding was a REAL bug (`6052e1f`)

The gate auto-closed the predecessor on this verdict. The finding was valid and is fixed here.

**`workflowkit/cron.go` `numField` inferred *contiguity* from the FIRST gap only.** The `..` branch read
`step := vals[1] - vals[0]` and, on `step == 1`, emitted a RANGE — so any list whose first two values
are consecutive but which has a later gap rendered as a range covering values cron never asked for.
**The schedule fires more often than authored:**

```
CronToOnCalendar("0 1,2,3,5 * * *")  ->  "*-*-* 01..05:00:00"   also fires at hour 04  WRONG
CronToOnCalendar("0,1,2,5 * * * *")  ->  "*-*-* *:00..05:00"    also fires at 03, 04    WRONG
```

This is the **same silent-mis-lowering class** as the round-3 DOM+DOW finding, at a different point of
the same function — and the sibling `lo/step` branch directly above it **verifies** its property with a
loop while the `..` branch merely assumed it. `numField`'s own doc comment named only `*` and `lo/step`
and said "else a comma list", so the code contradicted its own doc as well as `CronToOnCalendar`'s
"lists, ranges, steps and names all lower correctly".

**Fix 1 — the `..` branch now verifies contiguity over the whole set**, mirroring the `/step` branch's
existing shape:

```go
if step == 1 {
    contiguous := true
    for i, v := range vals {
        if v != vals[0]+i { contiguous = false; break }
    }
    if contiguous {
        return strconv.Itoa(vals[0]) + ".." + strconv.Itoa(vals[len(vals)-1])
    }
}
```

The `..` rendering is **kept** — it is load-bearing (`*/15 9-17 * * Mon-Fri` legitimately renders
`09..17:00/15:00`) — and a non-contiguous list falls back to the exact comma list.

**Fix 2 — `numField`'s doc comment now names all three renderings** (`*`, `lo..hi` for a contiguous
run, `lo/step`, else a comma list) and states the rule the function now follows.

**Fix 3 — the blast-radius audit (the duty the round-3 fix skipped).** Every rendering path in
`cron.go` was audited for the same class — *a property inferred from a partial observation* — with a
stated verdict: `numField`'s `*` branch (correct — `bitValues` is monotonic and visits each value once,
so the result is sorted/unique/bounded, and with those properties count-equals-range *is* the whole
range); the `lo/step` branch (correct — verifies uniformity, requires `vals[0] == lo`, and
`last+step > hi` encodes systemd's "unbounded from `lo` to the field end"); `pad2List` (correct — a
total `%02d` map with no length or gap inference at all); `padTimeField` (correct — rewrites every
digit run, so a whole comma list pads, while `*`, `..`, `/`, `,` and `-` pass through); the DOW join
(correct — and cron's `7`-as-Sunday is unreachable because robfig's parser rejects it loudly). **No
third instance of the class was found.**

**Fix 4 — the class is now pinned per field**, so no field can silently widen:

```go
{"0 1,2,3,5 * * *",  "*-*-* 01,02,03,05:00:00"},   // non-contiguous HOUR
{"0,1,2,5 * * * *",  "*-*-* *:00,01,02,05:00"},    // non-contiguous MINUTE
{"0 3 1,2,3,5 * *",  "*-*-01,02,03,05 03:00:00"},  // non-contiguous DAY-OF-MONTH
{"0 3 1 1,2,3,5 *",  "*-01,02,03,05-01 03:00:00"}, // non-contiguous MONTH
{"0-5 * * * *",      "*-*-* *:00..05:00"},         // contiguous control: `..` kept
```

The hour and minute rows **failed against `0593f7c`** exactly as predicted:

```
    cron_test.go:51: CronToOnCalendar("0 1,2,3,5 * * *") = "*-*-* 01..05:00:00", want "*-*-* 01,02,03,05:00:00"
    cron_test.go:51: CronToOnCalendar("0,1,2,5 * * * *") = "*-*-* *:00..05:00", want "*-*-* *:00,01,02,05:00"
--- FAIL: TestCronToOnCalendar (0.00s)
```

The DOM and month rows pass **before and after** — the empirical proof that `pad2List` has no shortcut.
