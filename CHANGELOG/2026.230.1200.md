# 2026.230.1200 — enable distro-shipped units through the resolved init only

`EmitInitAssembly` rendered a box's `use_packaged:` system-unit list through **every
ACTIVE init**, emitting one enable command per init into a single Containerfile.

`activeInits` is a SET by design — `InitConfig.ActiveInit` returns every init any candy
in the chain contributes fragments for, and each legitimately gets its own fragment
scratch stage and assembly step. Enablement is different in kind: a distro-shipped unit
is enabled by the ONE init that boots the image, which `InitConfig.ResolveInitSystem`
already resolves into `img.InitSystem`. The enable block now runs only when
`initName == img.InitSystem`; assembly and post-assembly stay per-init.

## This is a live regression on main, not a latent defect

OpenRC landed as a first-class init in `ca76c354` (2026-08-17 21:22). It declares
`supports_packaged: true` with no capability requirement, so from that commit every box
composing a `use_packaged:` system entry has had openrc in its active set and has emitted
`rc-update` regardless of the init that actually boots it.

Generating every box in the superproject and all five `box/<distro>` submodules, twice
from one tree — once with the guard neutralized, once with it in place:

```

  cachyos           7          0            31
```

The superproject's own row is zero: on `main`, `agentteams-worker` has no path to
`virtualization`, so no box defined in this repo composes a `use_packaged:` system entry.
An earlier revision of this entry reported `1 of 15` there. That figure was measured on a
branch that composed an unlanded candy chain reaching `virtualization`, so it was true of
that tree and not of `main` — the affected boxes all live in the `box/<distro>` submodules.

Affected boxes include the landed flagships `fedora-coder` and `charly-fedora`, both on a
Fedora base with no OpenRC, which die at the enable step exactly as `agentteams-worker`
does. `fedora-coder` is built by `check-fedora-coder-pod` — a landed `disposable: true`
bed — so the gate for this change was available all along.

Nothing was silently dropped: `fedora-coder`'s own `.build/fedora-coder/supervisor/`
carries `[program:sshd]`, `[program:virtqemud]` and `[program:virtnetworkd]` — the exact
three units the removed `rc-update` block targeted. The mixed-entry design already covers
them through the resolved init; the foreign arm was pure breakage.

## Coverage

`TestEmitInitAssemblyEnablesOnlyResolvedInit` asserts, per resolved init, that the
resolved init's enable command is present and every foreign one absent. Neutralizing the
guard fails all three subtests.

`TestEmitInitAssemblyKeepsPostAssemblyPerInit` pins the half that must NOT change:
assembly and post-assembly stay per-active-init. The guard was first written as
`continue`, which would also have skipped the post-assembly step below it, and the entire
deploykit suite stayed green with that bug in place — nothing else in the package
references `PostAssemblyTemplate`. This test fails on that short-circuit.

## Companion cutover, sequenced

`candy/charly-build/charly.yml` (superproject) states that a suppressed scratch stage
still leaves `system_enable_template` and `post_assembly_template` running, "independent
of the scratch stage". The enable half of that sentence becomes false once this change is
in effect, and the same passage still lists the init vocabulary as "currently
`supervisord` and `systemd`", which `ca76c354` already falsified. The claim is published
through two projections — `plugins/build/skills/generate/SKILL.md` and
`docs/src/content/docs/recipes/build/generate.md`.

That is one superproject cutover — bump the `sdk` gitlink to this change, correct the
source prose, regenerate both projections — and it must be sequenced against
`opencharly/charly#315`, which edits the same file. It cannot ride this PR: the prose is
only falsified once the pin moves, and the pin cannot move before this merges.
