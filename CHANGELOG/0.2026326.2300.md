# 0.2026326.2300 — fix(packagekit): an unasked-for release keeps nFPM's naming — no silent rename of every deb/apk/ipk

## Summary

Fixes a regression my own `#618` introduced, caught by the consumer's end-to-end test before it could reach a release.

`#618` defaulted `Release` to `"1"` for **every** build. That is not a no-op: nFPM only writes a release into the **file name** when one is set, so the next release would have published `charly_<ver>-1_amd64.deb`, `charly_<ver>-r1_x86_64.apk` and `charly_<ver>-1_x86_64.ipk` instead of the names consumers already download. `plugin-generate-packages`' E2E test asserts the produced file names and failed with exactly those three — the control that should catch it, doing its job.

- `Release` now passes through **unchanged**: `""` keeps today's naming (no suffix for deb/apk/ipk, `-1` for rpm/archlinux, nFPM's own default), and only a caller that asks for a republish gets `-2`.
- The test pins both directions: empty stays empty, and an explicit `"2"` reaches `nfpm.Info` while the upstream version does not move.

The purpose of the field is unchanged and is still what `layer-charly#23` needs: a repaired artifact of an already-shipped version must be publishable as `<version>-2` rather than as a rewritten `<version>-1`.
