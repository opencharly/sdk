# 0.2026276.1136 — fix(sdk): an unresolvable build-config COPY is a generate error, not an emitted directive

Relates to **opencharly/charly#764** — the init-polymorphism defect class. This is the **third
instance** of that class, one layer below the two `#336` already fixed (the missing fetch, the missing
injection).

## Summary

`sdk/deploykit/header_copy_remote.go` makes a build-config asset referenced by a remotely-included
`build.yml` — the init `header_file` — reachable from the image build. It probed the asset in the
project tree, then in every remote candy's `repo@version` cache root, and **returned `relPath`
unchanged when both missed**:

```go
// before
return relPath, nil // not in any remote cache root; leave as authored
```

The caller (`rewriteHeaderCopyForRemote`, reached from `deploykit/init.go:257`) puts that value
straight into the emitted `COPY <src>`, so a miss produced a directive naming a source that had just
been proven absent, and the image build then died **inside the engine** with
`copier: stat: "<relPath>": no such file or directory` — naming neither the candy nor the cache root.
That is exactly the P1 symptom this wave is about.

### RCA — is the fallthrough ever correct?

**No, and that is what makes the fix safe.** `dir` is the build context a `COPY <src>` resolves
against: `deploykit/generate.go` writes the Containerfile to `g.BuildDir/<box>/Containerfile` with
`g.BuildDir = filepath.Join(dir, ".build")` (`render_generator_from_project.go:160`), and the build
runs with `dir` as its context. That is exactly why the materialized branch returns
`.build/_buildconfig/<relPath>` — a **`dir`-relative** path, not a `buildDir`-relative one. Both probes
in the function therefore test the very path a `COPY <relPath>` would resolve to.

Once both probes have missed, the directive cannot do anything but fail. The fallthrough was
reachable **only when the COPY was already doomed**, so turning it into a generate-time error is a
pure fail-fast: it can never reject a build that would otherwise have succeeded, and it converts an
opaque engine error into one that reports the asset and every root that was searched.

## What changed

- **`deploykit/header_copy_remote.go`** (+31/−4) — the cache roots are bound once
  (`roots := remoteBuildConfigCacheRoots(candies)`) instead of being recomputed in the loop header,
  and the fallthrough becomes a hard error naming the asset, the project-tree path that was tried,
  and **every** cache root searched. When there is no remote candy at all the message says
  `no remote candy is in the resolved set` rather than printing an empty list. The doc comments now
  state the build-context invariant the reasoning rests on, and that a non-COPY line still passes
  through as-authored (the new error must not over-fire).
- **`deploykit/header_copy_remote_test.go`** (new, 169 lines) — six tests covering: the missing
  asset being a hard error that names asset + local path + searched root; the no-remote-candy
  wording; the remote cache root still materializing to a `dir`-relative source that really exists
  there; the local project asset still passing through unchanged; the wrapper propagating rather
  than swallowing; and non-COPY lines passing through verbatim.

### Why a unit test is the right boundary here (R7a)

This function crosses **no** live-service boundary: it is a filesystem `stat` plus a `cp`, with no
network, no `gh` call, no engine call. `R7a` requires the live-or-skip discipline for a boundary that
talks to a real service and explicitly keeps "pure/deterministic in-repo logic unit-testable
normally". No mock or stub of any external service is involved — the tests exercise the real exported
mechanism against real temporary trees. There is no `LIVE_`-gated test in `deploykit` today, because
none of its surface needs one.

### The live end-to-end path

`RewriteHeaderCopyForRemote` is wired by `NewRenderGeneratorFromProject` and driven by a plugin over
the reverse channel. Its **success** branches are unchanged by this PR (same inputs → same outputs);
only the previously-unreachable-and-doomed branch changes behaviour. Driving it end to end against a
real charly requires a charly binary built against this sdk, which is the consumer leg held behind
`opencharly/charly#762` — so that run is downstream of this PR, not a substitute for it.
