# 0.2026276.48 — fix(loaderkit): classify in-body members of a core resource kind (#748)

## Summary

Fixes the **load-time half** of `opencharly/charly#748`. The fix is two halves across two repos; **this is the producer half (leg 1)**, and the `charly` half follows it as leg 2.

**What was broken.** An in-body member — a resource key authored *inside* its bed's kind body, e.g.

```yaml
check-group:
    vm:
        from: eval-vm
        check-group-member:      # inside the vm body = deploys INTO the vm
            local:
                from: check-group-app
```

— was never classified as a member **child** whenever the bed's kind word had not been threaded into `Threaded.DeploySubstrates`. That set is filled only from the host's **out-of-process** deploy providers (`charly/loader_threaded.go:184`, under `case ClassDeployTarget:`) plus the parse-time prescan of a project's declared plugin words (`:196`), so before those connect a core word such as `vm` is absent from it while still being a core **resource kind** (`spec.ResourceKinds`). The parse then took the **structural** branch, whose rule is the F5 input rule — *the KEY ITSELF is a member-disc word* — and an in-body member's key is its **own name** (`check-group-member`), the kind word living in its VALUE. So the member was skipped as opaque data and `pn.Children` stayed empty.

**The change** (`loaderkit/parse.go:209`): `if t.DeploySubstrates[disc] || resourceKindSet[disc]`. `spec.ResourceKinds` is documented as exactly *the DEPLOYABLE subset of the kind keywords — the kinds whose `#Node` arm nests a sub-ENTITY (resource) child*, and `memberDisc` already consults it (`parse.go:63-64`) — the substrate-parent test did not.

**A core resource kind must not depend on provider-connection order.** `Threaded.DeploySubstrates` is populated in only two ways — a *connected* deploy provider and the prescan of a project's **declared** plugin words — while the core substrate words reach the loader from the compiled-in `plugin-substrate` as `kind` providers, whose deploy backends run out-of-process. So at parse time `vm` is absent from `DeploySubstrates` until a backend connects, and the classification of an in-body member must not hinge on that race.

**Why leg 2 is still needed, and why this one lands first.** Once the member IS a child, the authored body still carries its key — that key IS the position channel the derivation stamps `Member.Position` from — while `charly`'s top-level `#<Kind>Value` gate validated the authored body verbatim and so rejects the node. charly resolves this module from the Go proxy, so its half can only land against a **tag** of this one.

**The load-time guard for the host-deploying shape is NOT in this PR.** By operator ruling it is split out to `opencharly/sdk#330`, where it lands as its own producer-first chain together with the org-wide `host: local` marking sweep: it fires at **project resolve**, so its blast radius is the whole bed corpus, and keeping it here would block this fix behind an org-wide cutover of unmeasured size.
