# 0.2026268.1823 — feat(sdk): thread per-invocation RunEnv ctx through the bed session

## Summary of changes

Adopt `spec v0.2026268.1800` and thread the invocation's `context.Context` through
every in-process resolver a concurrent check-bed roster reaches, so bed isolation is
**explicit per-invocation data** rather than process-global `os.Setenv`
(plan §4.2 / F8; RCA issues 1, 2, 7). This is the sdk leg of the `check-bed-roster`
cutover.

### What changed
- **`deploykit`** — `LoadDeployConfig` / `SaveDeployConfig` / `MutateDeployConfig` /
  `AcquireDeployConfigLock` / `SaveDeployState` / `CleanDeployEntry` /
  `SaveVmDeployState` / `RemoveVmDeployEntry` / `LoadDeployConfigForRead|Write` take
  a trailing `ctx` (variadic — see the R5 note below) and resolve the overlay path via
  `spec.DefaultDeployConfigPath(ctx)`. A bed's ctx `RunEnv` therefore names its OWN
  overlay; sibling beds never share one.
  `AcquireDeployConfigLock` bounds the wait SHORT (10s) so a contended overlay write
  fails fast with the holder named (RCA issue 2 — the silent 30-minute cross-bed
  deadlock).
- **`deploykit.PersistBedDeployOverrides` + `BringUpMembers`/`TearDownMembers`** take
  `ctx` and pass it to every forked member child via `proc.RunCharlySubcommandCtx`.
  This closes the most severe live defect (RCA issue 7): those forks previously
  inherited the parent PROCESS env, so once bed isolation retired `os.Setenv` a member
  child resolved the OPERATOR's real `~/.config/charly/charly.yml` and wrote bed state
  into it.
- **`loaderkit`** — `hostDeployConfigDir(ctx)` and the repo-override reader
  (`runEnvValue`) honor the ctx `RunEnv`. `runEnvValue` delegates to
  `spec.RunEnvGet`, which wins on the ctx value and falls back to `os.Getenv` **inside
  RunEnvGet itself** — byte-identical to the former plain `os.Getenv` for the legacy
  host CLI (pinned by `runenv_value_test.go`).
- **`kit`** — re-export `AcquireFileLockWithin`.

**Closes / relates to:** sdk leg of the check-bed-roster cutover (plan §4.2).
Depends on spec#159 (merged, tagged `v0.2026268.1800`, pinned here).

### R5 disposition (the trailing-variadic ctx)
The validator allows either (a) make `ctx` required and migrate in-tree, or (b) **name
the immediate-next batch that removes the variadic**. This leg takes **(b)**: making
`ctx` required breaks **~32 call sites across 6 separate consumer repos**
(`plugin-pod`, `plugin-deploy-pod`, `plugin-fleet`, `plugin-vm`, `plugin-substrate`,
`plugin-check`), each a submodule that must migrate in its OWN SDK-first leg — outside
this leg's coherent scope per the umbrella's cutover rule. The removal is named:
**"plugin-consumers: make deploy-config ctx required"**, documented on
`LoadDeployConfig`. Every BED path already threads ctx (the roster is the only
concurrent in-process caller), so no fail-open path is reachable from the fixed
behavior; a future omission is caught by the named batch's compile break. (The
validator reviewed this and marked it **verified-non-blocking**.)

- **R4** — no sleep/retry. The overlay lock's new SHORT bound
  (`deployConfigLockWait = 10s`) is a deliberate FIXED constant, NOT config-sourced: it
  is a SAFETY bound on an internal lock, and a config knob would let a misconfiguration
  re-introduce the unbounded hang this closes. It bounds a hold that is milliseconds in
  practice — hundreds of times headroom — and is far below the 30-minute image-build
  bound the lock previously inherited. Documented at the constant and at
  `MutateDeployConfig` (whose stale "waits rather than failing" comment is corrected).
