# 0.2026287.1747 — feat(buildcache): the one store-backed plugin build cache — and the sdk/deploykit duplicate cluster is DELETED

## Summary

Phase 1 of the one-store wave (`opencharly/charly#896`): **the plugin build cache becomes the ONE
store-backed cache, keyed by D-STORE-4's inputs** — and the `sdk/deploykit` duplicate cluster is
**DELETED in this PR**.

The plugin build cache had **two live sibling implementations of one concept** — `charly/charly/plugin_loader.go`'s
cluster and a copy in `sdk/deploykit/bake_plugins.go` — both keyed by the **absolute source path**,
which is why a content-stamp sidecar (`.stamp`) and a per-binary lock (`.lock`) had to live **inside
the cache tree** beside each binary. A path key cannot answer "is this binary still current" (a
dependency bump leaves the path unchanged), which is exactly why the sidecar had to exist.

This adds **`sdk/buildcache`**: one implementation whose key **is** D-STORE-4's input set. Because
the **key is the freshness answer**, `.stamp` is impossible by construction rather than merely
deleted; the per-key build lock moves to the **runtime root**, where locks belong (a store tree
contains no locks). The payload is a content-addressed blob and the view a caller execs is a
**hardlink** of it, so the bytes exist once per digest.

**Deleted here (R5):** `deploykit/bake_plugins.go`'s second copy — `buildPluginBinary` with its
`safePluginBinName`, `pluginBuildCacheDir`, `pluginSourceTag`, `pluginBuildVCSFlag`,
`pluginBuildVCSFlagForContext`, `pluginBuildEnv`, `pluginSourceHasGitRevision` and `pluginGitProbe`
helpers, nine functions, all path-keyed, with no content-stamp reuse. `EmitBakedPlugins` — the
load-bearing `bake_plugin:` producer for `distro-omarchy`'s charly-mise-consumer chain — now calls
`buildcache.Build`; the emitted Containerfile fragment, the
`bakedPluginDir`/`bakedPluginImageDir`/`bakedPluginEnv` constants and the emit logic are unchanged.
It also deletes a **measurably false comment**: `buildPluginBinary`'s doc comment claimed
*"Byte-identical logic to charly/plugin_loader.go's function of the same name"* and was not — the
package-main copy had grown content-stamp reuse and this copy never did, so the two copies differed
in exactly the freshness behaviour that matters.

## The key's coverage, and the mutation that proves it

The key covers **everything that distinguishes the outputs** — which is *not* the same as the inputs
first thought of. D-STORE-4's inputs identify the **bytes**; the cache serves **built units**. Two
distinct plugins with byte-identical source are different units with the same bytes.

```
$ # eight concurrent distinct-NAME builds sharing one module source, with the plugin name dropped
$ # from the key (mutation M10 on this tree)
buildcache_test.go:424: the store holds 1 entries after 8 concurrent distinct-key builds — 7 were
  silently LOST (the operation was not serialized)
```

**A same-source test could never have found this**, because in production two plugins usually differ
in source too — the bug hides exactly where they do not. The plugin's leaf name is therefore part of
the key.

Content, never location:

| Input | How it enters the key |
|---|---|
| plugin identity | the candy's **leaf** name (never a path, never the full `@github` ref) |
| module source | content of the candy's tree **plus every module reached through a transitive local `replace`** — so an **uncommitted** edit in a replace target invalidates (a git-HEAD key would miss it) |
| `go.sum` | content digest, labelled as its own component (D-STORE-4 names it) |
| toolchain | `runtime.Version()` |
| platform | `GOOS/GOARCH/GOARM/GOAMD64/CGO_ENABLED/GOFLAGS/GOEXPERIMENT/GOWORK` |
| `GOWORK` | a **content digest** of the resolved `go.work`, never its path |
| `GOFLAGS` | every flag and value verbatim, **except** any `-flag=<existing entry>` which contributes its content identity — **mechanically, for ANY flag** (not a list of known ones); a FILE gives its content digest, a DIRECTORY a tree digest over its entries, and a directory's **name** does not participate (a name is location) |

No absolute path and no timestamp reaches a payload (D-STORE-6); the resolution record lives in the
entry's **annotations**, outside every payload digest by design. **Key computation is pure** — it
never publishes to the store, so a lookup cannot populate it (which is why `storekit`'s tree
primitive is deliberately not used to compute a key).

## The concurrency story, proven — including one defect it found

**Method, stated as method:** the concurrency tests were written **before** the concurrency story was
claimed, so the defect above surfaced as a **failing test** rather than as a false sentence in this
body.

```
$ # six concurrent builds of the SAME key must issue exactly ONE `go build`
$ go test ./buildcache/ -run TestBuild_ConcurrentSameKeySerializes -count=1
ok  	github.com/opencharly/sdk/buildcache	0.6s
```

**Every intermediate state is a MISS, never a wrong hit** — the payload blob is published before the
view is linked, and the entry after both, so a reader that catches the window rebuilds. That is the
conservative direction.
