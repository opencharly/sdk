# 0.2026288.2325 — fix(deploykit): read a moved skill's prose from its file, so the `ai.opencharly.skill` label keeps it (#418)

`deploykit.CollectSkills` is the ONE producer of a box's `ai.opencharly.skill` OCI label. It
projected the `skill:` entity straight onto the wire entry, so the moment a repo moved its
skill's prose into the file that repo owns — `.agents/skills/<name>/SKILL.md`, spec#247 — the
label entry shipped with `description` absent and `content: ""`: the routing metadata survived,
the prose silently did not. The settled cutover design names this read-back (ruling D6 / §4.6 of
`opencharly/opencharly#496`) as L2's obligation; L2 landed the shared reader *with tests and no
consumer*, and no leg in the plan's table owns wiring it. Nothing in the plan could have caught
it — a library with no caller has green tests by construction — and it was found by reading a
**built image's** label, which is what this PR closes.

## Summary

`CollectSkills` now reads a composed skill's prose through `candywalk.ReadSkillFile` — the ONE
reader `candy/plugin-marketplace` also uses — from the owning candy's source dir, and projects it
onto the wire `spec.LabelSkillEntry`. The node keeps the routing metadata (`family`, `owner`,
`triggers`, `category`), the file keeps the prose, and the label keeps carrying both.

Four files, every one of them accounted for:

- **`deploykit/skills_collect.go`** — the read-back. `CollectSkills` resolves the skill id (the
  node's `name:`, else the node name — spec#247's default, which is also the directory the file
  lives in), reads `<candy source dir>/.agents/skills/<name>/SKILL.md` via `candywalk.ReadSkillFile`,
  and fills `description`/`content`/`references` from it. A node with an in-line body and no file
  is the transitional form and is projected exactly as authored. The `ai.opencharly.skills` typo in
  the file's header comment is corrected to the label's real key, `ai.opencharly.skill`. It also
  documents the one stated limit (below).
- **`deploykit/render_prep.go`** — `CollectSkills` and `buildBakedMetadata` now return an error.
  A skill with neither an in-line body nor a file, a malformed/unreadable file, and a body that
  does not decode were all silent before (`continue`, or an empty projected entry). Each now
  fails the build. `buildBakedMetadata`'s only caller is `RenderPrepBox`, which already returns an
  error, so the failure reaches the build-prep seam; there is no other caller anywhere (measured,
  see below).
- **`deploykit/skills_collect_test.go`** — five cases (the existing one repointed at the new
  signature, and four added): prose read from the file; the node name as the id; a body-less node
  failing LOUD; a file whose frontmatter `name` disagrees with its directory failing LOUD; and the
  WHOLE entry's wire form, including the reference-less case the round-1 verdict asked about (see
  below). The file also carries the fixture both rounds share: `writeSkillFile` (frontmatter +
  body + `references/<stem>.md`, under the Agent-Skills location) and `skillFixtureID`, the
  constant naming the one skill id every arm authors — a parameter there could never vary, which
  is what `unparam` said in this round's own gate run.
- **`deploykit/baked_box_label_test.go`** — the two `buildBakedMetadata` call sites follow the
  new signature.

**The reference-less entry's wire form is unchanged, and now covered.** Round 1's projection built
its references slice with `make([]spec.LabelSkillReference, 0, len(s.References))`; the read-back
appends onto a nil slice, so a reference-less skill hands the wire `nil` where it used to hand an
empty slice. The field carries `json:"references,omitempty"`, so the two are indistinguishable in
the emitted label — and that is not an argument, it is a test:

```
$ go test ./deploykit/ -run TestCollectSkills_ReferenceLessEntryWireForm -v -count=1
=== RUN   TestCollectSkills_ReferenceLessEntryWireForm
--- PASS: TestCollectSkills_ReferenceLessEntryWireForm (0.00s)
PASS

```

Its three arms pin: nil and `[]spec.LabelSkillReference{}` marshal **byte-identically**; a
file-sourced reference-less entry carries no `references` key at all and keeps its prose; and a
skill whose file has `references/<stem>.md` still ships it, name and content. The live A/B below
extends to the whole entry for the same reason.

**Closes `opencharly/sdk#418`.**

Before the fix the moved skill's entry loses `description` outright; after it, the two arms' key
sets are identical and **every** field but `content` is equal. `references` is absent in all four
entries — the `omitempty` property, measured at the boundary rather than argued. The one residual
difference is a single leading newline in `content`, which is the authored file's own shape
(`extract` writes `frontmatter + "\n" + body`) and is byte-for-byte what `plugin-marketplace`
computes from the same file; `plugin-marketplace#29` closed that writer-side, and the L6.2
re-extraction picks it up. Trimming it in the reader instead would make the label disagree with
the corpus, which is the R2 failure this reader exists to prevent.

**One stated limit, filed not parked.** A candy that declares a NON-default `skills:` tree is not
resolvable on this path: the authored list lives on `#Candy` (`spec.Candy`, which the marketplace
generator reads off the authored entity), and the resolved-project envelope this collector walks
carries no such field — `spec.CandyModel` has `SourceDir` but not `Skills`, and `spec.CandyView`
has neither. The standard location is used, and the failure mode is LOUD rather than silent: such a
node finds no file and `CollectSkills` errors naming the tree it looked in. That gap is
**`opencharly/spec#254`**, filed with the measurement and the two possible fixes; it is not
deferred to "its own landing" in prose.
