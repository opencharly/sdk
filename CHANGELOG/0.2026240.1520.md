# 0.2026240.1520 — fix(init): honour candy_file:; report an unsatisfiable init depends_candy

## Summary

Two init defects that both end in silence. They land together because both are init
resolution/collection correctness in the same package, provable by one gate: **B1's last item** and
batch **B9**.

### 1. `candy_file:` was dead

`loaderkit.ScanCandyManifest` is init-agnostic by construction — it has no init definition in scope
— so it collected a hardcoded `*.service` glob into `CandyModel.ServiceFiles`, and `def.CandyFiles`
was consulted for init **detection** only. Two silent consequences:

- OpenRC's declared `candy_file: ['*.initd']` had **never matched a file**, because no `.initd` was
  ever collected for it to claim.
- An init could not widen its file set at all: adding `*.socket` to the vocabulary would have been a
  no-op, since the scan still found only `*.service`.

**Fixed by globbing at the point of use.** The three `file_copy` consumption sites in
`deploykit/init.go` are the only place where the candy directory and the resolved init are in scope
together, so `initUnitFiles(def, layer)` globs the init's own patterns there.

That choice matters. The alternatives were to thread the init vocabulary into the scanner (an
exported signature change rippling into charly) or to hardcode a superset of "unit-ish" extensions
in the scanner (replacing one hardcoded list with a longer one). Globbing at the consumption site
needs neither: **the vocabulary decides**, which is what `candy_file:` was always supposed to mean.

An init declaring no `candy_file:` keeps the historical `*.service` glob, so every shipped init
renders exactly as before.

### 2. An unsatisfiable `depends_candy` built an unstartable image, silently (B9)

`InjectInitDependsCandy` injects the resolved init's `depends_candy` at every box-resolution
chokepoint — which is why a box normally never declares its own init. When that candy is not in the
project's scanned set it correctly **declines** (injecting a dangling name "would manufacture an
'unknown candy' resolve failure that buries the project's real defect"), but it said **nothing**.

The build then *succeeded*, stamping the init and its entrypoint onto an image with no binary to run
it, and the failure surfaced only at `charly start`:

```
Error: crun: executable file `supervisord` not found in $PATH
```

— naming neither the init that was resolved, nor the candy that would have satisfied it, nor the
fact that a project-scan gap is the cause. Every fact needed is known where the injector gives up,
and the condition is decidable at **build** time.

Declining to inject is right. Saying nothing is the defect.

## How tested

### Live — the B9 diagnostic, at build time

A project with a `service:` candy and no `supervisord` candy in scan range (the shape every
standalone candy repo and spike project has):

```
$ charly box generate lonely-init-box
warning: box "lonely-init-box" resolves init "supervisord", which depends on the
"supervisord" candy, but no candy of that name is in this project's scanned set —
nothing was injected, so the image will declare init "supervisord" with no supervisord
binary and fail at start. Reference the candy directly in the box's candy: list, or pull
it in via a composed candy's require:.
```

Before this change that command printed nothing and exited 0.

### Coverage that fails without the change

`TestInitUnitFilesHonoursCandyFilePatterns` is table-driven over the four cases that distinguish the
fix from the old hardcoded glob — OpenRC claiming `.initd`, an init claiming several patterns, the
no-`candy_file` fallback, and unrelated files never being claimed. The first two return **nothing**
on the old code.

`TestUnsatisfiedInitDependsIsReported` asserts the report happens, names the box and the candy, and
— importantly — does **not** repeat across the three chokepoints.

## Design note: where the dedupe lives

The report is deduped per `(box, init, candy)` at the **call path**, not inside the reporting hook.
"Report at most once" is the caller's policy; the hook only decides *how* to report. That split is
what lets a test swap the hook and still observe the policy — with the dedupe inside the hook, the
first version of this test swapped it away and silently stopped testing the thing it named.

It is a warning rather than a hard error because the injector also runs on partially-resolved
configs where a later pass still supplies the candy; failing there would break them.

## Not covered

- **Widening systemd's `candy_file:` to `*.socket`/`*.target`/`*.slice`** is now a pure **data**
  change in charly's `charly.yml` — which is the point of this fix — but it is not made here,
  because systemd's `assembly_template` still hardcodes the extension twice
  (`cp /systemd/*.service …` and a `systemctl --global enable` loop that would be handed a `.slice`).
  Widening the patterns without rewriting that assembly would stage files the image never copies.
  Both are charly-side template data and land together there.
