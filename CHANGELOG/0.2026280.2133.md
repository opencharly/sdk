# 0.2026280.2133 — fix(sdk): carry a check verb's CapturedValue on the out-of-process wire (R3)

## Summary

`ServeCheckVerb` is the OUT-OF-PROCESS placement of a host-coupled kit check verb. Its `Invoke` ended with:

```go
res := s.kv.RunVerb(ctx, cc, &op)
return ResultJSON(kitStatusWire(res.Status), res.Message)
```

so a probe's `CapturedValue` — the parsed body of an HTTP probe, the matched fields of a log scan, the row a SQL check read — **was dropped on its way to the host**, while the in-process path already carried it (`charly/checkverb_result.go`'s `checkResultFromVerb`, `0c62bc1c`). The gap bit exactly the family `spec/ops/ops.go:224`'s own prose names as the field's purpose: the out-of-process probes (`cdp`/`kube`/`appium`/`adb`/`wl`/…). opencharly/charly#780.

The reply is now built in **one** place, `checkVerbReply`: it encodes the verdict's JSON-encoded capture as the wire's raw `captured_value` (the operator-ruled shape for #780 — JSON-encoded in both directions) and reports a **non-JSON stash as a FAIL naming the cause**, rather than emitting a corrupt `captured_value` or dropping it silently (R1). A verdict that captured nothing stays **byte-identical** to the pre-extension wire (the field's `omitempty`), asserted directly.

**Files (2):** `checkverb.go` (the reply is built by `checkVerbReply` + `capturedWireValue`), `checkverb_test.go` (new).

Refs opencharly/charly#780 — Refs opencharly/spec#194 (the contract's own doc for the field, whose spec leg is #203).

### Why the guard sits where every consumer's bytes cross

`checkverb_test.go` never re-declares the wire shape: it carries the reply across **the protobuf hop go-plugin's gRPC channel performs** and decodes it with the **contract module's own decoder**, `ops.ParseResultJSONFull` — so the assertion is about the bytes that cross (R3: one declaration per wire surface; the decoder lives in `spec/ops`). Five tests: the capture survives and is a JSON document; the empty capture is byte-identical to `ResultJSON`; a non-JSON stash is a loud FAIL; the status mapping survives with a capture; and the captureless builder's drop is pinned as its own test, so a future revert of `checkVerbReply` fails visibly instead of quietly restoring the defect.
