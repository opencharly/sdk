# 0.2026287.753 — fix(vmshared): populate the pacman keyring before the install transaction, not after the image stops shipping one

## Summary

**The guest-provisioning fix that `opencharly/charly#828` cannot land without, made in the repo that owns it.** That PR converges the Arch cloud-image pin from a dated directory onto the live rolling URL — correct, and the mirror really does rotate its dated directories. **What it surfaced is this:** the pacman-family branch of the cloud-init renderer omits the `packages:` key and prepends `pacman -Sy --needed --noconfirm <union>` to `runcmd` instead, and that path has always relied on an invariant nobody wrote down — **the base image ships a *populated* `/etc/pacman.d/gnupg`.** The dated image did. The live rolling image does not, so `-Sy` cannot verify a single signature and the whole transaction fails: **the guest fetches its base image and then cannot provision**, which is what left all six consuming `kind: vm` beds red after `#828`.

One step, in this branch only: `pacman-key --init && pacman-key --populate`, ahead of `pacmanCmd`.
