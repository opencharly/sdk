# 0.2026242.1217 — feat(vmshared): four arithmetic funcs for installer answer templates

## Summary

spec#80 put the target disk size in `#InstallerSeedContext`. **Go templates cannot add or
subtract at all**, so a template still could not compute a root partition from it.

Installer answer formats state partition geometry as absolute numbers — archinstall indexes
`partition['size']` with no default and has no fill-remaining sentinel — so subtracting the
ESP from the disk is not optional.

## Four functions, and that is the design

```go
var seedTemplateFuncs = template.FuncMap{
	"add": func(a, b int64) int64 { return a + b },
	"sub": func(a, b int64) int64 { return a - b },
	"mib": func(n int64) int64 { return n * 1024 * 1024 },
	"gib": func(n int64) int64 { return n * 1024 * 1024 * 1024 },
}
```

**Deliberately four and no more.** This is not a general-purpose expression language.
Everything a seed needs is integer byte arithmetic, and every function added here is
somewhere a distro author can hide logic where no gate can see it — the answer file is
rendered on the host and consumed inside a guest, so a template that computes something
surprising is invisible at both ends.

`mib` and `gib` exist so a template reads `gib 2` rather than `2147483648`. That is the form
a reviewer can check against upstream's own script line by line, which matters when the
consequence of a wrong number is a mis-partitioned disk.

## How tested

**Three tests, each verified to discriminate.**

```
$ go test -count=1 ./vmshared/ -run 'SeedTemplateArithmetic'
ok  	github.com/opencharly/sdk/vmshared	0.003s
```

### 1 — it reproduces upstream's exact partition math

The test renders Omarchy's configurator arithmetic through a real template:

```
boot_start={{mib 1}}
boot_size={{gib 2}}
main_start={{add (gib 2) (mib 1)}}
main_size={{sub (sub .DiskSizeBytes (add (gib 2) (mib 1))) (mib 1)}}
```

against a 40 GiB disk, and checks it against numbers computed **independently in the test**,
so a wrong helper cannot pass. It also asserts its own constants first, so a typo in the
expected string is caught rather than baked in:

```
boot_start=1048576
boot_size=2147483648
main_start=2148532224
main_size=40800092160
```

### 2 — an absent disk size renders a NEGATIVE number

This documents behaviour rather than asserting an error, and the distinction is the point:
the renderer cannot know that `0` is invalid for a given answer format, so it must not
pretend to. `{{sub .DiskSizeBytes (gib 2)}}` with no disk size renders `-2147483648`.

That is precisely why `BuildIsoVM` must populate `DiskSizeBytes` **unconditionally** for an
iso source rather than treating it as optional there — the test says so in place, so the
next person does not make it conditional.

### 3 — the func set is closed

A template reaching for `div` fails at **parse** time with the name in the message, rather
than silently rendering an empty string into an answer file.

**Negative control — drop `Funcs()` entirely:** two of the three tests fail.
