# 0.2026241.933 — feat(loaderkit): route every loader git operation through the centralized GitClient

## Summary

The loader's git operations now go through `spec/refs.GitClient` (the centralized git layer from spec#65) instead of each consumer running git commands itself (issues #423, #208). The GitClient cache lives in the `cache:` section of the PER-HOST charly.yml (`~/.config/charly/charly.yml`) — the single home for local system state (deployments, ledger, system, cache) — per spec#66, NOT in ad-hoc JSON files under `~/.cache/charly/repos`.

- **`refs_seams_executor.go`**: a process-wide `gitClient()` singleton whose cache lives in the `cache:` section of the per-host charly.yml (honoring the `CHARLY_DEPLOY_CONFIG` override); the `LatestTag` seam callback uses it.
- **`canonical_ref.go` + `scan_orchestrate.go`**: `GitDefaultBranch` calls go through `gitClient().DefaultBranch` (24h TTL).
- **`refs_collect.go`**: mutable-ref DOWNLOADS go through `gitClient().Download` (5m TTL — a branch can move, but not on every invocation, so the status fan-out pays the download once); first-startup WARM-UP prints `charly: fetching git metadata for N repo(s)...` when the cache is cold.
- **`scan_candy.go`**: the actual candy name is the manifest node key (`ly.Name`), so bare-name refs to a root-level standalone candy repo resolve.
- **`scan_orchestrate.go`**: a remote candy is ALSO keyed by its bare name, so a transitive bare-name dep (`versatiles-style` inside pod-versatiles-frontend's list) resolves instead of failing with "unknown candy".
- **`go.mod`**: bump spec to the GitClient + cache-in-charly.yml tag (spec#66).
- Also carries the retention-defaults seam (`ResolveRetentionDefaultsViaSeam` — the #423 clean-hang fix) and the two scan fixes from the earlier session.
