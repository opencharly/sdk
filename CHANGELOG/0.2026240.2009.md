# 0.2026240.2009 — feat(qemu): render video, display and qemu_override on the direct-QEMU backend

## Summary

The direct-QEMU leg of **B6 — the GPU configuration surface**.

`RenderQemuArgv` emitted a flat `-display none` and **no video device at all**:

```go
args = append(args, "-display", "none", "-daemonize")
```

So every `libvirt.devices.video`, `graphics` and `qemu_override` field silently did nothing on
`--backend qemu`. `-display none` is correct only when no video is declared; with one declared
it is an unrequested headless VM that *looks* configured — the failure mode where the YAML is
accepted, the field is dropped, and the guest gets hardware nobody asked for.

## What it renders now

- **The video device**, mapping libvirt's `<model device='…'/>` vocabulary to the QEMU device
  names. These are **not the same string** — libvirt's `virtio-gpu` is QEMU's `virtio-gpu-pci`,
  `virtio-gpu-gl` is `virtio-gpu-gl-pci` — while the VGA-flavoured variants keep their names
  because `virtio-vga` already *is* the device name. Emitting libvirt's spelling verbatim fails
  at startup.
- **`blob=on`**, and `heads` → `max_outputs` on the virtio-gpu family.
- **Each device's `qemu_override` properties.** On this backend these are not an escape hatch,
  they are the main road: `drm_native_context`, `hostmem`, `max_hostmem` and `venus` have no
  libvirt element at all, and `qemu-system-x86_64 -device virtio-vga-gl,help` lists exactly
  those four plus `blob`.
- **`-display egl-headless,rendernode=…`**, which is what gives the guest's virtio-gpu a host
  GL context and pins it to a specific DRM node.
- **The memfd shared-memory backing** blob resources require — the same coupling the libvirt
  renderer auto-pairs, so an author enabling `blob` never has to discover the requirement from
  a failed start.

Plus the `vmshared` aliases for the three new spec types (`LibvirtGraphicsGL`,
`LibvirtVideoResolution`, `LibvirtVideoDriver`) and the spec pin moved to the merged
`v0.2026240.1952`.

## One value, two spellings

A bool is `on`/`off` on the QEMU command line and `true`/`false` in libvirt's
`<qemu:property type='bool'/>`. QEMU rejects `true` for an on/off property, so getting this
wrong fails at **VM start**, not at render — which is why the value is rendered per backend
rather than stringified once at decode. Pinned by
`TestQemuOverrideProps_BoolsAreOnOffAndOrderIsStable`, which also pins **sorted** property
order: Go map iteration is random, and an argv that differs between runs is untestable and
unreadable in a process listing.

## Not covered

- **vnc / spice / rdp / dbus graphics.** These are wired by their own QEMU options rather than
  `-display`, and the direct backend has never rendered them (its doc comment lists
  `graphics/spice` among the documented gaps, alongside virtiofs and PCI hostdev). The display
  therefore stays `none` for those rather than pretending otherwise. Unchanged by this PR — it
  neither closes nor widens that gap.
- **QXL's vram quartet** (`ram`/`vram64`/`vgamem`) is modelled in the schema and rendered by the
  libvirt bridge, but not mapped to QEMU's `-device qxl-vga,vram_size=…` form here. Legacy-guest
  territory, and outside the GPU-in-VM scope this batch is sized to.
