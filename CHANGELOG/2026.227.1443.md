# 2026.227.1243 — namespace-aware box collectors: imported boxes bake their full label contract

Every box the superproject builds is reached under an import namespace
(`fedora.charly-fedora`) since the box inversion moved boxes into the
`box/<distro>` submodules. The box-collector family entered on that qualified
name through `cfg.BoxConfig` / `cfg.WalkBaseChain` — both deliberately FLAT,
root-internal lookups — found nothing, and returned an EMPTY result. So the
entire imported catalog shipped without:

- `ai.opencharly.description` — ADE's baked `plan:`. With the label absent,
  `charly check box <image>` answered `No plan steps defined for this image`
  and exited **0**: a gate that could not fail, across every box in the
  catalog.
- `ai.opencharly.port` — and therefore **no `EXPOSE` directives at all**.
- `ai.opencharly.volume`, `security`, `shell`, `alias`, `hook`, `skills`, `data`, and
  the box-level `env`.

Measured on `fedora.charly-fedora`, built both ways: from the superproject the
Containerfile carried 21 `ai.opencharly.*` labels and zero `EXPOSE`; from
`box/fedora` as its own project root, 25 labels and one `EXPOSE`. The five-label
gap was exactly `description`, `port`, `security`, `shell`, `volume`.

## The seam

- **`deploykit/config_candy_chain.go`** — new `BoxOwner(cfg, boxName)`: the ONE
  namespace-aware entry the whole family shares, resolving a possibly-qualified
  ref to the Config that OWNS it, the leaf name inside that owner, and its
  authored `BoxConfig`. It is a thin composition of the EXISTING
  `spec.ResolveBoxRef` + `spec.LeafName` — no new resolution mechanism.

  The descent mirrors `buildkit.ResolveBox`'s own entry descent, which already
  makes every one of its callers namespace-aware through a single chokepoint.
  **`spec` is deliberately untouched**: `WalkBaseChain` keeps its documented
  root-internal contract (it is now walked in the OWNER's config, where a base
  ref is relative, and its deliberate refusal to cross a namespace boundary
  MID-chain still holds), and `BoxConfig` stays flat because `WalkBaseChain`
  uses it as the "is this base internal?" predicate — making that descend would
  silently change the chain-stop semantics for every consumer.

- `BoxCandyChain` (the base-chain walk behind `CollectDescriptions`,
  `CollectBoxPorts`, `CollectBoxVolume`, `CollectHooks`, `CollectShell`,
  `CollectSkills`) and `BoxDirectCandies` (behind `CollectSecurity`,
  `CollectBoxAlias`) both enter through `BoxOwner`.

- `collectChainDataEntries` (`render_prep.go`, the `data` label) hand-rolled its
  own copy of the base-chain walk; it now uses `BoxCandyChain` like every
  sibling. See "the eleventh site" below.

- The box-level authored reads in `description_collect.go`, `shell_collect.go`,
  `security.go`, `box_build_resolve.go` (`CollectBoxAlias` + `ResolveBoxEngine`),
  `render_prep.go` (the `env` label) and `resolved_project.go`
  (`ProjectBoxAggregates` — plan / description / env / env_file / security on
  the ResolvedProject envelope) do the same.

The candy map stays flat and shared across namespaces — its keys are bare local
names or full remote refs, never namespace-qualified — which is why an owner's
namespace-relative candy refs resolve against the SAME layers map the render
path already used. That is why `service`, `init` and `env_candy` were the labels
that DID bake correctly: they are keyed off `GlobalOrderForBox(img.Candy)`,
which never went through the flat box lookup.

## The second bug the fix surfaced

With the collectors fixed, `ai.opencharly.port` appeared but `EXPOSE` still did
not — the exact divergence between the two that deriving both from one collected
set exists to prevent.

`pullNamespacedBox` stores an imported box under its fully-qualified key while
`ResolveBox` sets `ResolvedBox.Name` to the LEAF (which must stay bare — it is
what the registry image ref is built from: `ghcr.io/opencharly/charly-fedora`,
not `.../fedora.charly-fedora`). `generateContainerfile` read the port seam by
`img.Name`, missing the envelope entry for every imported box.

- **`deploykit/generate.go`** — `g.WriteExpose(&b, boxName)`, the QUALIFIED key
  every other seam in that function already uses. `ResolvedBox.Name` is left
  alone.

## The eleventh site, and the sweep key that missed it

`collectChainDataEntries` (`deploykit/render_prep.go`) had the same root cause and
sat two lines below one of the fixed calls. It emitted NO `ai.opencharly.data`
entries for an imported box.

It survived the first sweep because that sweep was keyed on the literal token
`BoxConfig(boxName)`, while this site spells the identical lookup
`BoxConfig(current)` — inside a **hand-rolled copy of the base-chain walk**:

```go
current := boxName
for {
    imgDef, ok := g.Config.BoxConfig(current)   // ← same miss, different spelling
    …
    current = imgDef.Base
}
```

The claim being swept was *"every by-name config lookup"*; the string grepped
was one spelling of it. **The correct sweep key is `.BoxConfig(`** — plus the
hand-rolled-walk shapes (`current = <x>.Base`) — with every hit argued, not a
single call form.

The fix is not merely a namespace-aware entry: the loop is replaced by the
shared `BoxCandyChain`, which is what every sibling chain collector already
uses. Carrying a private copy of that walk is exactly what let this site keep
the broken entry after all its siblings were fixed (R3), and the shared walk
also brings a cycle guard the hand-rolled loop lacked — a base cycle spun
forever. Dedupe semantics are unchanged: `BoxCandyChain` already de-duplicates
candy keys first-occurrence-wins across the chain, which is what the local
`seenDataCandies` set did.

Re-audit with the corrected key — seven `.BoxConfig(` sites across `deploykit/`
and `loaderkit/`, each argued:

| Site | Verdict |
|---|---|
| `render_prep.go` `collectChainDataEntries` (×2) | **was wrong** — fixed here |
| `init_depends.go:83` | correct — iterates `AllBoxNames()` inside the owning config |
| `loaderkit/resolve_project.go:91` | correct — same, bare names in their own config |
| `spec_box_resolve.go:70` | correct — `sub.BoxConfig(name)` where `sub` IS the namespace |
| `loaderkit/refs_collect.go:269` | correct — receives owner + leaf via `ResolveBoxRef`/`LeafName` |
| `loaderkit/refs_collect.go:308` | correct — iterates `AllBoxNames()` in the owning config |

A widened sweep for other hand-rolled base-chain walks (`current = <x>.Base`)
and for direct `.Namespaces[` access found no further site: the only remaining
`WalkBaseChain` caller is `BoxCandyChain` itself, and the `buildkit` namespace
descents are `ResolveBox`'s own, which are correct by design.

## Coverage

`deploykit/namespace_collect_test.go` — the whole family driven through a
namespace-qualified entry (`distro.app` on `distro.base`). All nine collector
tests FAIL on the pre-fix code with the reported symptoms (`BoxCandyChain =
[]`, `CollectDescriptions = empty`, `CollectBoxPorts = []`, `BoxDirectCandies:
box "distro.app" not found in charly.yml`, …). The discriminating guard is
`TestCollectDescriptions_ImportedBoxBakesNonEmptyLabel`: an imported box must
bake a non-empty set carrying both its candy-chain plans and its own box-level
plan.

`TestCollectChainDataEntries_ImportedBoxCollectsChainData` covers the eleventh
site. Its fixture puts the data candy on the BASE box, so the entry must be
reached through the base-chain walk rather than the leaf's own candies, and it
asserts the entry's CONTENT — volume, staging path, owning candy, dest — not
mere non-emptiness: a length check alone would pass on a wrongly-derived
staging path, and the staging path is precisely what a deploy reads back.

Measured live on `cachyos.jupyter-ml` (an imported box composing the
`notebook-templates` data candy): the `ai.opencharly.data` label is ABSENT
before the fix and after it reads

```
[{"volume":"workspace","staging":"/data/workspace/","candy":"github.com/opencharly/charly/candy/notebook-templates"}]
```
