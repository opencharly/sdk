# 0.2026308.351 — fix(loaderkit): fold deploy-level members of namespace-imported deploys

## Summary

This is the **consumer-side half** of the producer-first pair for opencharly/charly#1083. The contract half, opencharly/spec#291, has **merged** (`c9343efc2e344706d885053161d01129864b51a2`, tag `v0.2026308.344`), so this PR is now the sole remaining producer; charly then re-pins sdk + spec and runs the bed.

`FoldMembers` folded only the ROOT `uf.Deploy` map's deploy-level members. A deploy imported under a namespace (the umbrella project imports `charly/` as `charly`) kept its deploy-level members only inside the owner node's `Member` list, so the merged-root tree never contained the top-level addressable entry the Cutover C bare-name law promises. The re-entrant `charly deploy add <member>` then resolved no node, collected no substrate word, connected no provider, and defaulted the substrate to `pod` — refusing a substrate the project composes, after the member's VM already existed.

The fix recurses `uf.Namespaces` with the same path-scoped `NamespaceAncestors` guard the sibling whole-tree stamps use (`StampDeployDescents`). Because the merged-root projection addresses a folded member by its **bare** name, the name is global: a collision across scopes, or a member shadowing a root top-level deploy, is a hard load error; a diamond/multi-alias mount re-reaching the same node pointer stays idempotent.

**No file overlap with the open sdk PRs:** this diff touches only `loaderkit/deploy_load.go` and its test. #362 touches `deploykit/container_resolve.go`; #368 touches `workflowkit/lower.go` and `workflowkit/vocab_boundary_test.go`. Nothing here overlaps or depends on either.
