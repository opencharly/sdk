# 0.2026240.1439 — fix(deploykit): repair the build-time service render context; read #Box.init

## Summary

Two defects in the service-render path. Both are invisible on supervisord and both were waiting for
the first systemd consumer. This is the `sdk` leg of batch **B1 — service-render correctness**.

### 1. The build-time render context was seeded with dead fields, and missing the live ones

`GenerateInitFragments` hand-built a 13-field `ServiceRenderContext` from the entry. `RenderService`
then applies `spec.BuildServiceRenderContext`, which **overwrites every entry-derived field** — so
all of that was dead — **except `After`/`Before`, which it appends**. Pre-seeding those double-listed
every ordering directive:

```
After double-listed: got 2 entries [network.target network.target], want exactly 1
Before double-listed: got 2 entries [shutdown.target shutdown.target], want exactly 1
```

And the fields it *should* have carried were exactly the ones absent. Without `Home` the
home-expansion pass never runs, so a home-relative exec reaches a systemd unit verbatim:

```
Exec = "%(ENV_HOME)s/.local/bin/svc", want the home token expanded
unit dirs unset (system="" user=""): a scope: user unit has nowhere to land
```

supervisord expands `%(ENV_HOME)s` natively, which is why this stayed hidden on the only init path
that had consumers.

The context now carries **only** what `BuildServiceRenderContext` cannot derive — the candy name,
the home, and the unit dirs — extracted into `fragmentRenderContext` and mirroring
`compile_service_steps.go`'s deploy-time context (R3: one shape for both paths, not two).

### 2. `#Box.init` was declared and read by nothing

It is in the schema, generated into the Box model, and **all three** `ResolveInitSystem` call sites
passed a hardcoded `""` while the parameter was fully implemented with a correct fall-through. So
authoring `init: systemd` on a box silently did nothing. `AuthoredInit` is the reader that makes the
declaration load-bearing, and a guard test fails if a call site regresses to a hardcoded `""`.

## The one behaviour change, measured

This is **not** byte-identical output, and that is deliberate. Rendered fragment for the same candy,
pristine vs patched:

```diff
  [program:render-probe]
- command=%(ENV_HOME)s/.local/bin/render-probe
+ command=/home/user/.local/bin/render-probe
```

The expanded form is **already what the deploy path emits** for pods —
`compile_service_steps.go` sets `svcHome = img.Home` whenever the venue is not a machine venue. So
the build path was emitting a *different* form than the deploy path for the same candy; this makes
them agree. Functional equivalence is not argued, it is demonstrated below: the service starts and
stays up under the expanded path.
