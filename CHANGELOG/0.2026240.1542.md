# 0.2026240.1542 — fix(init): a wrapper-repo candy satisfies depends_candy

## Summary

Follow-up to **#176**: the report it added fires on boxes that are perfectly fine. Found by running
it against a real project immediately after merge.

A candy repo is named after its **repo**, not its **entity**. `ScanRemoteCandy` derives a root-level
candy's name from `path.Base(repoPath)`:

```go
if name == "" {
    // Root-level candy (the candy de-submodule cutover) …
    name = path.Base(repoPath)
}
```

So `@github.com/opencharly/layer-supervisord` scans as **`layer-supervisord`**, while the entity it
defines — and the one the init's `depends_candy: supervisord` names — is **`supervisord`**. The org
wraps entities in `<kind>-<entity>` repos (`layer-`, `pod-`, `plugin-`), so after the de-submodule
cutover this divergence is the *convention*, not an edge case.

`InjectInitDependsCandy` judged satisfaction with `candyKeyForName`, which matches the **scanned**
name. That misses every wrapper repo, so a box composing `layer-supervisord` **explicitly** was
reported as unable to install its init — and the report claims the image "will fail at start", which
for that box is flatly false:

```
box "plugin-resolution-box" resolves init "supervisord", which depends on the
"supervisord" candy, but no candy of that name is in this project's scanned set …
```

That box's bed runs green; supervisord is installed.

`orderSatisfiesInitDepends` now checks the **resolved order** for the bare name, the last path
segment, and that segment's `-<entity>` suffix.

### Coverage

`TestOrderSatisfiesInitDependsAcrossWrapperRepoNames` is table-driven over the shapes in the corpus —
the entity in-repo, a `layer-` wrapper, a `pod-` wrapper, a sub-path candy ref, an unrelated candy,
an empty order — plus the case that keeps the match honest:

```go
{"a near-miss substring must NOT match", []string{"supervisord-extras"}, false},
```

`TestUnsatisfiedInitDependsIgnoresBoxesThatComposeTheWrapperRepo` asserts both halves end to end: the
wrapper-repo box goes silent **and** the box that composes nothing is still reported. Asserting only
the first would pass trivially by disabling the report altogether.

## What this does *not* fix

The underlying naming divergence stands: a repo-root candy is still scanned under its repo name, so
auto-**injection** still cannot help a project that composes the init candy *nowhere* —
`candyKeyForName` finds nothing to inject. That case is exactly what the report exists for, and it
remains correct.

Making the scan record the manifest's entity name would fix injection too, but it changes a name
that sibling-dependency resolution (`QualifyRemoteSiblingDeps`) and display both consume, so it is
not a change to make as a drive-by inside a false-positive fix.
