# 0.2026289.800 — feat(candywalk): report per-ref resolution progress, so a corpus walk cannot look like a hang

## Summary

**The remote fix-point walk now reports one line per ref it resolves.** *Nothing about what the walk resolves changes — this is the missing half of its output.*

**The bug it addresses is diagnosability, and it cost a measured hour.** While characterising `opencharly/docs#162` I reproduced the docs deploy's regenerate step hanging, and the step's entire output was:

```
charly docs: walking 7 repo root(s): superproject, arch, cachyos, debian, fedora, omarchy, ubuntu
```

**…and then nothing, for tens of minutes.** *It took a `SIGQUIT` goroutine dump — not a log — to establish that the process was blocked in `spec/refs.GitResolveRef`, the `ls-remote` metadata step, and **not** in the download.* **The reason no `Downloading …` line ever appeared is that `downloadRepoFrom` prints it only after `GitResolveRef` returns.**

## The gap, precisely

**The two halves of `collectEntitiesWithRemote` report differently:**

| half | output |
|---|---|
| **resolve/fetch** (`spec/refs`) | *one line per repo — `Downloading %s:%s...`* |
| **walk the frontier** (`candywalk`) | ***nothing*** |

***So the phase that actually dominates the runtime — the walk resolves ~1 100 refs for the docs corpus, each a network round trip — is the silent one.***

## What changes

```go
seenRefs[key] = true

// Progress BEFORE the work, not after. The line names the ref about to be
// resolved, so a slow or stalled resolve is attributable to a specific repo
// rather than appearing as silence — and the caller can see the frontier
// shrinking. … without a matching line here, a corpus walk over a thousand
// refs reports nothing for its entire duration, which is what made a 20-35
// minute walk read as a hang (opencharly/docs#162).
fmt.Fprintf(os.Stderr, "charly: resolving %s (%d resolved, %d queued)\n", key, resolved, len(queue))
resolved++
```

**Emitted BEFORE the resolve, which is the property that matters.** *The last line in the log names the ref currently being worked on, so a stall is attributable to a specific repo; a line emitted after would name only the refs that already succeeded.*

***One test fails without the change; the other does not, and the next section says which and why — the first draft of this body claimed "both", which was wrong.***

**These two tests do different jobs, and only one of them can fail without the change. Stating that precisely, because the first draft of this body did not:**

- **`TestCollectEntitiesRemote_ReportsResolutionProgress` — the regression test, and it is mutation-verified.** *Asserts exactly one line, that it **names the ref being resolved**, and that it carries the resolved count and the frontier size.* **Reverting the `Fprintf` makes it fail with `got 0 progress line(s) on stderr, want exactly 1`** — *that is the R7 proof, and it is the only one of the two that provides it.*
- **`TestCollectEntitiesRemote_NoProgressWithoutRemoteMode` — a GUARD, and NOT mutation-verified.** *It asserts zero progress lines on the local-only walk (`resolve == nil`).* **With the `Fprintf` reverted there are also zero lines, so this test passes both before and after the change — it cannot fail without it, by construction.** ***Its job is the other direction: it stops the line from firing unconditionally and polluting every local walk, which is a real regression its absence would not catch but its presence would.*** *It is coverage of a constraint, not proof of the change, and it is labelled that way here.*

**And the double is honest rather than convenient:** *it returns an error on a mismatched ref instead of calling `t.Fatalf` inside the callback — which is also what stopped `unparam` flagging it twice (an unused parameter, then an always-nil error). Both findings were fixed properly, not suppressed.*

## Scope note — what this deliberately does NOT do

**This is the diagnosability half. The baseline cost — ~1 100 refs at 1–2 seconds each, resolved serially — is characterised in `opencharly/spec#258` and is NOT fixed here.**

*A bounded worker pool over the frontier is the obvious shape, and the per-path cache lock in `spec/refs` already makes concurrent resolution safe for the cache. It is filed rather than folded in because it (a) changes a shared SDK seam's concurrency contract that `plugin-docs` and every corpus walker depend on, (b) changes error semantics — today the first failed resolve aborts deterministically, under a pool "which error wins" and what happens to in-flight work become contract questions, and (c) requires load-proof under CONC rather than unit coverage.* **That is a separate change with its own gate.**
