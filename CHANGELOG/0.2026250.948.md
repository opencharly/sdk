# 0.2026250.948 — fix(packagekit): render /etc/charly/charly.yml as a bare minimal project (validates; a candy node rejected)

## Summary

Two coupled fixes that the per-distro install-test wave surfaced (both BLOCK the shipped /etc/charly/charly.yml from validating):

1. **packagekit renderer fix** — renderConfig now renders /etc/charly/charly.yml as a BARE minimal project (version only). The prior candy-node shape FAILED `charly box validate` live (released charly) with two rejections: the candy had no install content ("must have at least one install file ... a candy: field, ...") and the plan was run-only ("plan: must contain at least one check: step"). A version-stamped project is exactly what validates and what the systemd MCP server needs to resolve locally (the mcp command word comes from the baked /usr/lib/charly/plugins/plugin-mcp .providers manifest, not the project). New `TestRenderConfig_ValidatesWithCharly` runs `charly box validate` on the rendered output with a RELEASED charly (CHARLY_TEST_BIN; skips on a dev/worktree charly).

2. **loaderkit guard alignment (from the main-merge conflict resolution)** — the merged main added tests expecting the config-stack merge to surface the parse-level "duplicate top-level entity name" contract message for a within-layer duplicate top-level key. The yaml.Node raw round-trip preserves duplicates (the merge would silently collapse last-wins), so mergeConfigStackRaw now enforces the within-layer top-level-name uniqueness with that exact contract message — before any seam. The two tests (TestConfigStack_RejectsDuplicateKeysWithinLayer, TestConfigStack_CrossLayerDuplicateKeyStillMerges) that my earlier conflict resolution dropped are RESTORED. This belongs in this PR: it is the config-stack merge behavior the merge-conflict resolution changed, and the charly loader test (TestCrossKindNameReuse_LoaderRejectsWithinDocument) pins it.
