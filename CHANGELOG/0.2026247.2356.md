# 0.2026247.2356 — feat(loaderkit): cache the materialized merged deploy tree across CLI-subcommand children

## Summary

**The stall root (SIGQUIT goroutine dumps, 2026-09-05).** Every `charly fleet add` / `charly check live` / rebuild phase spawns a CLI subcommand child that **re-materializes the full merged deploy tree through CUE** — `ResolveMergedDeployTreeViaExecutor` → `MaterializeLoadedProject` → the CUE disjunction unify over the project's pinned-repo tree (goroutine 1 [runnable] inside `cuelang.org/go/cue/.../doDisjunct/crossProduct/processDisjunctions`). Under 32-lane oversubscription each lane's child burns CPU in the unify; the unify exceeds its budget and the parent's `os/exec.Cmd.Run` (host_build_cli.go via `executorReverseServer.HostBuild`) waits forever.

**The fix.** A **host-side cache of the materialized tree** (`spec.UnifiedFile` — the Materialize output), so the wave's later children on the same project state reuse the first child's materialization instead of re-running the unify:

- **Hook (one change point, all placements):** the cache wraps the `MaterializeLoadedProject` seam inside `LoadSeamsFromExecutor` (load_executor.go) — the ONE seam constructor both loader placements drive `loaderkit.LoadUnified` through: the compiled-in host placement (`hostLoaderExecutor`, charly's own load — the CLI subcommand children's hot path) AND every out-of-process plugin (`executorLoaderExecutor` over `Executor.HostBuild`). A shared on-disk cache is what lets the wave's separate OS processes reuse ONE another's work.
- **Cache key (the project config state + the resolved refs' hashes, content-addressed):** SHA-256 over (1) the deterministic JSON of the `spec.LoadedProject` walk envelope — the FULL materialize input: root config, directive `import:`/`repo:` pins, flat imports, discovered manifests and every mounted namespace, i.e. the CONTENT of every ref the walk resolved (fetched pinned repos are walked into the envelope) — and (2) the compiled schema CalVer (`kit.LatestSchemaVersion`). **Invalidation: any config/ref change = a new key** — a config edit, a ref re-pin, a branch advance, or a content change all alter the envelope → new key. Hashing the envelope is strictly stronger than a bare list of resolved commit hashes (it is a content hash of the resolved refs); the schema-CalVer half makes a binary schema upgrade re-key too.
- **TTL: 1 hour** (`materializeCacheTTL`, package var — test-adjustable like spec/lock's `lockTimeout`; matching the spec/refs submodule-verdict precedent). Bounds the only materialize input the envelope cannot see (a binary's provider-set/loader change WITHOUT a schema bump); a stale entry is a miss (re-materialize), never served.
- **Location + concurrency (the spec/refs git-cache patterns):** `~/.cache/charly/materialized/<sha256>.json` (`CHARLY_MATERIALIZED_CACHE` overrides the root, mirroring `CHARLY_REPO_CACHE`), entry = `{resolved RFC3339, tree = MarshalMaterialized bytes}` (PluginKinds preserved — never a plain json.Marshal). Reads are **lock-free** (writer publishes atomically: tmp + rename — readers see complete old or complete new, never torn); the **miss path** takes a per-key blocking advisory flock (`spec/lock.AcquireFileLock`, the downloadRepoFrom per-cache-path pattern) with a double-check under the lock, so the wave's first child materializes once and concurrent first-missers reuse its entry.
- **Failure contract:** the cache NEVER fails a load. Key error, read error, corrupt entry, or lock-contention timeout → direct `materialize(` exactly as before.
