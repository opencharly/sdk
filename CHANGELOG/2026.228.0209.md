# 2026.228.0209 — the bootstrap and the cloud-init sshd start work on a busybox base

Four fixes of one family: the image bootstrap and the VM cloud-init render both
assumed a glibc/shadow-utils userland with bash. Every assumption held on
Fedora/Debian/Arch and failed on Alpine, and each was invisible until an Alpine
box was actually built.

## 1. The go-task install assumed `curl`

`deploykit.WriteBootstrap` emitted `curl -fsSL … | tar -xzf -`. The Alpine base
ships busybox `wget` and no curl, so the very first bootstrap RUN died:

```
/bin/sh: curl: not found
tar: invalid magic
```

The URL now lives in a shell var and both downloaders target it —
`(curl -fsSL "$TASK_URL" || wget -qO- "$TASK_URL")`. A base with curl is
unaffected; a base with only wget now works.

## 2. User creation assumed `groupadd` / `useradd`

The next RUN emitted the shadow-utils pair unconditionally:

```
/bin/sh: groupadd: not found
Error: building at STEP "RUN if ! getent passwd 1000 …": exit status 127
```

Alpine provides busybox `adduser` / `addgroup` instead. Measured on
`docker.io/library/alpine:3.24`: `groupadd` and `useradd` absent, `adduser`,
`addgroup` and `getent` present — so the idempotency guard (`getent passwd`)
needed no change, only the creation commands.

The emitted shell now probes for the shadow-utils tool rather than branching on
a distro name, so any base with either userland works:

```sh
if command -v useradd >/dev/null 2>&1; then
  (getent group … || groupadd …) && useradd -m …
else
  (getent group … || addgroup …) && adduser -D -h … 
fi
```

## 3. The login shell assumed `/bin/bash`

`useradd -s /bin/bash` would have created a user with a broken login shell on
Alpine, which ships no bash — a defect a naive port of fix 2 would have shipped
silently. The shell is probed the same way:
`LOGIN_SHELL=/bin/sh; [ -x /bin/bash ] && LOGIN_SHELL=/bin/bash`.

## 4. cloud-init started sshd with systemd on an OpenRC guest

`vmshared.composeRunCmd` emitted `systemctl enable --now sshd` for every guest.
Alpine cloud images run OpenRC, so sshd never started and the VM booted without
a reachable SSH — the symptom being a guest that comes up and is simply never
connectable. `effectiveDistro` now infers `alpine` from `base_user: alpine` on a
`cloud_image` source, and that branch emits
`rc-update add sshd default && rc-service sshd start`.

## Why none of this was caught

No box in the fleet used a busybox base. Every bootstrap and every cloud-init
guest ran a glibc userland where all four assumptions are true, so they were
indistinguishable from correct code. They surfaced one at a time as an Alpine
check bed was brought up — each fix advancing the build to the next failure.

A fifth of the same family lives in `spec/exec` (the nested-jump interpreter
hardcoded `bash`) and is fixed separately in that repo, since it is a different
module.

## Coverage

`TestWriteBootstrap_UserCreationSupportsBusyboxBases` asserts both userland legs
and that the login shell is probed rather than hardcoded;
`TestWriteBootstrap_AdoptedUserEmitsNoUseradd` guards the adopt branch.
`TestEffectiveDistro`, `TestComposeRunCmd_AlpineOpenRC` and
`TestRenderCloudInit_Alpine_OpenRC` cover the OpenRC path. The byte-golden
render test (`render_parity_golden.txt`) pins the emitted bootstrap text.

Verified non-vacuous: reverting the user-creation block to the shadow-utils-only
form fails `TestWriteBootstrap_UserCreationSupportsBusyboxBases` on both the
busybox leg and the hardcoded-`/bin/bash` assertion.
