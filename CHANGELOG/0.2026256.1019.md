# 0.2026256.1019 — feat(charlylib): generic multi-call plugin host + data-driven generator

## Summary

Add the generic, plugin-**agnostic** shared host for out-of-process charly plugins, plus the
data-driven generator that builds one. **Scope of this PR (SDK repo only):** the library +
generator. It does **not** install anything, ship a package, or touch charly core/the loader —
packaging (`charly-lib` package + `plugin-<word>` symlinks) and the baked-path integration are
the next batch, tracked below.

- **`charlylib/`** — `Run(Registry)` dispatches to a plugin by `filepath.Base(os.Args[0])`
  (`plugin-<word>`) and delegates to `transport.Main` (the same serve-vs-CLI pivot every
  per-plugin `cmd/serve` uses). It names **no** plugin and imports **no** plugin module —
  `Plugin{Provider, Meta, CLI}` + `Registry` are the whole surface. Depends on `spec/proto` +
  `spec/transport` only. `Run` fails loudly (exit 2) for an unknown name or a nil registry field.
- **`cmd/charly-lib-gen/`** — reads a `<name>@<tag>` pins list (the format
  `charly/scripts/host-command-plugins.txt` already uses), maps each superproject tag to its Go
  module version (`v2026.239.1615` → `v0.2026239.1615`) and module path
  (`github.com/opencharly/<name>/candy/<name>`), and emits a deterministic `go.mod` + `main.go`
  registering each plugin into `charlylib.Run`. Adding a plugin is a **data** change.

**Why.** Every per-plugin binary statically re-links the whole shared SDK/spec closure:
`plugin-clean` and `plugin-doctor` share **99.7% of symbols** and each is ~21 MB stripped. Go has
no runtime shared library for this (`-buildmode=shared` needs cgo + a writable `GOROOT` and fails
across module roots; `-buildmode=plugin` needs cgo + in-process loading), so the only way to store
the closure once is **one image**. **Loader contract unchanged is a property of the design** (the
host is exec'd exactly like a per-plugin binary); realizing it in a package is the next batch.

**Measured (live):** one generated 10-plugin host = **27,742,368 bytes** vs **213.9 MB** for the
ten separate stripped binaries — **87%**.

every word from a disposable Arch repo deploy) is the packaging batch. **Operator sign-off:** the
operator approved this phased plan explicitly — SDK host/generator → `charly-lib` repo + release →
packaging cutover — with the packaging R10 bed in the packaging batch; ground rule 3's bootstrap
path applies to the portion that provably cannot exist before packaging.

### Finding routing (R2 → named batch, concrete set)

The RDD surfaced that a shared host forces **one SDK/spec version across all pinned plugins**, and
two current `host-command-plugins.txt` pins are stale against a single compatible SDK/spec (e.g.
`plugin-vm@v2026.240.2034` imports the removed `spec/fleet`). This is routed to its named batch —
**opencharly/charly#605** — with the concrete verified-compatible pin set (sdk v0.2026254.523 +
the plugin tags listed there), not deferred to an unnamed phase.
