# 0.2026328.1130 — refactor(deploykit,kit): every per-host config writer reads inside the shared lock

## Summary

Closes opencharly/sdk#631. The per-host `charly.yml` (`~/.config/charly/charly.yml`) has four
section writers that run in different charly processes — the deploy overlay, the install ledger,
the host snapshot and the git-ref cache. opencharly/spec#437 published `spec/perhost` as that
file's ONE reader/writer (`Lock`, `Apply`, `Update`, `Read`, `Get`, `Set`); this routes the three
SDK writers through it and fixes the lost update the ledger had kept.

**The ledger read outside the lock (a real data loss, found by this migration).**
`WriteDeployRecord`, `WriteCandyRecord`, `DeleteDeployRecord`, `DeleteCandyRecord` and
`AddCandyDeployment`/`RemoveCandyDeployment` read the ledger, mutated that snapshot, and handed it
to `writeLedger`, which locked and replaced the whole `ledger:` section with the snapshot it had
been given. Two concurrent ledger writes therefore each dropped the other's record — measured
against the pre-change tree with the new test: **21 of 24 concurrently-added candy records lost,
on 5 of 5 runs**. They now call ONE `mutateLedger`, which decodes the `ledger:` section from the
document `spec/perhost`'s lock just read and runs the mutation on THOSE maps: read inside the
lock, own key only, atomic replace.

**The deploy writer's second copy.** `SaveDeployConfig` kept its own
read/marshal/tempfile/chmod/rename. It is called INSIDE the deploy cycle
(`deploykit.MutateDeployConfig`), which already holds the lock and must not be re-entered —
`flock` is per-open-file-description, so a second acquire in one process waits for the first and
fails at `perhost.LockWait`. It now writes through `perhost.Apply` (the lock-held half of
`perhost.Update`), and the cycle takes its lock from `perhost.Lock`, so `deployConfigLockWait` (a
10 s copy of `perhost.LockWait`) and its second lock path are gone. The fail-safe re-read moves
INSIDE the locked mutation, so the check and the write are one critical section.

**The reader.** `readLedger`, `readLedgerStrict` and every writer decode through one
`ledgerFromRoot` over `perhost.Read`; the hand-rolled `ledgerDoc` decode of the same section is
deleted. `ledgerFromRoot` REFUSES a wrong-shape section (`ledger:` / `ledger.deploys:` /
`ledger.candies:` present but not a mapping) by name, so the strict reader keeps the strictness it
exists for: the strict path propagates the refusal, the best-effort path degrades to empty, and a
writer refuses to rewrite a malformed ledger.

The remaining per-host writer is `kit.writeSystemInfo` (`system:`), migrated in the same commit.

## Change classification

- **Class:** library refactor (three writers, three new test files, one dependency bump).
- **Impact:** no exported signature changes. `SaveDeployConfig`'s contract is now stated: it is
  the lock-held writer its cycle calls (`deploykit.MutateDeployConfig`, `AcquireDeployConfigLock`),
  writing through `perhost.Apply`. Every runtime caller is already inside that cycle. One
  behaviour change, deliberate and named: a malformed `ledger:` section is now REFUSED by a writer
  and by the strict reader instead of being read as empty.
- **Error text:** the parse path still reports `parse ledger <path>: …`; an *unreadable* file now
  reports `parse ledger <path>: per-host config <path>: …` where the old code said `read ledger
  <path>: …`.
- **Rollback:** revert the two commits and the spec pin; the writers return to their own copies.
