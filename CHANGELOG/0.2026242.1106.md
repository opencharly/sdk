# 0.2026242.1106 — fix(kit): bound engine commands with a timeout — fail fast on a saturated podman daemon

## Summary
Two unbounded-wait root causes in the sdk were traced from the recurring fleet-del/remove stall (VM beds' cleanup hanging in futex_wait):

1. **kit/images.go — unbounded engine command.** `RemoveImagesByReference` ran `podman images` / `podman rmi` with NO timeout, so under heavy concurrent load a stalled podman daemon hung the calling bed's cleanup step forever. Fix: bound every engine command with a 2-minute timeout (`engineCommandTimeout`, a package var for testability), killing the whole process group on expiry (a shell wrapper's children must not survive and hold the output pipe open). A timed-out list/rmi is a skipped best-effort cleanup, never a hang.

2. **agentkit/store.go — unbounded store-lock wait.** `withLock` ran `syscall.Flock(LOCK_EX)` with no timeout, so a store lock held by a peer (parallel bed runs) hung the caller forever. Fix: `flockBounded` acquires the lock non-blocking with a 50ms poll, failing fast after `storeLockTimeout` (2 min, a package var for testability).
