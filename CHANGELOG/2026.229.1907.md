## A hardcoded bash, and four ways to ship an image without its packages

Two defects in the Containerfile emitter, found while composing the first candy onto a
busybox base. The second is the more serious one: the emitter had four separate paths on
which a candy's resolved packages were dropped **without a word**, and the resulting
Containerfile looked correct.

### 1. Every emitted build step hardcoded bash

`deploykit/tasks_emit.go` had two emit sites, and both named `bash` as the interpreter:
the `-c` form wrote `… bash -c '<cmd>'`, the heredoc form wrote `bash <<'OVCMD'`. Alpine
ships busybox `ash` and no `/bin/bash`, so **every** candy shell step — the `cmd` verb and
the `download` verb alike — was unbuildable on any busybox base, regardless of what the
step did.

Both sites now route through one of two shared helpers (R3), which prefer `/bin/bash`
when it exists and fall back to POSIX `sh`:

```go
func BuildStepShellDashC() string {
    return `sh -c 'SH=/bin/sh; [ -x /bin/bash ] && SH=/bin/bash; exec "$SH" -c "$1"' sh`
}
func BuildStepShellHeredoc() string {
    return `sh -c 'SH=/bin/sh; [ -x /bin/bash ] && SH=/bin/bash; exec "$SH"' sh`
}
```

The authored command reaches the chosen shell unchanged — it is passed as `$1` and
re-exec'd, so author `$(cmd)` and `${VAR}` still expand in the shell that runs them; the
heredoc form relies on `exec` preserving stdin. This mirrors the probe `WriteBootstrap`'s
create branch already emitted for the login shell, so the two now agree.

A doc comment claiming "Shell is bash via a single-quoted heredoc" was corrected in the
same change rather than left to describe the old behaviour.

### 2. Four silent drops in the package-install emit

`deploykit/candy_steps.go` resolved a candy's packages through the shared cascade and
then discarded them on any of four conditions, three in one nested `if` and one a few
lines below:

| condition | old behaviour |
|---|---|
| `img.DistroDef == nil` | guard failed, nothing emitted, no error |
| `img.DistroDef.Format[img.Pkg] == nil` | inner guard failed, nothing emitted, no error |
| `RenderTemplate` returned an error | `if err == nil { … }` with no `else` — error discarded |
| `EmitTasks` returned an error | written into the Containerfile as `# emitTasks error: …` and execution continued |

**The third is the one that actually shipped**, and it is worth being precise about why
it was expensive. A format's `install_template` calling a function that is not in
`buildkit.TemplateFuncs` is a plain authoring mistake. The emitter turned that mistake
into a Containerfile that built successfully, exited 0, and produced an image with none
of the candy's packages in it. Nothing in the artifact indicated a step was missing. The
failure surfaced later, in an unrelated place, as a binary that was not on the image.

All four now return an error naming the candy, the format, and the box. A candy that
resolves **no** packages for this box still passes through untouched — that is the common
per-distro case (a `distro:` map with no section for this box's distro), and it is not an
error.

The precedent was already in this same function: the localpkg render's identical
silent-mask (an error emitted as a Containerfile *comment*) had been converted to a hard
error earlier, for the same reason and with the same reasoning in its comment. These four
bring the rest of the function into line with it.

### Coverage

`deploykit/candy_steps_loud_failure_test.go` pins all four. Reverting the package block
to its pre-fix form fails exactly three of them and leaves the fourth passing:

```
--- FAIL: TestWriteCandySteps_UnrenderableInstallTemplateIsLoud
--- FAIL: TestWriteCandySteps_MissingFormatDefIsLoud
--- FAIL: TestWriteCandySteps_NoDistroDefIsLoud
```

The fourth, `TestWriteCandySteps_NoPackagesStillRenders`, is the **presence control** and
passes both before and after — deliberately. Without it, an emitter that errored on every
path would satisfy the other three just as well, and the suite could not tell a working
fix from a broken one.

The emitted-artifact check is the other half: with the fix, generating a box whose
`install_template` calls an undefined function fails with

```
candy sudo-nopasswd: rendering the apk install template for box alpine-repo-box failed:
  parsing template "apk-install": template: apk-install:4: function "base" not defined
```

and without it, the same tree generates 0 install lines and exits 0. Fifteen boxes across
the superproject generate clean under the new hard errors, so the added strictness has no
false positives on any existing box.

### 3. A kill that named no deadline

`sdk/kit/planrun.go` already detected that the per-attempt never-hang deadline had fired —
it set `DeadlineExceeded` on the result — and then reported the exec layer's message
unchanged: `process terminated by signal (signal: killed)`. That names the *mechanism* of
death and not its cause, so a step killed by the bound is indistinguishable from a step that
crashed, and the reader goes hunting a bug in their own command. **The bound was known at
the moment the deadline fired and thrown away.**

Measured cost: installing charly from a published distro repo pulls ~190 packages, so
`dnf install` crossed the 90s floor (`runnerProbeNeverHangFallback`) while `pacman -S` fitted
under it. Two beds differing only in package manager, one green and one "killed", invites a
distro-specific theory — repo layout, signing, cloud image — when the variable is elapsed
time against a shared floor. A peer confirmed the same trap independently: they had put
`timeout: 600s` on an image-stream step by guessing at a duration, not knowing a floor
existed, and without that guess would have hunted a transfer bug that did not exist, *in
their own new code*.

`AnnotateNeverHangKill` (extracted into `sdk/kit/runner.go` so it is testable rather than
inline) now names the bound, states that the step ran longer rather than crashed, and points
at `timeout:` — which `ProbeNeverHang` honours over the floor, making it the mechanism's own
parameter rather than a workaround.

Coverage: `sdk/kit/never_hang_message_test.go` asserts the message carries the bound, the
remedy, and an explicit contradiction of the crash reading; the second test is the presence
control — it pins that the original text survives verbatim and that an authored `timeout:`
raises the bound that gets *reported*, so an implementation that appended the text
unconditionally, or that always printed the floor, fails.

## A Debian-family cloud image could be left with SSH masked and never restarted

`composeBootCmd` masks `ssh.socket` in `bootcmd` — deliberately, so a socket-activated sshd
cannot accept a connection before cloud-init has finished configuring the guest. `composeRunCmd`
then unmasks it and starts the service. The start named ONE unit:

```go
sshUnit := sshUnitForDistro(spec.Source.Distro)   // "ssh" on debian/ubuntu, else "sshd"
runcmd = append(runcmd, "systemctl unmask ssh.socket || true",
    fmt.Sprintf("systemctl enable --now %s", sshUnit))
```

`sshUnitForDistro` reads `source.distro`, which is an **optional** field, and `effectiveDistro`
infers `arch`/`alpine` from `base_user` but **never** `debian`/`ubuntu`. So a Debian-family
`cloud_image` that omits `distro:` — the easy thing to do, since `base_user: ubuntu` already
says which distro it is — rendered `systemctl enable --now sshd`, a unit that does not exist
there. Paired with the bootcmd mask, that leaves a socket-activated sshd **masked and never
started**, and the guest boots permanently unreachable.

### Why it cost hours

The symptom points nowhere near cloud-init. The domain reports `running`, the libvirt
portForward is correct (`passt --tcp-ports 127.0.0.1/33345:22`), TCP is ACCEPTED, and then the
guest resets — `kex_exchange_identification: read: Connection reset by peer`. The guest itself
looks healthy from the console: cloud-init completes every stage from `DataSourceNoCloud`,
reaches `graphical.target`, and shows a login prompt.

**This file's own header already described that signature** — for an unrelated cause (pacman
reinstalling openssh under a live sshd). Two different defects presenting identically is
exactly what makes the signature untrustworthy as a diagnosis on its own. The line that
actually named the cause was in the boot console:

```
cloud-init[650]: Created symlink /etc/systemd/system/ssh.socket → /dev/null.
[FAILED] Failed to listen on ssh.socket.
```

and the confirmation was the rendered seed artifact, not the code: `packages: [openssh, …]`
(the Arch name, which apt cannot locate) and `systemctl enable --now sshd`.

### The fix

The start now falls back to the other unit name:
`systemctl enable --now <unit> || systemctl enable --now <other>`. There are exactly two names
in play across every distro charly renders cloud-init for, the distro-derived one still goes
first (so the common case runs one command), and a missing or wrong `distro:` can no longer
brick SSH.

This does not make `distro:` optional in general — `composePackages` still needs it to choose
`openssh-server` over `openssh`, and a wrong package name hard-fails apt's install stage. The
file's header already records the proper long-term fix as schema-level (require or default
`distro:` for every `cloud_image` source); that remains the right shape and is not attempted
here. What changed is that forgetting it now costs a redundant `systemctl` call instead of an
unreachable VM.

Proven live: with `distro: ubuntu` set and the fallback in place, `check-ubuntu-repo` goes from
never reaching `check-live` to **PASS (steps=9)**, including the fresh `charly update` and
`check-live-rebuild` legs, with all 7 in-container checks green in both.

## The renderer stops guessing the distro, and stops hardcoding two of its traits

Three pieces of guesswork are deleted outright, not narrowed.

### 1. `effectiveDistro` — DELETED

It inferred the distro from `base_user`: `arch` → arch, `alpine` → alpine, everything else →
`""`, which `composePackages` and `composeRunCmd` then treated as Arch/Fedora. So a
Debian-family cloud image that did not spell out `distro:` was rendered with the Arch package
name `openssh` and `systemctl enable --now sshd` — a unit Debian and Ubuntu do not have. With
`composeBootCmd`'s deliberate `mask ssh.socket`, that left a socket-activated sshd masked and
never started, and the guest booted permanently unreachable.

An account name says nothing about an operating system. `Source.Distro` is now read directly;
the field is validated by the vm kind's OpValidate capability, so an omission is an authoring
error rather than a silent default.

### 2. The `ssh || sshd` fallback — DELETED

A previous entry added `systemctl enable --now <unit> || systemctl enable --now <other>` so a
missing `distro:` "could not brick SSH". That was a stopgap: it made the wrong input survive
instead of rejecting it, and it hid the very omission that needed reporting. With the field
required and closed, the unit name is known exactly and exactly one command is emitted.

### 3. Two hardcoded distro traits — now generated data

`sshUnitForDistro` was a Go `switch` returning `ssh` for debian/ubuntu and `sshd` for
everything else. The Alpine OpenRC path was `if spec.Source.Distro == "alpine"`. Both now read
the tables generated from `schema/distro_vocab.cue`'s `#Distros` (`spec.DistroSSHUnits`,
`spec.DistroInits` — see the spec entry). A branch on a distro NAME encodes a trait as a fact
about one distro: not enumerable, not validatable, silently treating every unlisted distro as
systemd, and needing to be found and edited again for the next OpenRC distro.

`distroInit()` is the only thing that decides how a service is enabled and started in a guest.

### The test named "ByteIdenticalToPreFix" is gone

Replaced by `TestRenderCloudInit_NonPacmanUsesPackagesKey`, which asserts the containment that
actually matters: non-pacman distros deliver packages via the `packages:` key and never reach
the pacman runcmd branch.

The old name pinned the rendered output against a historical baseline rather than a behaviour.
"pre-fix" named a moment nobody can look up; the assertion had to be re-baselined by every
legitimate change; and it had already accumulated a comment explaining why its own name was no
longer true. **A test whose name has to be explained away is pinning an accident.**

### Coverage

`TestRenderCloudInit_Alpine_OpenRC` survives the deletion of the inference tests and now
declares `distro: alpine` explicitly — it covers the OpenRC branch, which is not inference
coverage. `TestComposeRunCmd_AlpineOpenRC`'s second case varies `base_user` while pinning
`distro: alpine`, proving `base_user` no longer participates in the decision at all.

### Legacy removal: the frozen init table, and two fallbacks that hid failures

**`wellKnownInitDefs` is deleted.** It was described in its own comment as "the legacy fallback
for pre-init_def-label images … frozen at the two init systems that predate the label; do NOT
add new ones". Three problems, any one sufficient:

- It was **triplicated verbatim** — `sdk/kit/entrypoint.go`, `candy/plugin-pod`, and
  `candy/plugin-deploy-pod`, the last one commented "mirrors charly-core service.go's table
  VERBATIM" (R3).
- It was **frozen at supervisord + systemd**, so with `openrc:` now a first-class init system
  the table could only ever answer for two of three — silently, for the third.
- It existed for images built before the `ai.opencharly.init_def` label. Every image charly
  builds today carries that label.

`ResolveEntrypointFromMeta` / `ResolveInitDefFromMeta` now read the label as their only source;
an image without it errors, naming the rebuild, rather than resolving a guessed management CLI
that would drive the wrong supervisor. `candy/plugin-deploy-pod`'s local
`resolveEntrypointFromMeta` — a fourth copy, of the *function* this time — is deleted with it and
its callers routed to the single `kit` implementation.

**`LibvirtSessionSocketWithProbes` no longer returns a path it did not find.** With neither the
modular (`virtqemud-sock`) nor the monolithic (`libvirt-sock`) socket present it returned the
monolithic path anyway, as though found. That made `status_vm`'s own `if sock == ""` guard **dead
code** and turned "libvirt is not running" into a stat failure on a socket the host may never
have used. It returns `""`; every caller already stats the result. The two-socket probe itself
stays — that is third-party version compatibility, and `probed` still carries both for the
diagnostic trail.

**`SmbiosCredForRootSSH` is deleted** — a compatibility wrapper "preserved for the existing call
sites in vm.go", which has zero production callers; those call sites were removed in an earlier
K-wave and only its own test still referenced it.

### Triaged and deliberately kept

Two `legacy`-labelled branches are NOT charly's superseded paths and stay, with their comments
corrected so the next sweep does not mis-trigger: `status_pod`'s quadlet-description
fall-through handles units charly did not write, and `status_flat`'s `lookupDeploy` alternates
match bed-rolled container names. Neither has a superseded charly format behind it; deleting
them would remove capability, not legacy.

## The fifth silent drop

The three sections above convert four silent drops in the emitter into hard errors. A validator
pointed out a fifth of the same class that this change had introduced and not counted:
`sshUnitForDistro` and `distroInit` are bare lookups into the generated tables, so an id the
vocabulary does not carry yields `""` — which renders `systemctl enable --now ` with no unit name, or
takes the systemd arm on an OpenRC guest. Either way the guest boots, is unreachable, and nothing in
the output says why.

`validateDistroVocabulary` now rejects such an id at `RenderCloudInit`, the entry point that can
carry an error — one check rather than a result type threaded through `composeRunCmd`'s `[]any`
signature. An empty distro is deliberately NOT this guard's business: presence is enforced at author
time by the vm kind's `OpValidate`, and turning absence into a render error here would break every
spec written before that gate existed.

This is defence in depth, not the primary gate. It catches a spec that reached the renderer without
passing `OpValidate`, which is exactly the argument the other four conversions rest on.

## Live gate

Unit tests assert the SHAPE of the emitted prefix (`HasPrefix("sh -c")`, `Contains('exec "$SH"')`).
Nothing in them executes it, and that prefix now wraps every build step of every image — so a quoting
or stdin defect would satisfy every assertion and break the ecosystem. Both emitted forms were built
live with podman 6.0.2:

```
# busybox base (alpine:3.20, no /bin/bash) — heredoc form
shell=/bin/sh        bash=absent
single / double / home=/root / uid=0 / a,b     → quoting + embedded newline intact     exit 0

# same base — the pre-fix `bash -c` form, as the counterfactual
/bin/sh: bash: not found                                                               exit 127

# bash-carrying base (debian:13-slim) — heredoc form
shell=/bin/bash      is_bash=yes (5.2.37(1)-release)                                   exit 0

# busybox base — the `-c` ($1-passing) form
shell=/bin/sh   sq='x' dq="y"   arith=42   nl:a,b   home=/root                         exit 0
```

Both branches ran: the busybox fallback AND the bash preference. The counterfactual is what makes it
evidence rather than a demo — the pre-fix form fails on the same base with exit 127.

**Tier: `analysed on a live system`.** The changed path ran live with the output above; no disposable
bed ran, so `fully tested and validated` is not available. An earlier revision leaned on the
circularity that lowered `spec#35`'s tier — every project-loading command failing on a poisoned pin —
and that reason had already expired: the box repos landed, the pins bumped, and `charly box validate`
