# 0.2026239.1643 — fix(deploykit): remoteBuildConfigCacheRoot must handle root-level standalone candies

## Summary

The candy de-submodule cutover moved every candy to a **root-level manifest in its own standalone repo** (ref == repoPath, `SubPathPrefix` empty). `remoteBuildConfigCacheRoot` (deploykit/header_copy_remote.go) was written for the OLD subpath shape (`candy/<name>` inside the charly repo): it strips `SubPathPrefix + Name` off the candy's SourceDir to reach the shared `repo@version` cache root.

For a root-level standalone candy the SourceDir **IS** the cache root itself (e.g. `.../layer-supervisord@v2026.239.1300`), so the `CutSuffix(SourceDir, subpath/name)` never matches (the dir ends with `@v2026.239.1300`, not the bare name) → the function returns `""` → `materializeBuildConfigAsset` leaves the header COPY as authored → **every box composing a service candy fails at `COPY templates/supervisord.header.conf`: no such file or directory**.

This was surfaced by distro-arch#25's box rebuilds (the merged distro sweeps were static ref sweeps — R8 N/A, no image builds — so the seam was never exercised). The buildah `--jobs` stage-parallelism panic on the 62-stage Containerfile was a separate, masking symptom; `--podman-jobs 1` surfaced the real header error.

**Fix:** when `SubPathPrefix` is empty (root-level candy), return `SourceDir` directly — it is the cache root. The subpath branch (old `candy/<name>` shape) is unchanged.
