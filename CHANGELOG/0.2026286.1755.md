# 0.2026286.1755 — test(deploykit): skip engine-backed tests on an UNUSABLE engine, not merely an absent one (#364)

## Summary

Three integration tests guarded themselves with `exec.LookPath("podman")`, which answers **whether the binary is there**, never whether the engine works. On a host whose engine is installed but cannot initialise — a stale runtime dir, a socket the kernel refuses, a read-only `/run/user/<uid>/libpod` — the guard passes and the test then fails with an error that has nothing to do with the code under test:

```
Failed to obtain podman configuration: set sticky bit on: chmod /run/user/1000/libpod: read-only file system
```

That is this issue. **Presence is not usability.** The change replaces all three guards with one shared helper (`deploykit/engine_guard_test.go`):

- it keeps the presence check, then runs the engine's own `info` — the call a human would make — bounded to 30s;
- on failure it **skips visibly with the engine's own stderr**, so a broken engine produces an honest skip on every host instead of three red tests on one;
- a wedged engine that does not answer within the ceiling is a skip too, because **not answering is not usability**.

R2: one helper over three sites rather than three patched copies. The `qemu-img` guard beside one of them is deliberately untouched — a different tool, a different question, not this issue.

**`TestEngineUsable_PresentButBrokenIsNotUsable` is the test that fails without the change:** presence-only logic — what the three guards had — returns true for a `podman` that resolves and cannot run. Its stub is a two-line script in a temp dir placed first on PATH; nothing is contacted, no live service is faked, and **it asserts its own precondition** (that the stub resolves, and that `withEmptyPATH` really emptied PATH) so neither test can pass by accident.
