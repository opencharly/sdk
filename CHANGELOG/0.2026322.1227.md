# 0.2026322.1227 — feat(storekit): move the charly image store into storekit as the registry store's entries

## Summary

W3.6's charly image store — the `oci-layout` marker, ONE `index.json`, `blobs/<alg>/<digest>`, the
atomic index rewrite under a cross-process lock, the streamed blob copies and the
`io.containerd.image.name` export annotation — lived package-private in
`plugin-build/candy/plugin-build/imagestore.go`, so `deploykit.ImageResolver` (opencharly/sdk#459)
could only reach it through an interface. Steps 1 and 2 of opencharly/sdk#460 move that layout into
`sdk/storekit` as the store's own machinery, and `deploykit.CharlyImageSource`'s production
implementation becomes a thin adapter over it.

**The store is the `registry` NAMED store under the ONE cache root.** A second OCI layout in a
second root is what the contract forbids, so `ImageStoreDir()` is `StoreDir("registry")`:
`CHARLY_CACHE_DIR` relocates it with every other store, and `$XDG_DATA_HOME/charly/images` plus its
`CHARLY_IMAGE_STORE_DIR` override are DELETED rather than carried. The name is not invented —
plugin-clean's retirement record names `<cache root>/registry` as image content's home (and
`<cache root>/images` as the RETIRED blob store, so that name is taken), and D-STORE-10 makes the
served registry "a view of store entries", which a built image can only be if it is an entry of
that store.

**The keying reading, stated.** An artifact is a `storekit.Entry` whose KEY is the artifact's own
digest, whose Payload is the same digest (its root document), and whose ANNOTATIONS carry the
reference and the build time. The mutable name is resolved to a digest before the write; the
digest is what the index keys on; a reader resolves a name by reading the annotations, newest build
time first. This is reading (a) of the D-STORE-3/D-STORE-5 question — an index is a name→digest map
and moving a name mutates no entry — made true BY CONSTRUCTION, because the store no longer even
holds the name as a key. Rows cited by line and answered individually under `## Rulebook
compliance`.

**A rebuild deletes nothing.** A rebuild is a different digest, hence a different key: the store
APPENDS a second entry and the previous artifact stays a first-class entry, addressable by its own
digest. Reclaiming a superseded artifact is D-STORE-7's sweep decision, taken from what `Entries()`
exposes — key (digest), reference, build time — through `DeleteEntry` + `UnreferencedBlobs` +
`RemoveBlob`; it is never something a build performs.

Two defects the move exposed and fixes, both required by D-STORE-7:

- **the layout marker.** No storekit-created store ever wrote `oci-layout`, so `NamedStores()` — and
  therefore `charly clean --cache` — could not see ANY named store. `indexEntry` now publishes it,
  because a store that has published an index IS an OCI image layout.
- **an artifact's graph.** Reachability marked an entry's payload and nothing behind it, so a sweep
  would keep an image's manifest and delete the config and layers it names. `ReachableBlobs` now
  walks the artifact graph — ONE walk, shared with `Archive` — so what a live entry reaches stays
  live.

`Add` also refuses an export that names a different reference than the one it is added as, and the
stored payload carries no name and no timestamp (D-STORE-6): the export annotation is re-applied by
`Archive`, the one surface that crosses the engine boundary.
