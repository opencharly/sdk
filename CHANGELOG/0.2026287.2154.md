## Summary

**The daemon config carries the resolved `stage_parallelism`, so the rename is not resolved-but-dead.**

`podman build --jobs N` — the knob legs 1–2 renamed — bounded the concurrent **stages of one build**. BuildKit's client has no per-build equivalent, and the daemon's own surface has the successor (its flag help, measured):

```
$ buildkitd --help | grep -i parallel
   --oci-max-parallelism int        limit the number of parallel build steps that can run at the same time (default: 0)
   --containerd-max-parallelism int limit the number of parallel build steps that can run at the same time (default: 0)
```

So the value is a **daemon** setting (`[worker.oci] max-parallelism`), and this package now renders and compares it:

| symbol | what it owns |
|---|---|
| `DaemonOptions{MaxParallelism}` | the resolved value the drive passes (the `min(NCPU, cap)` resolution stays where it already lives) |
| `DaemonConfig(opts)` | renders it; **omits the key at ≤ 0**, which is the daemon's own default |
| `ConfigMaxParallelism(config)` | reads the value back, so a running daemon's setting is compared, never assumed |
| `NeedsRestart(configured, want)` | the comparison — **with a no-opinion arm: `want ≤ 0` never acts** |
| `logTail(path, n)` | the last lines of the daemon log, so a start failure carries its **reason** rather than only the fact that nothing answered |
| the one caller | `deploykit/vm_box_emit.go` passes `DaemonOptions{}` deliberately — no opinion, so it never overwrites a config the drive wrote |

**⚑ The no-opinion arm is load-bearing, not a convenience.** Two callers with different opinions would otherwise fight over one daemon, and the loser's config would be silently overwritten — the VM-box emit path (which has no parallelism input) and the build drive both ensure the same daemon. `want ≤ 0 never acts` makes the destructive case unrepresentable rather than documented.

Changed: **4 files, +175/−14, two commits** — and every diff item is accounted for above: `buildkitdrive/paths.go` + `buildkitdrive/daemon.go` (the four symbols and `logTail`), `buildkitdrive/buildkitdrive_test.go` (the two new controls), and `deploykit/vm_box_emit.go` (the one caller) — 3 files in `buildkitdrive/` + 1 in `deploykit/` = 4, which is the diff's file count.

## ⚑ What this PR does NOT do, and why — a measured negative result

**A changed value is REPORTED, not force-applied.** I was asked how the drive should apply a changed daemon-level setting, and to bring the measurement back rather than pick the quiet option. The measurement: **the daemon has no process to own.**

It is a detached `rootlesskit` tree that **re-execs itself** — the process table shows the wrapper *and* a `/proc/self/exe` child with identical args — so there is **no single pid to record, probe or signal**, and a liveness probe on the recorded parent calls a **live** daemon dead (observed directly: `Ensure` aborted in 0.00s with "the daemon exited" while the daemon was running and later served `debug workers`). Every restart variant failed on that identity problem in a different costume:

1. **a false-positive restart** — `Restarted=true` reported while the *original* daemon kept the socket, so the config claimed a value no running daemon had (my own first, silently-skipping arm);
2. **the stale state-dir lock** — `failed to lock …/rootlesskit-state/lock, another RootlessKit is running with the same state directory?`;
3. **a socket file that outlives the daemon** — `connection refused` on a file that still exists, so waiting for the *file* to vanish times out against a daemon already gone;
4. **an unowned daemon** answering that this kit has no record of — where killing it would mean killing a process we do not own.

Four fixes, each suggesting the next hole: a pid record, then an ownership gate, then a liveness fast-fail, then a changed wait predicate. **Applying a changed daemon-level setting reliably needs a supervisor** (a `systemd --user` unit = the persistent host artifact D-2 declined), which is a design decision this package does not take on its own. So a mismatch is a **named, actionable error**, measured live:

```
ensure want=4            err=false config=4  workers=true      # cold start: the value reaches the daemon
attach want=4            err=false config=4  workers=true      # same value: attach
mismatch want=8          err=true
    message: buildkitdrive: the running daemon was configured with max-parallelism=4 but 8 was
             requested; the value is set at daemon start, so stop the daemon
             (/run/user/1000/charly/buildkitd.sock) and this drive will start it with the new value
no opinion (running)     err=false config=4  workers=true      # no opinion: attach, never overwrite
```

**⚑ THE WART, named here because the next reader will hit it:** **whoever starts the daemon first fixes the value.** A no-opinion caller (a VM-box emit) that starts the daemon writes the default config (no key), so a later *opinionated* `box build` gets the mismatch error until the daemon is stopped. That is the honest cost of (i); the remedy is a D-2 revision that carries a supervisor **and** the packaging leg that owns it, not a restart slipped into the drive.
