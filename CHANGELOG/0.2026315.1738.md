# 0.2026315.1738 — fix(kit): the build-activity lock root comes from the one cache resolver

## Summary

`kit.BuildActivityDir` built the live-build-activity lock directory by hand —
`$XDG_CACHE_HOME/charly/locks/builds` — so it ignored `CHARLY_CACHE_DIR`, the ONE override
`storekit` declares for the cache root (D-STORE-1). A relocated install therefore wrote its
in-flight `charly box build` locks OUTSIDE the root the builds they gate write to, and
`candy/plugin-clean`'s floor CalVer could not see them: the lock is the only channel by which a
completing sibling build learns which `FROM` pins an in-flight build may still resolve.

The path now comes from `storekit.Dir(storekit.RootCache)`, and the file header's stale caller
is corrected in the same cutover: it named "charly core's acquireBuildActivityLock
(charly/filelock.go)", a symbol that no longer exists in `charly` (deleted with `charly/build.go`
in P8b). The writer is `candy/plugin-box`'s `acquireBuildActivityLock`; the reader is
`candy/plugin-clean`'s `liveBuildFloor`.

| file | change |
|---|---|
| `kit/build_activity.go` | the root comes from `storekit.Dir(RootCache)`; the header names the real writer/reader |
| `kit/build_activity_test.go` | new: the lock root honors `CHARLY_CACHE_DIR`, and the no-override default is pinned |

No behavior change on a default install: with `CHARLY_CACHE_DIR` unset, `storekit.CacheDir()` is
`$XDG_CACHE_HOME/charly`, which is exactly the path the hand-built expression composed. The only
change is the relocated case, which was the defect.

### One environment anomaly, RCA'd before the bed was re-run

```
charly: error: command "build": building check-pod: preparing the builder for check-pod: buildkitdrive: the running daemon was configured with max-parallelism=0 but 4 was requested; the value is set at daemon start, so stop the daemon (/run/user/1000/charly/buildkitd.sock) and this drive will start it with the new value
```

Mechanism: `buildkitdrive` takes the daemon's socket from the runtime root but its config from the
cache root. A daemon left running from an earlier session (started from the DEFAULT cache root)
answered on the shared socket while this relocated client read
`/tmp/charly-cache-bed/buildkitd/buildkitd.toml` — absent, so `configured = 0` — and the drive
refuses to reuse a daemon whose setting it cannot match. Class: **environment, not this diff** —
the change moves a lock path, not the builder. Remedy applied was the error's own documented one
(stop the stale daemon; the drive starts one with the resolved value); the retry ran a fully
relocated daemon (`--root /tmp/charly-cache-bed/buildkitd`) and went 16/16 green. The
relocated-vs-shared-socket mismatch is a genuine SDK rough edge, so it is filed rather than left
in a log: `opencharly/sdk#498`.

## Change classification

Behavior fix + stale-prose correction in one SDK library function; no schema, no wire shape, no
API signature change, no new dependency (`storekit` is a sibling package in this same module).

**Breaking change + rollback:** none for consumers — the signature, the error contract and the
no-override path are unchanged, and the only visible difference is that a `CHARLY_CACHE_DIR`-
relocated install now writes its build-activity locks under the override instead of under
`$XDG_CACHE_HOME/charly`. Rollback is a one-file revert of `kit/build_activity.go` (the test
would go red again, which is the regression it guards). During a mixed-version window the writer
(`plugin-box`) and the reader (`plugin-clean`) pin this module independently: before both carry
this tag they disagree ONLY when `CHARLY_CACHE_DIR` is set — which is precisely the case that was
already broken, because the lock then sat outside the build root while the build honored it.
