# 0.2026294.1343 — fix(workflowkit): validate a loop body's refs against the body's own scope (#441)

## Summary

`workflowkit.ValidatePipeline` is the ONE gate `plugin-pipeline` runs on every authored
`kind: pipeline` before lowering. It passed `refsAmong: defined` to every LOOP BODY
sub-step, and `defined` accumulates TOP-LEVEL step ids only — so a loop body's own earlier
siblings were invisible to it and every multi-stage body was refused at load:

```
step "lane" sub-step "render".when: reference $oracle.* names a step that is not declared earlier
step "lane" sub-step "render".plan: reference $oracle.* names a step that is not declared earlier
```

The ENGINE runs that document. `plugin-lobster`'s `runSubSteps` runs a body against a
per-item COPY of the enclosing result set (`results.scoped`, `refs.go:107`) and does
`scope[sub.Id] = res` after each sub-step (`batch.go:402`), so sub-step N reads every
sub-step before it. The gate was stricter than the engine, and the gate was wrong: a
chained body is how a multi-stage loop body is written, and it is the shape every faithful
migration of a retired pipeline-level `lanes:` fan-out produces (`plugin-migrate#24`
measured it on `eval-omarchy`'s `eval-pr-plan`).

**The fix: a loop body gets its OWN namespace.** `validateLoopBody`
(`workflowkit/validate.go:128`) validates a body against a COPY of the enclosing
earlier-step set, extended with each sub-step as it is validated, in document order. The
call site is `validate.go:100`; the `refsAmong: body` wiring is `validate.go:154`.
`checkEarlierRefs` (`validate.go:303`) is untouched — it still enforces EARLIER-ONLY, now
against the scope that actually holds the reference.

**Which scope each step kind is validated against, after this change:**

| site | scope it is validated against |
|---|---|
| a top-level step | the pipeline's earlier top-level steps (`validate.go:73`) |
| a `parallel:` branch | the pipeline's earlier top-level steps — branches are CONCURRENT, so none has observed a sibling (`validate.go:95`, unchanged) |
| a `for_each:` / `lanes:` BODY sub-step | the enclosing earlier steps PLUS its own body's earlier sub-steps (`validate.go:154`) |

**The protection is pointed, not disabled.** Four edges stay errors and are pinned by
tests: a body reference to a step that does not exist, to a LATER sibling, to ITSELF, and —
from outside — a top-level step naming a sub-step. That last one is the namespace boundary:
the per-item scope never merges back into the run's, so a sub-step id must stay invisible to
the pipeline.
