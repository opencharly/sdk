# 0.2026280.1341 — feat(deploykit): a venue-op seam so a k8s node's containerd reuses the verified transfer

## Summary

`ImageVenue` was podman-shaped: its four store operations (`… image exists`, the torn-overlay `… run`, `… rmi -f`, `… tag`) are podman verbs, so a **k8s node's containerd** store (`ctr -n k8s.io images …`) could not be addressed without forking the verified transfer — the opposite of what `image_transfer.go`'s own comment promises (*"a second venue costs a constructor rather than a copy"*).

This moves those four operations behind a small `venueOps` seam:

- **`podmanOps`** is the **default** (a nil `ops` field) — byte-for-byte today's behaviour, so `charly vm cp-box` and `charly box load` are unchanged.
- **`ctrOps` + `NewNodeVenue`** address a node's containerd. `IsCorrupt` is false: containerd's `ctr images import` is atomic and `ctr` has no `run` to probe a torn layer, so it says so rather than faking a probe.

This is the reusable primitive the `opencharly/charly#809` design names (Phase 2: *"a kubernetes-node venue added to `deploykit`, generalizing the `kindLoadImage` pattern"*). `TransferImageToVenue` is **not** forked (R3).
