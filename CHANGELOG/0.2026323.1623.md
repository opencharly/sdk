# 0.2026323.1623 — fix(loaderkit): name a losing revision pin, and the producer-first way out

## Summary

`PickCandyVersion` orders candidates by CalVer, so a release tag always beats a ref that is not one. **That preference stays**, and this PR does not change it: it is the fix for opencharly/charly#1179, where a stale pinned revision two hops away beat the release carrying the actual fix, and reversing it would let a shared scope compose an arbitrary revision — worse than refusing.

What changes is the sentence the refusal emits. Measured on 2026-11-19 in a disposable `distro-cachyos` checkout while trying to bed-prove `opencharly/layer-cuda#28` (`box/nvidia-cdi` pinned a layer at a 40-hex revision; the layer's own `require:` named a tag in the same box scope):

```console
$ charly box validate
Notice: candy github.com/opencharly/layer-cuda resolved to multiple git tags with differing content within one scope (box=nvidia-cdi); using newest referenced v2026.323.0252 (from github.com/opencharly/layer-cuda@v2026.323.0252); also referenced 219f643b… (scopes: box=nvidia-cdi); …
charly: error: command "validate": validation error: candy github.com/opencharly/layer-cuda resolved to multiple git tags with differing content within one scope (box=nvidia-cdi); using newest referenced v2026.323.0252 …
exit=1
```

It says "multiple git **tags**" about a reader who pinned no tag, never names their revision's fate, and offers no way forward — so an unmerged layer's composing bed reads as impossible until the layer merges and is tagged (`opencharly/charly#1215`).

After this change, one sentence per losing non-CalVer ref in a conflicted box scope is appended (the pre-existing sentence still leads, so the line stays recognizable):

```console
… also referenced 219f643b404acdba32592784eb23ca488fe57f1b (from …; scopes: box=nvidia-cdi); box=nvidia-cdi pins 219f643b404acdba32592784eb23ca488fe57f1b, which is a revision with no CalVer to order it and cannot be arbitrated against a release tag: it carries no recency the CalVer order can read, so v2026.323.0252 wins and 219f643b… is never composed. Move the `require:` that names v2026.323.0252 to a release containing 219f643b… FIRST (producer-first: land it, merge it, tag it, then move the pin), or stop naming v2026.323.0252 in box=nvidia-cdi
```

A tag-vs-tag skew gains no such clause (nothing there is a revision), and a cross-box difference stays silent — the scope rule is applied before the remedy, so nothing can leak out of the silent path.

**Decision, stated because the issue asked for one:** the *loud diagnostic* over *sha-awareness*, on the evidence in `newerCandidate`'s own doc comment plus `candy_version_warn_test.go`'s `TestPickCandyVersionNamesTheLosingRefs` — the CalVer-over-revision rule was added deliberately for #1179 and a revision carries no recency, so promoting it would be a regression, not a fix. Also, the loudness already exists on the validate path (measured above: exit 1); what was missing was the actionable text.

It contradicts `spec.Diagnostic.IsError()` and `PickCandyVersion`'s own "a resolvable skew is INFO, never WARNING … must not fail on a successful arbitration" contract; measured (a `Notice:` line and the identical text as the command's error, exit 1).
