# 0.2026309.1926 — fix(deploykit): persist and classify a pod deploy's authored engine selector

## Summary

`spec.SaveDeployStateInput` gained the authored `engine:` selector
(opencharly/spec#292, tag `v0.2026309.1917`). This is the sdk consumer leg of
opencharly/charly#1109:

- `deploykit.applyDeployState` writes a non-empty `Engine` onto the per-host
  entry and never clears an existing value with an empty patch. `charly config`
  / `charly start` resolve their run mode from that entry, so the selector must
  survive the state write.
- `deploykit.deployDiscForEntity` treats `engine:` as a pod-only signal. A
  no-overlay `PrepareVenue` patch can carry ONLY the selector; without this the
  node-form writer would emit a targetless `group:` entry and the next load
  would reject `engine` there (`#GroupInput`).

The consumer legs that run the live bed are `plugin-deploy-pod` (carries the
node's engine into the patch and derives the run mode from it) and the charly
pin bump that assembles both; the `pod:`/`engine: containerd` bed is named in
those PRs.
