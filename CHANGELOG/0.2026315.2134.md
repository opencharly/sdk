# 0.2026315.2134 — refactor(storekit): re-export the roots resolver instead of computing it

## Summary

`storekit/roots.go` stops COMPUTING the four roots and starts RE-EXPORTING them.

Leg 1 (`opencharly/spec#303`, tagged `v0.2026315.2118`) moved the roots and the single
`CHARLY_CACHE_DIR` override into `github.com/opencharly/spec/storeroot`, because `charly` core —
the plugin HOST — may import only `spec/*` and therefore could never resolve its cache root
through a mechanism kit (`opencharly/charly#1119`). This PR is leg 2: the sdk side of that move.

What the file is now:

```go
type Root = storeroot.Root
const (
	RootConfig  = storeroot.RootConfig
	RootCache   = storeroot.RootCache
	RootState   = storeroot.RootState
	RootRuntime = storeroot.RootRuntime
)

func Dir(r Root) (string, error) { return storeroot.Dir(r) }
func CacheDir() (string, error) { return storeroot.CacheDir() }
```

- **No second implementation.** `Dir` and `CacheDir` delegate; `Root` is an ALIAS, so
  `storekit.Root` and `storeroot.Root` are one type and a value crosses the boundary in either
  direction with no conversion.
- **The public API does not move.** `Root`, the four consts, `Dir`, `CacheDir`, `StoreDir` and
  `NamedStores` keep their names, signatures and results, so every plugin that imports
  `github.com/opencharly/sdk/storekit` — `kit`, `buildcache`, `buildkitdrive`, `artifactkit` —
  compiles and behaves exactly as before.
- **`StoreDir` and `NamedStores` stay here**, because they are store ADDRESSING, not root
  resolution: they join a store name onto the cache root and test the `oci-layout` marker. They
  now inherit the root from the contract resolver like everything else.
- `require github.com/opencharly/spec` is bumped to the tag that carries the new package.

**This is the lockstep leg.** The bump and the re-export are one commit on purpose: an sdk that
bumped `spec` without re-exporting would leave the roots reachable only where they now are, and a
re-export with no bump would not resolve. The measured straddler is not `vmshared` (it compiles
against the new `spec` unchanged) — it is the reason the bump cannot be separated from the code:
`sdk`'s own `storekit` is the file that must stop computing.

## Change classification

**Mechanism relocation, API-compatible.** No exported identifier is added, removed or renamed:
`Root`, `RootConfig`, `RootCache`, `RootState`, `RootRuntime`, `Dir`, `CacheDir`, `StoreDir`,
`NamedStores`, `Store`, `OpenStore`, … all keep their names, signatures and results. What moves is
the IMPLEMENTATION of the four roots — into the contract module — and what changes here is that
`Dir`/`CacheDir` delegate instead of computing.

**Breaking change + rollback:** nothing breaks for `sdk`'s consumers. The one observable difference
is where the roots are IMPLEMENTED, and that is invisible through this package's API; a plugin that
imports `storekit` keeps its compile and its behaviour (proved by the three-way dump in §1 and by
the whole module's suite). The `require github.com/opencharly/spec` line moves forward one tag, so
a consumer that pins `sdk` and also pins `spec` below `v0.2026315.2118` must raise its `spec` pin to
match — otherwise MVS raises it for them at `go mod tidy` and the build is unaffected. Rollback is
two commits, in this order: revert this repo's commit (the `go.mod` bump goes with it, returning
to the previous `spec`), and — only if the resolver itself must be withdrawn — revert leg 1's
commit in `spec`. No data migration in either direction: the roots resolve to the directories they
always did, which is exactly what §1 measures.
