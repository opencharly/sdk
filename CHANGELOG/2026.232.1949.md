# 2026.232.1949 — the sdk tag-scheme guard

The org-wide `auto-merge` engine mints its release tag as `v<YYYY.DDD.HHMM>`
from the merge-time CalVer stamp. That form is **not a valid Go module
version** for this repo:

- the major `YYYY` is ≥ 2, so a valid semver would force the module path
  `github.com/opencharly/sdk/v2026`, which does not exist — every
  `import github.com/opencharly/sdk` would break;
- the `DDD` / `HHMM` segments carry leading zeros (semver forbids a leading-zero
  segment).

Go module resolution therefore cannot use any `v2026.*` tag. All 371 tags on
this repo are of that form and unusable for `go get` / module resolution.

## The guard

`ensure_tag` now computes the tag version through `tag_ver()`, which converts
the stamp to this repo's Go-module scheme **`v0.<YYYYDDD>.<HHMM with all
leading zeros stripped>`** — e.g. `2026.232.0733` → `v0.2026232.733`,
`2026.232.1949` → `v0.2026232.1949`. Mandatory, not an exemption: a Go module
path without a `/vN` suffix must be major 0.

The guard is **inert on every non-sdk repo** (the `REPO = opencharly/sdk`
branch never fires), so the one byte-identical engine serves all thirteen
repos. The conversion is proven by the 102-assertion stub-gh harness
(scenarios s21–s23: the mint POST fires with the converted `v0.` form, the
merged-HEAD tag is the `v0.` form, and the already-exists path is unchanged).
