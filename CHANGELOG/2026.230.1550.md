# 2026.230.1550 — two deploykit fixes: unless_exists, and the packaging child's project scope

Both consume contracts that land first in `opencharly/spec`.

## `EmitDownload` honors `unless_exists`

Consumes the `unless_exists` field added to `#Op` in the spec contract repo.

When set, the emitted RUN wraps the WHOLE step — fetch, extract AND chmod — in a
build-time existence test:

```sh
if [ -e '/usr/bin/ollama' ]; then echo "skipping download: /usr/bin/ollama already present";
else { ...fetch + extract... }; fi
```

Wrapping all three matters. Guarding only the fetch would still pay the extract, and a
`chmod` left outside the guard fails on a path that was never created.

Absent, the emission is byte-identical to before, so no existing candy changes.

The guard is honoured by the two emitters that produce ONE RUN for ONE op — `EmitDownload`
and `EmitCmd` (the `run:` verb) — through one shared `WrapUnlessExists`. That matters
because the schema documents the field on `#Op`'s shared modifier block as a gate for "an
install step": honouring it in a single emitter would have made `unless_exists:` a silent
no-op on every other step kind, which is exactly the shape a reader cannot detect. The batch
emitters (mkdir/link/setcap) fold MANY ops into one RUN, so a per-op guard has no expressible
position there, and copy/write emit a COPY instruction that no shell test can wrap; those
combinations are rejected at validation rather than silently ignored (opencharly/charly#309).

The guard is shell-quoted in BOTH positions. The first draft quoted it for the `[ -e ]` test
and interpolated it RAW into the echo, so a path containing a double quote emitted a shell
syntax error and one containing `$(…)` command-substituted in the message while the test used
the literal — the skip line could name a different path than the one checked.

Three review rounds found three ways for this emitter to produce shell that does not run, so
the tests now parse what they assert on: both guard tests write the emitted body to a file and
run `bash -n` over it, and the `run:` test is table-driven over ten authored command shapes.

The termination rule is the part worth recording. `{ list; }` accepts `;` **or** a newline
before the closing brace, and `;` is a COMMAND separator — safe only when the preceding text
is a complete simple command. Three ordinary shapes are not: a trailing `# comment` swallows
the `; }; fi` into itself so the brace never closes; a body ending in a heredoc needs its
terminator alone on a line, so `EOT; }; fi` never ends it; and a body already ending in `;`
yields `;;`, the case-clause token. No amount of trimming turns any of those into a command
position.

`{ list; }` also requires the list to be NON-EMPTY — the same rule on its other end. A `run:`
step whose command is empty or comment-only would emit `{ }`, so a leading `:` (the shell
no-op) guarantees at least one command for every body and is invisible for every other shape.
Without it, adding a guard to a step that already did nothing turned it into a build failure.

So the guard ships as two entry points sharing one implementation of its SEMANTICS:
`WrapUnlessExists` (`; }`) for `EmitDownload`, whose payload is a single-quoted argument on one
Containerfile `RUN` line where a literal newline would end the instruction, and
`WrapUnlessExistsBlock` (`\n}`) for `EmitCmd`, whose payload is a heredoc body that is already
multi-line. One form serving both lexical contexts is exactly what could not hold.

Proven in both directions on real builds of the consuming superproject: on Fedora (no
ollama package) the step executes and fetches; on CachyOS (packaged `ollama`) it emits the
skip line and performs no fetch at all.

## The packaging child runs under the candy's own project scope

`generateLocalPkg` spawns a `charly generate-packages` child to build the in-development
package for a `localpkg:` candy. It inherited the PARENT's project scope, which is about the
BOX being built — and when that box lives in a `box/<distro>` submodule, the submodule
vendors no candies and declares no `generate-packages` command plugin. The child therefore
resolved the wrong project and the verb did not exist there, so `--dev-local-pkg` died
roughly 14 seconds into every submodule build. Seven boxes were affected.

Three things had to be true at once, and each is now explicit:

- **The child's scope is the project that OWNS the candy**, resolved by walking up from the
  candy's `charly.yml` (`candyProjectDir`), not the parent's scope.
- **Every path handed across the process boundary is absolute** (`absFromHere`). The child
  chdirs into its own project, so a path still relative at the boundary would resolve against
  the child's directory rather than ours.
- **Both project-scope environment variables move together.** They are mutually exclusive in
  the CLI, so stripping one and leaving the other makes the child exit on
  `--repo and --dir are mutually exclusive` instead of running.

That last invariant is not local to this package, so it does not live here: it ships as
`spec.ChildProjectEnv` in the contract module (opencharly/spec#38), and this package calls it.
An earlier revision of this branch had a private `charlyChildEnv` doing the same work; review
found a third copy of the same filter in `candy/plugin-mcp`, which is exactly the drift the
contract module exists to prevent. All three call sites now share one implementation, and the
helper's unit tests live with the helper — including the lookalike-name case this package's
deleted test was the only thing covering.
