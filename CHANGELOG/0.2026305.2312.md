# 0.2026305.2312 — fix(deploykit): derive a candy's COPY source from its resolution origin, not its name

## Summary

A candy DECLARED IN an imported namespace lives in that namespace's own fetched checkout, OUTSIDE the importing project's tree. Its build-context COPY source was nevertheless emitted as the project-relative `candy/<name>/`, so the image build died with `"/candy/<name>": not found` and the candy was never staged. Measured live on a project importing `distro-cachyos` as a namespace and building its `cachyos.cachyos` box:

```console
# pre-fix: charly `bin/charly` 2026.293.1809, sdk v0.2026293.417
$ charly -C <repro> box generate cachyos.cachyos   # exit 0
$ grep 'COPY .*cachyos-base-check' .build/cachyos.cachyos/Containerfile
6:COPY candy/cachyos-base-check/ /
$ ls .build/_candy/cachyos-base-check
ls: cannot access '.../.build/_candy/cachyos-base-check': No such file or directory   # never staged

# fixed: charly 7bb19d0a rebuilt against THIS branch's sdk (head 1341a5b)
$ charly -C <repro> box generate cachyos.cachyos   # exit 0
$ grep 'COPY .*cachyos-base-check' .build/cachyos.cachyos/Containerfile
6:COPY .build/_candy/cachyos-base-check/ /
$ ls .build/_candy/cachyos-base-check
charly.yml                                          # staged, so the COPY resolves
```

The repro project is the whole config, pinned to a cached namespace tag:

```yaml
repo: github.com/opencharly/copysource-repro
defaults: {platform: [linux/amd64], tag: auto, registry: ghcr.io/opencharly, build: [pac]}
import:
  - cachyos: '@github.com/opencharly/distro-cachyos:v2026.274.2120'
```

**Mechanism.** `loaderkit.projectCandiesScanned` folds each imported namespace by recursing with the namespace's OWN `RootDir`, and that same parameter was also the root the "outside the project → mark Remote" check compared against. A candy inside the namespace's checkout is therefore INSIDE the comparison root, so it stayed `Remote=false`; `deploykit.CandyCopySource` fell through to its name-derived `candy/<name>/`, and `plugin-build`'s staging (keyed on the same `Remote` flag) never copied it into the build context.

**Fix (final state of this branch).**
- `loaderkit/project_candies.go` — thread TWO roots through the fold: `rootDir` still anchors each namespace's relative `from:` paths, while the new `projectRoot` is the unchanged TOP-LEVEL project directory and is what the Remote marking compares against. An imported-namespace candy is now `Remote=true` and is staged like an `@github` ref. The outside-root test is exact (`..` or a `../` prefix), in both the loader and the renderer, so a project-local directory literally named `..<x>` is not misclassified.
- `deploykit/candy_stage.go` — `candyOrigin` is the ONE origin predicate (Remote, or a resolved directory outside the build root) and it returns BOTH the staged verdict and the project-relative directory; `candyCopySource` is the ONE origin→COPY-source mapping built on it, with no duplicated guard and no dead branch. `candySourceDir` is the shared directory resolver.
- `deploykit/builder_support.go` — `BuildStageContext` calls the same mapping from the layer in hand instead of re-deriving the candy's map key (`CandyMapKey(layer)` returned an EMPTY key for a Remote candy with no `RepoPath`, i.e. an imported-namespace candy, so the lookup dereferenced a nil layer).
- `deploykit/candy_stage.go` (`rootCopySources`) — the other name-derived candy-path site uses the same predicate and directory resolver.
