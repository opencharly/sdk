# 0.2026320.2158 — fix(loaderkit): a real CalVer tag outranks a bare SHA, and the skew names every loser

## Summary

Two defects in the candy-version arbiter, both found while advancing a pin in a consumer project
(opencharly/distro-cachyos#184) and both of a kind that silently produces the WRONG image.

**1. A bare SHA wins the "newest" arbitration.** `PickCandyVersion` orders candidates with the
lenient `kit.CompareCalVer`, whose lexical fallback compares `7766a9d06ec5` against
`v2026.320.1938` as strings: `'7' > '2'`, so **the stale SHA is "newest"**. A bare commit SHA is
a legitimate pin — the `distro-*` rule pins SHAs precisely because those commits are untagged —
but it carries no recency at all, so this inverts the arbitration exactly when a project mixes
the two forms.

Measured in opencharly/distro-cachyos: the CDI driver-shadowing fix at
`layer-nvidia:v2026.320.1938` lost to the pre-fix commit that a stale `require:` two hops away
still pinned, and the resolver said so at INFO level:

```
Notice: candy github.com/opencharly/layer-nvidia resolved to multiple git tags with differing
content within one scope (box=versa); using newest referenced 7766a9d06ec5fe8c276c091a68fb72cea12688e3
```

`spec/calver.ParseCalVer` already documents the intended semantics — *"a false result is treated
by the freshness comparison as older than every real CalVer"* — so this restores it rather than
inventing a new rule: a parsed CalVer tag outranks a non-CalVer ref, and only two non-CalVer refs
fall back to the legacy lenient order (so a project that pins only SHAs is unaffected). Tags
carry a leading `v`, so the comparison trims it before parsing — without the trim every tag
parses as non-CalVer and the preference would never apply.

**2. The skew diagnostic named only the winner.** A message that states a comparison and hides
one side is not actionable: the reader cannot tell which refs disagree, nor where the losing one
came from. The line now appends every losing candidate with its tag, its source, and the box
scopes that named it:

```
... using newest referenced v2026.320.1938 (from ...); also referenced 7766a9d06ec5
(from ...; scopes: box=versa)
```

That gap is opencharly/charly#1179, filed from the same episode: finding the losing ref took
bisecting an eighteen-candy box one candy at a time, because the tool named one side of a
two-sided comparison.

## Change classification

**Breaking change + rollback:** behaviour changes for exactly one case — a closure that names the
same candy both by CalVer tag and by bare SHA now resolves to the TAG instead of the lexically
greater SHA. That is the intended semantics (a SHA is a pinned old commit, not a newer version),
and it is what a consumer wants: the alternative silently kept pre-fix content. Rollback is
reverting this commit; consumers then resolve to the SHA again, which is the defect.

Change class: **library code** — unit suite + `go vet` + the repo's validate gate.
