# 2026.216.0001 — the injection writes the composition SOURCE, not a derived view

`opencharly/sdk#119` (merged as `bc183d13`, `v0.2026215.2321`) shipped an incomplete fix. It made
a box composing only service candies install its init — and in doing so it silently removed six
acceptance probes from the teaching box, including the only one proving the init actually runs.
This is the completion, and it deletes the duplicate derivation rather than bridging it.

## The root cause, stated plainly

`InjectInitDependsCandy` wrote to `buildkit.ResolvedBox.Candy`. But `resolved.Candy` is a **pure
`BareCandyRef` normalization of the authored list** (`buildkit/config_resolve.go:124-126`) — a
DERIVED VIEW, not an independent source of truth. Writing to a derivation does not change what it
derives from, so every consumer reading the source saw nothing.

Five collectors read the source, via `BoxCandyChain` → `cfg.WalkBaseChain` → `node.Img.Candy`:

| Collector | What an injected candy silently stopped contributing |
|---|---|
| `deploykit/description_collect.go:81` | its `plan:` — the ADE acceptance spec baked into `ai.opencharly.description` |
| `deploykit/hooks_collect.go:48` | its hooks |
| `deploykit/ports_collect.go:22` | its published ports |
| `deploykit/shell_collect.go:24` | its shell contributions |
| `deploykit/volume_collect.go:20` | its volumes |

Measured on `box/fedora` `tutorial-shell`, same bed, one variable:

```
2026.215.2048  supervisord composed explicitly   live 24 steps: 22 passed   image 24: 19 passed
2026.215.2254  supervisord injected (#119)       live 18 steps: 16 passed   image 18: 14 passed
```

The ADE inversion is the serious part: the shipped image ran supervisord as PID 1, but
`charly box pull` + `charly check box` no longer tested it. #119's own argument was that boxes
SHOULD now rely on injection — so every box adopting it inherited the hole.

## What lands

**`deploykit/init_depends.go`** — `InjectInitDependsCandy(cfg *spec.Config, layers, initCfg)` now
prepends the active init's candy to the box's AUTHORED composition via `cfg.SetBox`, before box
resolution. `ResolveBox` then derives it into `resolved.Candy` for free, at every composition path.

**The five collectors are UNCHANGED** — no signature change, no threading, no fallback branch, and
no special case naming `supervisord` or `init`. They keep walking `cfg.WalkBaseChain`, so
base-chain folding (union across levels, first-occurrence-wins) is untouched; the injected candy is
simply present in the list they were already reading, at every level.

**The three chokepoints move before resolution** — `loaderkit/resolve_project.go`,
`deploykit/spec_box_resolve.go`, and `candy/plugin-build/resolve.go` (that one lands in the
superproject, see "Cross-repo" below).

**`loaderkit/resolve_project.go` loses the two-pass dance.** The `freshOrder` / `freshBoxes`
accumulate-then-inject-then-reproject sequence existed ONLY because injection had to run after
resolve. One pass again; deleted, not left dormant.

**The authored list is passed to `ResolveCandyOrder` raw.** It carries
`@github.com/…/candy/x:v2026.201.0706` forms the candy map never has (it is keyed bare), but no
normalization belongs in this pass: `ResolveCandyOrder` already normalizes at its own chokepoint —
`ExpandCandy` (`deploykit/graph.go:36-42`) BareRef-normalizes every ref before lookup and documents
itself as "the single chokepoint every ResolveCandyOrder caller funnels through".

An earlier revision of this PR added a `BareCandyRef` pre-pass here and justified it with the claim
that "without normalizing, a remote-ref composition resolves to nothing and injection silently
skips". **That claim was false and the code was dead.** Deleting the pre-pass leaves the whole
module green — including both remote-ref tests — because `BareCandyRef` is idempotent and
`ExpandCandy` was already doing the work. It was worse than merely redundant: it was a second copy
of a chokepoint's job (R3), and its comment taught the next maintainer that `ResolveCandyOrder`
does not normalize, inviting the same pre-pass at the next call site. Caught by a validator that
mutation-tested the line rather than reading the comment; the superproject leg
(`candy/plugin-build/resolve.go:124`) had it right all along.

## Why this and not "make the collectors read the resolved boxes"

That was the first direction taken, and it was wrong. It redirects readers to whichever copy
happened to be patched while leaving `FillBoxPlans` (`deploykit/resolved_project.go:144`, the
`include: box:<name>` plan-splice arm) and every namespaced box still re-deriving from authored
cfg — the same bug class in a second location. It also could not work for namespaces at all, whose
resolved boxes exist only transiently inside `FillNamespaceBoxViews`. One list is the fix; two
lists with better-behaved readers is not.

`deploykit/init_depends_collect_test.go` (new) — the seam itself, asserted on the CONTRIBUTION
class rather than only on descriptions, so a future transform that reopens it fails on whatever it
breaks:

- `TestInjectedCandyReachesCollectedDescription`
- `TestInjectedCandyReachesCollectedPorts`
- `TestInjectedCandyReachesCollectedVolumes`
- `TestInjectedCandyReachesBaseChainCollectors` — a leaf inherits the base's injected init candy, with a de-dup assertion
- `TestInjectionLeavesMachineVenueCollectorsAlone`
- `TestInjectionIsIdempotentAcrossChokepoints`
- `TestInjectionIsIdempotentAcrossChokepointsRemoteKeyed` — see the idempotence note below

Mutation-verified. Stub = drop the `cfg.SetBox` write so the pass computes the same answer and
writes nothing (exactly the pre-fix shape). **Nine** tests fail in `deploykit` — the four new seam
tests, both idempotence guards, and three existing injection tests — and **ten** module-wide, the
tenth being `loaderkit`'s `TestProjectResolvedProject_InjectsInitDependsCandy`. Restored: green.

(An earlier revision of this entry said seven. That number was carried from a report instead of
re-derived by running the mutation, and a validator counted it correctly. The figure here is from
`go test -count=1 ./... 2>&1 | grep -cE '^--- FAIL'` on the mutant.)

**`TestInjectionIsIdempotentAcrossChokepointsRemoteKeyed` exists because the first idempotence
guard was vacuous on the shape that ships.** Three chokepoints can now fire against one shared
`*spec.Config`, so idempotence became load-bearing. The first guard was mutation-tested by deleting
its `slices.Contains(order, key)` check — and stayed GREEN, because the earlier bare-name check
still fires when key == name. Only a REMOTE-keyed init candy depends on the deleted guard, and that
is every distro submodule. Re-mutated with the remote-keyed case:

```
--- FAIL: TestInjectionIsIdempotentAcrossChokepointsRemoteKeyed
    three passes over one config must equal one:
      [.../supervisord @.../sshd:2026.200.1200]
   -> [.../supervisord .../supervisord .../supervisord @.../sshd:2026.200.1200]
```

A guard that only passes on the shape that does not ship is worse than no guard, because it reads
as coverage.

## A deliberate asymmetry, now tested rather than accidental

The documentation site renders the AUTHORED composition while the built image carries the COMPOSED
one. `candy/plugin-docs` never constructs a `spec.Config` — `collectEntities` reads each
`charly.yml` with `os.ReadDir` + `os.ReadFile` + `yaml.Unmarshal` into `yaml.Node`, so it cannot
reach an injection chokepoint by construction. The generated `tutorial-shell` page therefore keeps
listing two candies, matching its source and the site prose that explains the init is deliberately
absent. That is the correct split for a teaching page; it is recorded here so a future change that
routes docs generation through the loader knows it is changing published behaviour.
