# 0.2026294.1003 — fix(workflowkit): admit the `lanes` arm, the pooled fan-out spec now declares

## Summary

`spec#263` put `lanes?` on `#PipelineArms`, and `plugin-lobster#8` serves it as a POOLED fan-out over a runtime collection. But `sdk/workflowkit.ValidatePipeline` — the ONE gate `plugin-pipeline` runs on every authored pipeline BEFORE lowering (`entity.go:213`, `plugin.go:106`) — knew only `for_each`. An authored `lanes:` step therefore read as arm-less and every companion it carries as a stray, so the arm could not reach an engine through the front-end:

```
step "lane": no execution arm — set exactly one of run/pipeline/workflow/parallel/for_each/input/plan/charly/approval
step "lane": steps/item_var/batch_size only apply alongside for_each
```

**Why `lanes` is an arm, not a knob.** An arm is the key that decides what a step EXECUTES. `lanes:` executes its `steps:` body once per item of a runtime collection, through a pool of `batch_size` concurrent lanes. `for_each:` executes the same body once per item IN ORDER — upstream lobster's own semantics — and ignores `batch_size`. Two different execution shapes over one body, mutually exclusive with each other and with `run`/`pipeline`/`workflow`/`parallel`: so `lanes` joins `execArms`, and the exec-arm XOR refuses `for_each` + `lanes` on one step instead of silently picking one.

The four edits:

1. `execArms` gains `lanes` beside `for_each` (`workflowkit/validate.go:30`) and the arm map gains `"lanes": v.lanes != ""` (`validate.go:143`). Without either, the XOR cannot see the arm.
2. `stepView` gains `lanes` (`validate.go:121`), wired from `s.Lanes` (`validate.go:62`), so the shared validator sees the expression.
3. The two loop co-field rules admit EITHER loop arm and name both (`validate.go:213` for the missing body, `validate.go:230` for the strays), so a `lanes` step is no longer told its body belongs to `for_each`.
4. The arms' PACING rules stay apart (`validate.go:238`, `validate.go:243`, `validate.go:246`): `lanes` REQUIRES `batch_size >= 1` (the pool width) and refuses `pause_ms`; `for_each` keeps upstream's sequential semantics with `batch_size` ignored.

Two further sites, and the pin:

5. **The earlier-step reference rule** (`validate.go:197`). `for_each:`'s collection expression is checked against the earlier-steps set; `lanes:` carries the same kind of expression (`$seed.items`). Without this rule the gate accepts `lanes: $later.items` and the engine fails at run time — the class of error the gate exists to prevent. This is the fifth edit, measured below like the others.
6. **`GraphEdges`** (`workflowkit/graph.go:39`): `when` / `stdin` / `for_each` were dataflow edges. `lanes` is the same edge kind, and without it the rendered graph draws a step whose input it cannot show.
7. **`spec` pinned at `v0.2026294.929`** in `go.mod` — the tag that carries `#PipelineArms.lanes` (`lanes?: string & !=""`).

`Lower` needs no change, as leg 3 measured: it copies lobster-native step keys verbatim, and the emitted `.lobster` keeps `lanes` / `batch_size` / `item_var` intact (pasted below).

The committed diff (`git diff --shortstat origin/main HEAD`): 7 files changed, 265 insertions(+), 56 deletions(-), listed item by item below.
