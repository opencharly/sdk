# 0.2026250.154 — fix(kit): the ledger TRANSACTION lock gets its own file — the charly.yml.lock conflation self-deadlocked every fleet del/add

## Summary

The ledger TRANSACTION lock (`kit.AcquireLedgerLock` — held for the WHOLE `charly fleet del`/`fleet add` operation: resolve → members-down → node-del-dispatch) and the per-host `charly.yml` read-modify-write lock (`LedgerPaths.LockFile`, shared by `writeLedger`, `deploykit.MutateFleetConfig`/`SaveFleetConfig`, and `spec/refs GitClient.save`'s cache section) were collapsed onto ONE file (`charly.yml.lock`). `flock` is per-open-file-description, so every in-process nested config RMW under a transaction hold contended with the holder's OWN fd and stalled — the deterministic `charly fleet del <name> --assume-yes` deadlock (7/7 reproducible, standalone and inside check runs, on every binary):

```
FleetDelCmd.Run (candy/plugin-fleet walk.go)
  └─ kit.AcquireLedgerLock                    ← holds charly.yml.lock (fd 4)
     └─ resolveTreeViaLoader → deploy-plugins-connect → loadDeployPlugins → scan
        └─ refs.GitClient.LatestTag (cache miss) → GitClient.save
           └─ AcquireFileLock(charly.yml.lock) ← fd 7 retries flock forever
```

Captured evidence: SIGQUIT goroutine dump — goroutine 1 parked in `spec/lock.flockBounded` ← `AcquireFileLock` ← `GitClient.save` under the del's own ledger-lock fd; kernel `fdinfo` showed fd 4 holding `FLOCK ADVISORY WRITE` on `charly.yml.lock` while fd 7 retried with 0 CPU. The 2-min `lockTimeout` bound caps each wait, but every timeout SILENTLY DROPS the write and the git cache never persists, so the next save stalls again — dozens of teardown-phase records × 2 min each ⇒ the never-completes hang plus silent lost config/ledger writes. The del's teardown phase (`RemoveVmDeployEntry` → `MutateFleetConfig`) nests under the same hold identically.

**Fix**: the transaction lock moves to its OWN file (`<config>.ledger.lock`, new `LedgerTxLockPath`) — restoring the genesis semantics (the pre-sdk ledger lock was a dedicated `~/.config/opencharly/installed/.lock`, never the config lock). The config RMW lock keeps guarding `charly.yml` for ALL its writers (correctly shared — they RMW the same file); the transaction lock orders fleet flows against EACH OTHER; brief config writers legitimately interleave inside a transaction (each RMW re-reads the current file under the config lock and preserves the other sections). All `AcquireLedgerLock` callers go through `kit.DefaultLedgerPaths`/`LedgerPaths.ConfigFile` (verified: plugin-fleet walk.go/deploy_target.go, plugin-substrate status_local.go — no independent lock-path construction), so they move atomically.
