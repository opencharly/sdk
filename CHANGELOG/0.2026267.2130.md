# 0.2026267.2130 — fix(deploykit): scope volume teardown to the deploy's own volumes

## Summary

Fix a silent **data-loss** defect in deploy volume teardown/listing, and repair the stale schema-stamp fixtures that rot on every schema HEAD bump.

### The defect

A deploy's named volumes are namespaced by **prefix** — `DeployVolumePrefix` is
`charly-<deploy-key>-<instance>-`. A **base** deploy's prefix
(`charly-githubrunner-`) is itself a prefix of every sibling **instance's**
volume name (`charly-githubrunner-no-1-state`). Podman's
`volume ls --filter name=<X>` is a **substring** match (verified live on podman
6.1.2), and `RemoveEncryptedVolumes` enumerates encrypted-volume directories by
the same prefix. So a prefix-only scope touched a **live sibling instance's**
volumes:

- `charly remove --purge <base>` deleted `<base>/<instance>`'s state/storage volumes and its gocryptfs cipher dirs.
- `charly volume list <base>` listed the sibling volumes.

Reproduced on this host with `githubrunner` + instances `no-1..no-4`.

### The fix

One pure predicate pair in `sdk/deploykit` (single owner of the "is this volume mine?" decision, R3):

- `SiblingVolumePrefixes(dc, deployKey, instance)` — prefixes of every **other** deploy in the per-host config.
- `VolumeNameBelongsTo(name, deployKey, instance, siblings)` — **longest-prefix wins**: the name must carry this deploy's prefix AND no sibling prefix may match at greater length. An instance still owns its own volumes; the base can no longer claim them; the trailing dash prevents a `no-1` vs `no-10` near-miss.

`RemoveEncryptedVolumes` now takes the caller's config via the new
`RemoveEncryptedVolumesWithConfig`. **This matters:** the bare
`deploykit.LoadDeployConfig` is a documented *silent no-op out-of-process* (it
returns `nil,nil` unless charly-core's init registers `DeployStateHost`), and
`candy/plugin-pod` **is** out-of-process — so the round-1 version still
over-matched on the encrypted path *live*. The live proof below caught exactly
that; the plugin now passes its executor-loaded config (the same seam discipline
`resolveSidecarNames` already follows). The companion `opencharly/plugin-pod`
PR consumes these helpers and must land **after** this one; until it does, the
pod-side `remove --purge` / `volume list` data-loss remains open on `plugin-pod`'s side.

### Stale schema-stamp fixtures (R2 — fixed in-tree, not deferred)

`packagekit.TestRenderConfig_ValidatesWithCharly` rendered a config stamped
`2026.249.2125` and failed against the current dev charly
(`schema 2026.261.1747 is required (found "2026.249.2125")`). The fixtures now
source the stamp from `spec.SchemaVersion`, so they cannot rot: the live-validate
test and its same-mechanism sibling `loaderkit/cross_kind_name_test.go`
(claim-keyed sweep). No "pre-existing / unrelated" deferral — fixed here.

## How tested

### Live end-to-end proof (the actual changed runtime path)

Run on an explicitly **`disposable: true`** target — an isolated
`CHARLY_DEPLOY_CONFIG` whose deployed entities carry the marker:

```yaml
version: 2026.261.1747
app:      {pod: {image: app, disposable: true}}
app/no-1: {pod: {image: app, disposable: true}}
app/no-2: {pod: {image: app, disposable: true}}
other:    {pod: {image: other}}
```

Built charly with the fixed `sdk` + fixed `plugin-pod` compiled in, real podman
volumes and real gocryptfs cipher dirs, then ran the real purge. (The destroy is
authorized by `disposable: true`, never inferred from a name.)

**Pre-fix (`origin/main` sdk + plugin-pod):**
```
$ charly remove app --purge
Removed volume charly-app-no-1-state
Removed volume charly-app-no-1-storage
Removed volume charly-app-no-2-state
Removed volume charly-app-no-2-storage
Removed volume charly-app-state
Removed volume charly-app-storage
Removed encrypted volume no-1-secrets
Removed encrypted volume no-2-secrets
Removed encrypted volume secrets
$ podman volume ls ... ; ls $CHARLY_ENCRYPTED_STORAGE_PATH
charly-other-state          # ONLY the unrelated deploy survived — siblings destroyed
charly-other-secrets
```

**Post-fix (this PR):**
```
$ charly remove app --purge
Removed volume charly-app-state
Removed volume charly-app-storage
Removed encrypted volume secrets
$ podman volume ls ... ; ls $CHARLY_ENCRYPTED_STORAGE_PATH
charly-app-no-1-state
charly-app-no-1-storage
charly-app-no-2-state
charly-app-no-2-storage
charly-other-state
charly-app-no-1-secrets
charly-app-no-2-secrets
charly-other-secrets
```

Only the base deploy's own volumes/dirs are removed; every sibling and the
unrelated deploy survive.
