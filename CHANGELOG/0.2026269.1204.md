# 0.2026269.1204 — feat(vm-box): parameterize the in-image disk path (VM-box vs containerDisk)

## Summary

`EmitVmBox` hard-coded the disk at `/disk.qcow2`. That is the charly VM-box reader's path,
but it is NOT the KubeVirt containerDisk contract: KubeVirt scans the `/disk` directory for
the disk (default `/disk/disk.img`), which is exactly what a Cua Fleet image carries. As a
result a charly-emitted VM box could not be booted as a containerDisk without a path
override, and vice versa.

Split the emitter:

- **`EmitVmBox(engine, ref, meta, disk)`** — UNCHANGED behaviour, writes the disk at the
  new `VmBoxDiskPath` const (`/disk.qcow2`).
- **`EmitVmBoxAt(engine, ref, meta, disk, inImagePath)`** — the explicit-path form; the
  in-image path is **validated** (see the review-round fixes below), never written raw.

The Containerfile rendering is extracted to a PURE `renderVmBoxContainerfile`, so the
two-path contract is unit-testable with no container engine, and the disk COPY / metadata
LABELs are unchanged.

`ContainerDiskPath` (`/disk/disk.img`) is the shared constant for the KubeVirt / Cua Fleet
caller (plugin-oci / plugin-vm), so the path lives in ONE place.

The constants live **sdk-local** deliberately: the sdk resolves `spec` from the module proxy
at a pinned version, so sdk code must not reference symbols that only exist on an unreleased
spec branch (the `container_disk` arm + `#VmBoxSource.image` land in spec#171 and are
consumed by plugin-vm AFTER both tags).

### Review-round fixes (this head)

1. **T3 (injection) — the in-image COPY destination was written unvalidated/unquoted.**
   A value like `/disk/x\nRUN <cmd>` would inject a second build instruction that `buildah`
   executes, and a space would corrupt the `COPY`. The prefix-only guard is replaced with
   **`validInImagePath`** (container-absolute, charset `[A-Za-z0-9._/+-]`), and
   `TestEmitVmBoxAtRejectsUnsafePath` covers newline / space / tab / quote / semicolon /
   root / empty.
2. **R1/R5 — the `EmitVmBox` doc referenced a non-existent `spec.ContainerDiskPath`.**
   The constant is the sdk-local `deploykit.ContainerDiskPath`; the comment now says so
   (and no longer contradicts the pinned-`spec` rationale).
3. **A3 — the NEW path is now proven live.** `TestEmitVmBoxAtContainerDiskPathLive` emits a
   real image via `EmitVmBoxAt(..., ContainerDiskPath)`, saves it as an OCI layout
   (`podman save --format oci-dir`), and reads the **layer tar's entry names** — proving the
   disk lands at `disk/disk.img` and NOT `disk.qcow2`.
