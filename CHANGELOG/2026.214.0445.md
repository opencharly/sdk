## Why spec/clireflect is a SEPARATE slice from spec/climodel (Rule 2)

`BuildCLIModel` is a SHARED mechanism used by BOTH charly core (the host CLI) AND a command plugin
(`candy/plugin-agent`), so by the fabric-vs-capability decision rule it is a FABRIC PRIMITIVE → it
lives in a `spec/<slice>`, not charly-only (R3 duplication) and not the sdk root (the step-1 gate).
It does NOT go into `spec/climodel` (cuelang-bearing) because two of `spec/climodel`'s consumers
do NOT use kong — merging it there would force `alecthomas/kong` on every `spec/climodel`
consumer, violating Rule 2 (each heavy third-party dep lives ONLY in the slice that needs it). The
new `spec/clireflect` slice (merged in the upstream spec leg) contains kong; consumers that need
only CUE validation (`spec/climodel`) never pull kong, and consumers that need only CLI reflection
never pull cuelang. Go module-graph pruning + package granularity enforce this at build time.
