# 2026.217.0030 — the quadlet asks a capability, not a backend name

Whether a deploy's unit may be enabled at boot is now decided by ONE property: **can this
deploy's encryption passphrase be obtained with no human present.** `deploykit` no longer knows
any backend's name.

## Why the previous two shapes were both wrong

`if backend == "keyring"` hardcoded a name into a kind-blind host — a backend that CAN unlock
unattended would be denied autostart for no reason but not being called `keyring`. Unconditional
`WantedBy=default.target` was the opposite failure: it enabled units whose secret cannot be
obtained at boot, so they fail on every boot, forever. The capability form excludes the nonsense
combination structurally rather than special-casing it, and it fixes the defect underneath: the
old branch conflated *not keyring* with *not resolvable without a human*, so a deploy that HAD a
usable stored passphrase was denied autostart purely on backend identity.

## The decision

| deploy | `[Install]` | `TimeoutStartSec` |
|---|---|---|
| encrypted, unattended-capable | `WantedBy=default.target` | `0` — wait, no deadline |
| encrypted, human-gated | none; needs an explicit `charly start` | `900` |
| no encrypted volumes | `WantedBy=default.target` | `900` |

`ExecStartPre=charly config mount` survives on both encrypted arms — on the human-gated one it is
what produces the actionable error.

## What changed

| File | Change |
|---|---|
| `deploykit/quadlet.go` | `KeyringBackend bool` → `UnattendedUnlock bool`; `emitInstallSection` reads `cfg` again (clearing the `unparam` lint the previous shape introduced); the `TimeoutStartSec` fork is keyed on the capability |
| `deploykit/quadlet_pod.go` | calls `emitInstallSection` instead of carrying a second copy of the decision (R3) — the pod owns the app container's lifecycle, so it must answer identically |
| `deploykit/enc_passphrase.go` | new `EncPassphraseUnattended`; the `!usesWaitingBackend` fast-fail branch deleted; two remediation hints stopped prescribing the removed `secret_backend config` |
| `kit/secret_backend.go` | new — `NormalizeSecretBackend` + `SecretBackendAuto`/`SecretBackendKeyring`, the one place that knows the vocabulary |

`EncPassphraseUnattended` classifies by SOURCE, never by backend name: a value in hand
(`env`/`keyring`/`config`) or `locked` qualifies — `locked` because a Secret Service collection
unlocks when the operator logs in, with no charly command involved, which is precisely the path
`TimeoutStartSec=0` exists to wait for. `default` (stored nowhere) and `unavailable` (backend
unprobeable) do not. It resolves with an EMPTY envVar because `ResolveEncPassphraseForMount` does
so under systemd; consulting an env override here would promise autostart on a value the unit
cannot see.

## Removing the `config` backend

`secret_backend: config` is gone as a selectable value. Rejecting it in the settings validator
alone would not remove it from service — it also arrives from a config file written before the
removal and from `CHARLY_SECRET_BACKEND` — so both readers normalize through
`kit.NormalizeSecretBackend`, which coerces it to `auto` with a one-time notice. Coercion rather
than rejection keeps an already-configured host working: `auto` still reads the config file when
no keyring is present, so nothing becomes unreachable; the operator loses only the ability to PIN
charly to the plaintext store, which is the point.

That guarantee is what lets `ResolveEncPassphraseForMountWithResolver` drop its non-waiting
branch: every value the resolver can now return is one that waits.

**Behaviour change, measured.** A host that pinned `secret_backend: config` and has no
passphrase stored used to fail `charly config mount` immediately via the deleted branch. It now
classifies as `unavailable` and polls to `EncMountDeadline` — **120.09s measured**, then fails
with the same actionable error. Bounded, and already the behaviour of the default `auto` setting
on any keyring-less host; the pin was the only way to opt out of it. Recorded here rather than
smoothed over, because it is the one user-visible regression in this change.

## Coverage

`TestQuadletEncryptedAutostartCapability` asserts BOTH arms for BOTH unit kinds; the two arms
differ only in `UnattendedUnlock`, so each assertion gates that field rather than the fixture.
`TestEncPassphraseUnattended` covers all five sources plus the envVar/namespace the boot path
uses. `TestNormalizeSecretBackend` pins the vocabulary, and a second test states the
never-returns-a-non-waiting-backend invariant at the point `deploykit` relies on it.

Each was mutation-proven red before being cited: always-emit `[Install]` (both human-gated arms
fail), never-emit (both capable arms fail), always-`TimeoutStartSec=0` (the human-gated container
fails), dropping the `locked` clause, and consulting an env override or the wrong credential
namespace. The `unparam` lint gate was proven too, by reproducing the exact
`emitInstallSection - cfg is unused` finding the previous shape shipped.

`TestQuadletWithEncryptedBindMountsNonKeyring` and
`TestResolveEncPassphraseForMount_ExplicitConfigBackend_FailsFast` are deleted: both asserted the
removed branch. The second is worth naming — with the branch gone it would still have PASSED,
because `source=default` is terminal on the waiting path too. A test that survives the deletion of
its own subject is not coverage.

## Consumer

`candy/plugin-deploy-pod` computes the capability and threads it at both `QuadletConfig` sites;
`candy/plugin-settings`, `candy/plugin-doctor`, `candy/plugin-secrets` and `candy/plugin-pod`
carry the rest of the backend removal. That half lands in the charly repository, which picks this
up by gitlink.
