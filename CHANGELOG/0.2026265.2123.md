# 0.2026265.2123 — refactor(loaderkit): fold the materialized-tree cache onto spec/cache.Store

## Summary

Fold `sdk/loaderkit`'s materialized-tree cache onto the ONE shared
`github.com/opencharly/spec/cache.Store` (spec v0.2026265.2108) and delete the
private copy of the cache mechanism. R3: this was the second content-addressed
cache implementation in the tree; it now shares the mechanism the status caches
use.

Deleted from `loaderkit/load_cache.go` (now owned by `spec/cache.Store`):

- the per-file cache directory layout (`<sha256>.json`) and its path helpers;
- the atomic tmp+rename publish;
- the per-key advisory flock + double-check on the miss path;
- the Docker-style prune by entry cap;
- the private `materializedCacheEntry` / `sha256Hex`.

What loaderkit KEEPS — the materialize-specific inputs the shared Store cannot
know:

- `loadedProjectCacheKey` — the components (config-envelope hash + schema CalVer
  + loader identity) → the Store key + the components for the drift check;
- `loaderIdentity` — the sdk-version component that re-keys on a loader-logic
  change (the Phase-3 RCA gate);
- the tree wire codec (`MarshalMaterialized`/`UnmarshalMaterialized`);
- the seam-shaped `MaterializeLoadedProjectCached` face, now driving
  `Store.Fill`.

### Cache-root CHANGE (explicit)

The materialized-tree cache root MOVES from the private
`~/.cache/charly/materialized/` to the shared cache home,
`~/.config/charly/cache/materialized/` (`cache.StoreDir("materialized")`), so
every cache the tree owns sits under ONE directory and `CHARLY_CACHE_DIR`
relocates them together. `CHARLY_MATERIALIZED_CACHE` still overrides the root
outright.

Consequence, stated rather than hidden: pre-existing entries in the old root are
ORPHANED, so every existing user pays a ONE-TIME re-materialize on the next load
(the cache is disposable and self-heals — the correctness contract below is
unchanged). The old directory is not read or deleted; it is simply no longer
consulted, and can be removed with `rm -rf ~/.cache/charly/materialized` once
convenient. This is a cache-location change only: no authored config, no schema,
no wire type.

Contract preserved (unchanged): validity is component-based with NO time expiry;
a same-state load re-materializes exactly once; a config change, schema bump, or
loader-identity change re-keys and re-materializes; a corrupt entry degrades to a
direct materialize; Store-internal failures never fail a load.

The existing cache contract tests all pass against the folded implementation and
FAIL without it:

- `TestMaterializedCache_SameStateMaterializesOnce` — the second same-state load
  performs NO unify (the materializer call-count is the witness).
- `TestMaterializedCache_ValidWhileInputsUnchanged` — a component-matched entry
  is served regardless of age (the Docker rule); ages the entry through
  `Store.PutEntry`.
- `TestMaterializedCache_PruneReclaimsStorage` — the cap reclaims the oldest;
  asserts `Store.Len()`.
- `TestMaterializedCache_CorruptEntryDegradesAndSelfHeals` — seeds corrupt bytes
  at the Store's own filename and asserts re-materialize + self-heal.
- `TestMaterializedCache_KeySensitiveToEnvelope` / `_ConfigChangeReMaterializes` /
  `_LoaderIdentityDriftReKeys` / `_ConnectPassBypassesCache` / `_LoadUnifiedEndToEnd`.
