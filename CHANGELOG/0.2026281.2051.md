# 0.2026281.2051 — fix(loaderkit): name an uninitialized submodule instead of reporting a missing file

## Summary

`loaderkit`'s unified-file walk reports a **missing file** when the real cause is **an uninitialized submodule**. Fixes `opencharly/charly#847`.

A namespaced import whose target is a declared submodule resolves to that directory; the directory *exists* (a gitlink directory always does), so `os.Stat` succeeds, the `IsDir` branch appends `charly.yml`, and the read fails with a bare `ENOENT`. On an older engine the same tree surfaced the identical state as `json: unsupported value: encountered a cycle via map[string]*spec.UnifiedFile`. **Neither reading names the cause**, and both send the reader into the loader.

That is not cosmetic: the umbrella's pre-commit hook calls `charly task …`, and Part II rule 2 makes a session worktree the sanctioned place for umbrella work — so a bare `ENOENT` from the loader **silently blocks every umbrella PR from the sanctioned place**, and R6 forbids the bypass.

The walk now reports the cause it can prove — the directory is **empty** *and* its containing repository **declares it as a submodule path** in `.gitmodules`:

```
submodule "charly" is not initialized: /tmp/wtfix/charly is empty, so
/tmp/wtfix/charly/charly.yml cannot be read; run: git submodule update --init charly (from /tmp/wtfix)
```

**The restraint is the point:** a populated directory, an undeclared empty directory, a non-`NotFound` error and an existing target are all left untouched, so the ordinary not-found path still works for a genuinely wrong ref. A hint that fires on the wrong tree would be worse than the `ENOENT` it replaces.
