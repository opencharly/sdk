# 0.2026242.913 — fix(deploykit): reset to root between overlay candies

## Summary

Fixes opencharly/charly#467 — and the root cause in that issue was **wrong**, so it is restated here from evidence.

The issue said the overlay "must run the root-requiring install steps before the USER 1000 switch". That is not what happens: the overlay assembler already emits `USER root` immediately after the main `FROM` (`plugin-deploy-pod/overlay.go`), and has since that repo was created. The real cause is one candy leaking its user state into the next.

`OCITarget.emitPlan` splices each step's Containerfile fragment **verbatim** — the fragments come from a plugin's build-emit, so the walker never sees inside them. A candy whose fragment legitimately switches to the image user (an inline builder, a user-scoped install) therefore leaves the whole build in that user, and every *later* candy's root work runs unprivileged.

The full-image path never had this bug: `Generator.WriteCandySteps` emits the steps itself, tracks `asUser`, and resets between candies (`if asUser && !skipRootReset`). The overlay walker has to restore the same invariant explicitly, which is what this change does.

**On rootless.** The reset is `USER root` *inside a rootless build* — container UID 0 maps to the invoking user. It is namespaced root, not host root, and is exactly the privilege the full-image build already uses for package installs. Nothing here runs as host root, and the base image's own `USER` is still restored after the last candy by the overlay assembler, so the shipped image is unchanged.

## How tested

**Reproduced deterministically first.** A probe deploy overlaying the failing bed's own candy chain (`layer-agentteams-snapshot` + `pod-virtualization`, which pulls in `charly`) onto a cachyos-based image. The generated Containerfile shows the leak plainly:

```
 63: USER root                    <- the overlay's own reset, after FROM
105: USER 1000                    <- spliced from plugin-example-deploy
121: # Layer: virtualization
123:   pacman-key --init && \     <- still USER 1000
```

Building it reproduces charly#467 exactly:

```
$ podman build -f .build/overlay-rca467-overlay-probe/Containerfile -t rca467-probe:test .
[20/20] STEP  2/17: USER root
[20/20] STEP  8/17: USER 1000
[20/20] STEP  9/17: RUN mkdir -p /tmp/charly-exampledeploy-steps
[20/20] STEP 11/17: RUN --mount=... pacman-key --init && ...
==> ERROR: pacman-key needs to be run as root for this operation.
Error: building at STEP "RUN ... pacman-key --init ..."
build exit=1
```

No reset between steps 8 and 11 — the mechanism, observed rather than argued.

**End-to-end causal proof.** Applying this fix's exact algorithm to that captured Containerfile inserts precisely **one** directive, at the next candy boundary after the user switch:

```
105: USER 1000
109: USER root        <- the only change
122: # Layer: virtualization
124:   pacman-key --init && \
```

Same file, same context, same base image, one directive different:

```
$ podman build -f .../Containerfile.fixed -t rca467-probe:fixed .
build exit=0
'needs to be run as root' occurrences: 0
Successfully tagged localhost/rca467-probe:fixed
```
