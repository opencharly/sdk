# 0.2026271.1129 — fix(loaderkit)!: version-less remote refs resolve to the DEFAULT BRANCH, not the latest tag (supersedes #317)

Supersedes #317 (auto-closed at the validator's 5-BLOCK threshold). All findings from #317's and #318's BLOCK verdicts are fixed in this head.

## Summary

A version-less remote candy ref (`@github.com/owner/repo`, no `:tag` — e.g. the generated corpus ref, or a builder plugin connected by word) means "the current tip of that repo", so it now resolves to the repo's **DEFAULT BRANCH** instead of the newest tag.

**Why:** resolving to the latest tag silently served a **stale build** whenever a repo had newer work on its default branch than on its last tag — and the stale tag's provider **SHADOWED a project's own explicit pin for the same word**. A bed that pinned a plugin to a branch was served the repo's old tagged build instead, so the pinned fix never ran (`opencharly/charly#715`).

The default branch is a **mutable** ref, so it re-resolves per access (`refs.IsMutableRef`) and a stale export refreshes; a repo with no resolvable default branch errors loudly. Resolution goes through a package-level `resolveDefaultBranch` seam (defaulting to the cached `gitClient().DefaultBranch`).

Also drops the now-dead `seams.LatestTag` writer and bumps the `spec` pin to **`v0.2026271.743`** — the tag of the merged **opencharly/spec#184**, which already removed the `RefsCollectSeams.LatestTag` field.
