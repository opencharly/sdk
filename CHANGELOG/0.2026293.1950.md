# 0.2026293.1950 — feat(buildkitdrive): let a build read local OCI layouts via --oci-layout

## Summary

Lets a build read a **local OCI image layout**: `Build.OCILayouts` is rendered as `--oci-layout <id>=<dir>`, so a Containerfile or `FROM` can address `oci-layout://<id>`. Three files change: `buildkitdrive/buildctl.go`, `buildkitdrive/ocilayout.go` and `buildkitdrive/ocilayout_test.go`.

**A correction first, because it changes what this PR is.** I previously recorded — in `sdk#401` and in the body of the merged `sdk#432` — that *"a drive built on `buildctl` cannot resolve an `oci-layout://` source; that scheme is served by the client library through a buildkit session content store, not by the CLI."* **That is false:**

```console
$ buildctl build --help | grep oci-layout
   --oci-layout string [ --oci-layout string ]   Allow build access to the local OCI layout
```

```go
// cmd/buildctl/build.go:280
solveOpt.OCIStores, err = build.ParseOCILayout(clicontext.StringSlice("oci-layout"))
```

So `buildctl` parses the flag into `SolveOpt.OCIStores` **itself**. A drive that shells out needs no session code — only the argument. What was actually missing was one line of argument rendering, not a capability.

**What that means for `sdk#432`:** its code remains useful — `OCILayout`, `ParseOCILayoutSpec`, `Store`/`ContentStores` are the right helpers for a **Go client** that wants to serve layouts itself — but its stated motivation was wrong, and this PR is the fix for the drive's actual path. I would rather say that than let a false premise stand in a merged commit message.

**The change:**

- `Build.OCILayouts []OCILayout` — reusing the `OCILayout` type `#432` introduced rather than a parallel one;
- rendered before the output arg as `--oci-layout <id>=<dir>`, the same `id=path` grammar `ParseOCILayoutSpec` accepts;
- `OCILayout.validate()` extracted so `Store()` and `Args()` share **one** check rather than two that could drift: `local.NewStore` does not validate (it initialises an empty layout on an empty directory), and an **id-less** layout is unaddressable because a solve addresses it as `oci-layout://<id>`.

Three new tests, each able to fail without the change:

- `TestBuildArgsRendersOCILayout` — asserts `--oci-layout src=<dir>` is present **with the right adjacent argument**, not merely that the string appears somewhere;
- `TestBuildArgsRejectsANonLayout` — a bare temp directory must be refused. This holds the standard `bridge.go:129` sets: a layout the solve cannot read should fail at the boundary, not inside a build as a confusing frontend error;
- `TestBuildArgsRejectsALayoutWithoutAnID` — a well-formed layout with no id is unaddressable, so it is refused.
