# 2026.226.1046 — `vmshared.QemuAlive`: one QEMU liveness predicate, hardened

The QEMU liveness probe is hand-rolled per call site in the consumer repo, all
copies answering "is the VM recorded in `<stateDir>/qemu.pid` running?" and none
agreeing on the answer. On `opencharly/charly` **main** there are TWO, both a
bare `Signal(0)` that reports a recycled PID as running: `charly vm list`'s
state scan, and `candy/plugin-preempt`'s holder probe — the arbiter deciding
whether a preemptible GPU-holder VM may be preempted. (`charly vm start` has no
liveness guard at all on main, which is the defect its in-flight consumer PR
fixes; on that branch the count is three.) This adds the single predicate they
all come to share.

`QemuAlive` belongs in `sdk/vmshared` because it has consumers in more than one
module and the module already owns this class — `VmStateRoot` resolves the state
dir it reads, and `RenderQemuArgv` emits the very argv it matches against.

**It also asserts more than any of the three copies did.** A bare `Signal(0)`
probe reports a recycled PID as "running". Narrowing that with a
`/proc/<pid>/cmdline` substring match on `qemu-system` is still not enough: a
PID reused by a DIFFERENT VM's qemu satisfies it. The consequences are real in
both directions — `vm start` would treat a stopped VM as running and no-op
instead of starting it, and the preempt arbiter would treat a departed holder
as live and refuse to reclaim its GPU.

`QemuAlive` therefore matches `-pidfile <stateDir>/qemu.pid` as ADJACENT
NUL-separated argv fields, so a live process is confirmed to be the qemu
started for THAT state dir. The comparison is whole-field rather than
substring, so a longer path sharing the same prefix does not match.
`qemu_liveness_test.go` tables the discriminating cases, including the
recycled-onto-another-VM case the substring check accepted and the prefix case
a naive `Contains` would accept.

That second check rests on a CALLER invariant, not a renderer guarantee, and
the comment says so: `RenderQemuArgv` appends `-pidfile` CONDITIONALLY
(`if paths.PidFile != ""`), so an empty `PidFile` is permitted there. What
makes the argv reliable is that every production launch sets it to
`<vmStateDir>/qemu.pid`. A future caller leaving it empty would make
`QemuAlive` report those VMs DEAD — the worse direction, since callers act on
"not running" by starting a second qemu — so the invariant is documented where
that maintainer will read it.

The resolution step is shared too: `qemuProcFromStateDir` now owns the
read-parse-find sequence for the package, and `KillQemuByPID` routes through
it. That sequence was previously hand-rolled in both places, putting the
`"qemu.pid"` literal and the same three error guards in two spots inside one
package — a fresh R3 violation in the very module doing the unifying, which
this avoids rather than ships.

Change class: sdk Go (additive library). Gates across the whole module:
`gofmt -l .` empty, `go build ./...` clean, `go vet` clean,
`go test -count=1 ./...` green (10 packages), `golangci-lint run ./...`
0 issues.

Invoked live against a real charly-managed direct-qemu VM — no consumer needed,
since the predicate takes only a state-dir path. A `check-debian-debootstrap-vm`
VM was created (`charly vm create`, backend QEMU), its argv confirmed to carry
`-pidfile /home/…/charly-debian-debootstrap/qemu.pid` (the caller invariant
above, observed in production rather than assumed), and the predicate invoked
against that dir:

```
QemuAlive(".../charly-debian-debootstrap") = true    [VM running]
QemuAlive(".../charly-debian-debootstrap") = false   [after charly vm stop]
```

Both directions, on the real state dir, with the pidfile still on disk after
the stop — which is exactly the stale-pidfile case a naive existence check gets
wrong. The fresh-rebuild R10 still belongs to the consumer PR.
