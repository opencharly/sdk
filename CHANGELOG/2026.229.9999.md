# 2026.229.9999 — TransferImageToVenue: verified image delivery, venue-generic

<!-- PLACEHOLDER CalVer: the pr-validator regenerates this stamp at merge. -->

## Why

Delivering a locally-built image into a venue's own container store is the same problem at
every venue, but the verified-transfer logic lived only in the VM path
(`charly vm cp-box`). The new container-venue verb `charly box load` needed all of it, and
copying it would have been the second home for logic that is subtle enough to be worth
exactly one.

## What landed

`deploykit.TransferImageToVenue` + `deploykit.ImageVenue` — the venue-generic verified
delivery path, lifted out of plugin-vm:

- the idempotency skip that fires only when the venue holds the ref AND that image is
  VERIFIED intact, so a present-but-torn image is not wrongly skipped;
- the torn-overlay integrity probe, which counts ONLY the `storage/overlay` signature as
  corruption — any other failure means the overlay mounted fine, so it is an integrity
  check and not an entrypoint test;
- the drop-and-re-stream-once recovery, with a second failure a hard error rather than a
  broken image shipped silently;
- the post-load tag, issued through the SAME podman prefix the load used, so the two can
  never disagree about which store they addressed.

A venue supplies two things: `PodmanCmd`, the in-venue invocation prefix that is the one
place a storage scope is decided, and `NewLoadCmd`, the host-side process that consumes
the save stream. `kit.TransferToRootful` moves onto `container.StreamLoad` in the same
change.

## Proof

Exercised live by the superproject's `check-boxload-pod` bed (the container binding) and
`check-agentteams-vm` (the VM binding, via `charly vm cp-box`).
