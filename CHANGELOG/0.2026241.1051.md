# 0.2026241.1051 — feat(kit): strict ledger enumeration that reports a malformed charly.yml

## Summary

`readLedger` deliberately swallows a read/parse failure and yields an empty ledger. That is the right contract for callers which treat *"no ledger yet"* and *"unreadable ledger"* alike — and `ListDeployIDs` / `ListCandyNames` inherit it. It is the **wrong** contract for a user-facing command, which then prints "nothing deployed" for a file it simply could not parse.

This adds the error-reporting twin:

```go
func ListDeployIDsStrict(paths *LedgerPaths) ([]string, error)
func ListCandyNamesStrict(paths *LedgerPaths) ([]string, error)
```

An **absent** file is still not an error — nothing has been deployed on this host. Only an unreadable or unparseable one is, and the message names the path and the cause (`parse ledger <path>: …`).

## Why this exists — found by getting it wrong

While migrating `plugin-substrate` onto the non-strict listers (opencharly/plugin-substrate#4) I claimed the substitution was "behaviour-preserving by construction". It was not, and the review caught it. The old consumer code propagated a wrapped error from the candy path:

```go
candyNames, err := ledgerCandyNames(paths)
if err != nil {
    return spec.SubstrateStatusReply{}, fmt.Errorf("local ledger candies: %w", err)
}
```

Moving that to `kit.ListCandyNames` would have **silently dropped the error path** — a malformed `charly.yml` reported as "no candies" instead of as a parse failure. That is the same silent-wrong-answer shape the ledger relocation already produced once (`os.Stat("")` → ENOENT → zero rows with a nil error), so accepting it would have been a regression I had spent the day arguing against.

The consumer's error handling was also already **asymmetric** on `main` — the deploys path swallowed its error (`return reply, nil`) while the candies path propagated it. Rather than preserve that asymmetry, keep a second YAML parser per consumer, or quietly drop the loud half, give `kit` the contract the consumer actually needs so both paths can be uniformly loud.

## Rulebook compliance

- **R1** — the defect was root-caused (a swallowed error path in a substitution I made) rather than papered over; the fix is at the contract, not at the call site.
- **R2** — no parking: the consumer that needs this is open at plugin-substrate#4 and is updated in the same wave.
- **R3** — one canonical enumeration; the strict variants share `readLedgerStrict` rather than duplicating the parse, and consumers no longer need a private YAML parser to get an error.
- **R5** — purely additive; the existing non-strict listers keep their documented best-effort contract, which other callers legitimately rely on.
- **R6** — no force-push, no direct push to `main`, no hook bypass.
