# 2026.230.1102 — three deploykit fixes: unless_exists, the packaging child's project scope, and system-enable attribution

The first two consume contracts that land first in `opencharly/spec`; the third is a defect the
other two surfaced by finally letting a build get far enough to hit it.

## `EmitDownload` honors `unless_exists`

Consumes the `unless_exists` field added to `#Op` in the spec contract repo.

When set, the emitted RUN wraps the WHOLE step — fetch, extract AND chmod — in a
build-time existence test:

```sh
if [ -e '/usr/bin/ollama' ]; then echo "skipping download: /usr/bin/ollama already present";
else { ...fetch + extract... }; fi
```

Wrapping all three matters. Guarding only the fetch would still pay the extract, and a
`chmod` left outside the guard fails on a path that was never created.

Absent, the emission is byte-identical to before, so no existing candy changes.

Proven in both directions on real builds of the consuming superproject: on Fedora (no
ollama package) the step executes and fetches; on CachyOS (packaged `ollama`) it emits the
skip line and performs no fetch at all.

## The packaging child runs under the candy's own project scope

`generateLocalPkg` spawns a `charly generate-packages` child to build the in-development
package for a `localpkg:` candy. It inherited the PARENT's project scope, which is about the
BOX being built — and when that box lives in a `box/<distro>` submodule, the submodule
vendors no candies and declares no `generate-packages` command plugin. The child therefore
resolved the wrong project and the verb did not exist there, so `--dev-local-pkg` died
roughly 14 seconds into every submodule build. Seven boxes were affected.

Three things had to be true at once, and each is now explicit:

- **The child's scope is the project that OWNS the candy**, resolved by walking up from the
  candy's `charly.yml` (`candyProjectDir`), not the parent's scope.
- **Every path handed across the process boundary is absolute** (`absFromHere`). The child
  chdirs into its own project, so a path still relative at the boundary would resolve against
  the child's directory rather than ours.
- **Both project-scope environment variables move together.** They are mutually exclusive in
  the CLI, so stripping one and leaving the other makes the child exit on
  `--repo and --dir are mutually exclusive` instead of running.

That last invariant is not local to this package, so it does not live here: it ships as
`spec.ChildProjectEnv` in the contract module (opencharly/spec#38), and this package calls it.
An earlier revision of this branch had a private `charlyChildEnv` doing the same work; review
found a third copy of the same filter in `candy/plugin-mcp`, which is exactly the drift the
contract module exists to prevent. All three call sites now share one implementation, and the
helper's unit tests live with the helper — including the lookalike-name case this package's
deleted test was the only thing covering.

## `system_enable_template` renders for the RESOLVED init, not every ACTIVE one

`EmitInitAssembly` looped over every ACTIVE init system and rendered each one's
`system_enable_template` against the same list of `use_packaged:` units. But a
`use_packaged:` entry names a unit the DISTRO ships, so exactly one init can own it.

An image whose resolved init is supervisord while openrc is merely active — any candy
contributing openrc fragments, or relay ports while openrc declares a `relay_template` —
therefore emitted

```
RUN rc-update add virtqemud.socket default && rc-update add virtnetworkd.socket default
```

into a container with no OpenRC installed, and the build died at `rc-update: command not
found` twenty lines above its own `LABEL ai.opencharly.init="supervisord"`. Because
`candy/charly` requires `virtualization`, that made EVERY image composing the charly
toolchain on an Arch/CachyOS base unbuildable: `check-charly-selftest-pod`,
`check-githubrunner-pod` and `check-openclaw-desktop-pod` were all red.

The other active inits are not skipped as a special case. They are active because they
contribute FRAGMENTS and relay wiring, and neither has anything to do with enabling a
distro-shipped system unit; their `assembly_template` and `post_assembly_template` still
render exactly as before. An init with no `system_enable_template` at all (supervisord)
still renders nothing there — its mixed-entry `exec:` sibling is how that daemon runs under
supervision, which is the whole point of the mixed-entry model.

Reported with its RCA as opencharly/charly#320 before this fix existed; the report's two
candidate designs were "attribute each unit to its owning init" and "restrict rendering to
the resolved init". The second is the one that matches the model already in the tree: the
resolved init is what the image labels itself with and what `charly service` drives at
runtime, so it is the init that can meaningfully enable anything.
