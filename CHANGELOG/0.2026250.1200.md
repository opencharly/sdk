# 0.2026250.1200 — fix(deploy): packaged service overrides materialize as a systemd drop-in

## Summary

The deploy compiler dropped a `use_packaged` service entry's `overrides:` block: `CompileServiceSteps` emitted the `ServicePackagedStep` without populating `OverridesText`/`OverridesPath` — so a candy-declared runtime override (e.g. `overrides.exec: "/usr/bin/charly mcp serve --listen 0.0.0.0:18765"`) was silently inert on a packaged unit. The spec fields + the executor path (`walkServicePackaged`: write drop-in → daemon-reload → enable --now) both existed; only the compiler never populated them. The R10 bed (check-cachyos-mcp-vm) proved the gap: the MCP server shipped with the packaged unit (127.0.0.1 bind), the drop-in never landed, and the forwarded-port checks reset on the first POST.

The fix renders the drop-in through the SAME init-provider seam the custom-exec path uses (R3): entry.Overrides != nil + systemd target → the seam's OpResolve emits `DropinText`/`DropinPath` (the spec's `BuildServiceRenderContext` precomputes `PackagedUnit`+`RenderDropin`; the executor was already complete). The shipped unit stays untouched; the runtime override binds the server as declared.
