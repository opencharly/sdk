### Defect 1 is refused, and the message names the replacement

The old message was `reference $report.* names a step that is not declared earlier`, which
sends the author looking for a step to declare. There is no such step, and there is nothing
left to restore. The populator that once made an entity knob readable from a step was one
line in the plugin's retired executor; the cutover deleted that file and kept the readers.
The counts below are the whole measurement (counts only — the paths are in another repo this
PR does not touch):

```

$ git -C plugin-pipeline grep -n 'raw\["report"\]' HEAD -- '*.go' | wc -l

So at HEAD every surviving `rc.report` reference — one helper call and three direct reads —
reads a map nothing assigns: it is nil, and a reference that got past the gate would render
the LITERAL TEXT (the generate verb's arm leaves its template as the authored string when
the lookup misses) rather than a value.
The reshape does duplicate the knob block into each lifted verb body, and no verb body reads
that key (0, above). Widening the grammar to accept `$<knob>.<field>` would therefore be a
half-restore with no value source — a run-time emptiness in place of a load error, which is
the worse trade.

The gate now refuses it with a message that names the replacement. Both retired namespaces —
a `config:` knob, and the retired entity-env spelling whose value would have to be spliced
into the expression as text — are answered by the gate itself:

```

The classifier is keyed on the DOCUMENT (the `config:` keys of `spec.Pipeline.Config`, whose
own CUE comment names the former knobs `llm/media/report/skills/channels/gates/repo/redo/agent`),
never on a hard-coded list, and all five earlier-step call sites share one helper
(`checkRefNames`), so the misleading step message cannot survive at `stdin:`/`for_each:`/
`lanes:`/`plan:` either.

**What `eval-omarchy` must do instead — a documented hand-fix, not a promise.** Its two knob
references are `eval-omarchy/charly.yml:1673` (`template: "$report.bed_template"`) and `:1899`
(`report: "$report.template"`). Both are string fields whose value the author already holds
in the entity, so the fix is to author that value at the point of use. The consumer's third
item, the `eval-pr` pin at the retired `plugin-pipeline:v2026.272.0332`, is that repo's own
change and is untouched here.

### Defect 2 is restored

`${env.NAME}` is not an invented spelling: the org's own migration emits exactly this form
for the retired `$env.NAME` (`plugin-migrate`'s documented ref rewrite — "the ref must be
brace form to expand"), so the producer's output could not load against the target grammar.
`expr` cannot parse the brace form at all, so the measured failure is a PARSE error rather
than a grammar rejection:

The restore has three parts, and each is pinned:

- `rewriteEnvRefs` turns `${env.NAME}` into an `env("NAME")` call before the patcher runs,
  because the brace form never reaches the parser otherwise;
- the patcher admits `env` as a second CALL name beside `ref`, and refuses any other arity
  (`env()` names nothing, and a load-time refusal beats a run-time one);
- `Eval` resolves it from the PROCESS environment — the same source the retired form read,
  whose surviving `envMap()` in the retired executor's package is built from `os.Environ()`.

The value comes back as the lobster LITERAL the retired text substitution would have put in
its place (`true`/`false`/`null`, a number, else the string), because that is what makes the
consumer's guard mean what its author wrote: `when: '!(${env.EVAL_PUBLISH} != true)'` must
RUN when the variable is `true`. A raw-string lookup would compare `"true" != true` — always
true — and the stage would be skipped forever.

The widen is ONE named call, not a namespace: `env.NAME` (a bare member access) is still
refused, as is every other call, so the grammar's refusal set is unchanged except for the one
form the migration emits. An unset variable reads as empty, `os.Getenv`'s own contract.
