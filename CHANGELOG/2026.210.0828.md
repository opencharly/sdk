# 2026.210.0828 — Consume the loader-RESULT types from spec (#55 Phase B, Cutover 1)

The consumer leg (sdk half) of #55 Phase B Cutover 1: the cleanly wire-shaped
loader-result type family MOVED to the types-only `spec` module (see
`spec/CHANGELOG/2026.210.0700.md`). This repo deletes those definitions and
repoints every use to `spec.X`.

Deleted (moved to `github.com/opencharly/spec/spec`):

- `sdk/loaderkit/unified_file.go` (whole file) — `UnifiedFile` + `InlineCandy` +
  `DecodeInlineCandy`/`EncodeInlineCandy` + `ResolvePluginKindViaPlugin`/
  `DecodePluginKindMap` + all uf projection methods.
- `sdk/loaderkit/templates_project.go` (whole file) — the `ProjectTemplates`
  free function + `fillNamespacedTemplates`; now the `spec.UnifiedFile`
  `.ProjectTemplates()` METHOD (`resolve_project.go`'s one caller updated).
- `sdk/loaderkit/resolve_opts.go` — the `ValidationError` accumulator (the file's
  `ResolveOpts` STAYS, see below).
- `sdk/loaderkit/candy_version.go` — the `CandyCandidate` type (the
  `PickCandyVersion` arbiter STAYS; it needs kit's semver/CalVer comparison).
- `sdk/kit/loader_directives.go` — `ImportEntry`/`ImportList`/`DiscoverConfig`/
  `ScanSpec` (the file keeps only `AnchorScanSpecs`, retargeted onto
  `spec.ScanSpec`).
- `sdk/kit/migrate_support.go` — the `UnifiedFileName` const (moved to
  `spec.UnifiedFileName`; `DefaultBoxDir`/`DefaultCandyDir` stay).
- `sdk/deploykit/provides.go` — `EnvProvideEntry` + `ProvidesConfig` (the provides
  PIPELINE — FilterOwnProvides/PodAwareEnvProvides/ResolveTemplate/… — stays,
  consuming the spec types).

Added:

- `sdk/deploykit/project_bundle.go` — `deploykit.ProjectBundleConfig(uf
  *spec.UnifiedFile) *BundleConfig`, the ONE loader-result projection that could
  NOT travel to spec (it returns a `*deploykit.BundleConfig`, and spec must never
  import a mechanism kit). Was the `uf.ProjectBundleConfig()` method; every caller
  becomes `deploykit.ProjectBundleConfig(uf)`.

**ResolveOpts stays in loaderkit — a follow-on, not residue.** `ResolveOpts`
embeds `*buildkit.{InitConfig,DistroConfig,BuilderConfig}` — buildkit MECHANISM
config (ResolveDistro/ExpandPackageInheritance/ResolveInitSystem; InitConfig even
imports `sdk/kit`), which the types-only spec module can never import (a
spec←buildkit cycle). So `ResolveOpts` is correctly-placed loader mechanism, not
a wire type. It exits loaderkit ONLY if it is later redesigned to carry
spec-level RESULT types instead of `*buildkit` config — a separate design cutover
in the buildkit/mechanism-seam track, NOT this one. (A prior RDD spike's recipe
missed this second entanglement; the bed-vs-doc rule found it.)

Verified in the assembled workspace: `go build/vet/test ./...` green; `gofmt -l`
clean on the touched files.
