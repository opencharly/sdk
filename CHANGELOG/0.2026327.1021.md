# 0.2026327.1021 — fix(buildkitdrive): remove a build's OCI export on every exit path

## Summary

`charly box build` (and the VM-box emitter) stage each image as an OCI archive under the builder's
state root, bridge it into the run engine, and remove it. The removal ran **only after a successful
bridge**, so every failure path — the build itself, `annotateExport`, the store ingest, the engine
load, or a cancellation — left a partial or 0-byte archive behind under a name no later build
reuses. On a host with a build history that grows without bound (opencharly/plugin-build#64: 71
archives, 68 GiB) the export eventually fails on a full disk under a path nobody recognises as a
leak.

This change gives the archive ONE lifecycle rule in ONE place and wires the SDK side to it:

- **`buildkitdrive.RemoveExport(dest)`** (new, `buildkitdrive/export.go`) — removes the archive
  whatever the outcome; a missing file is a no-op (a build can fail before the exporter opens it),
  and a real removal error is reported by path. It is a plain removal rather than a "cleanup func"
  so a caller can JOIN its error onto the build's own: the cleanup must never replace the reason a
  build failed (the ENOSPC case is exactly where both exist).
- **`deploykit/vm_box_emit.go`** — the VM-box emitter installs the cleanup with a `defer` the
  moment the destination is known, and drops its remove-only-on-success block.
- The bridge switches from `container.EngineBinary` to **`kit.EngineBinary`**, the accessor the
  rest of `deploykit` already uses (one accessor, and it is a var, which makes the failure path
  testable).
- **`plugin-build`'s build drive will call the same helper** (its own PR, after this one lands and
  is tagged, since it consumes the SDK through a pinned module version).

No DESIGN shape is touched: the archive's location still comes from `StageDir`/`ExportFile`
(D-STORE-1's one resolver), and the rule is behavioural only.
