# 0.2026265.2104 — fix(loaderkit): the per-host deploy overlay is not a config-stack layer

## Summary of changes

The layered config stack (`loaderkit/config_stack.go`) raw-merged the **per-host deploy overlay** (`~/.config/charly/charly.yml`, `spec.DefaultDeployConfigPath`) as a PROJECT document layer. That overlay is a `DeployConfig` — per-host RUNTIME STATE (deploy entries + cache/ledger/system), not an authored project. Raw-merging its `deploy` entries into the authored deploy map **before `FoldMembers` runs** injects top-level keys that duplicate the project's nested members, and `FoldMembers` then hard-fails:

```
peer name "preempt-holder" (declared under deploy "check-preempt-live-pod")
collides with an existing deploy/bed/peer entry — peer names must be globally unique
```

This breaks **every member-bearing check bed** (`check-preempt-live-pod`, `check-cross-pod-cdp`, …), which fail at `steps=1` on the first member build.

The overlay has ALWAYS had its own correct application path: a per-field MERGE onto the loaded project tree (`deploykit.MergeDeployConfigs` → `deploy.MergeDeployNode`, driven by `loaderkit.ResolveMergedTreeViaExecutor` and `deploykit.MergedDeployTree`), whose lookup (`deploykit.FindDeployNode`) recurses into a node's `Member` tree — so it can never create a stray top-level key.

Concrete edits:
- `loaderkit/config_stack.go` — the stack is now **system → in-dir** (projects only). `readConfigStack` no longer reads `spec.DefaultDeployConfigPath()`. File + function headers document why the overlay is not a layer and name its ONE application path.
- `loaderkit/load_unified.go` — the config-stack comment corrected (system → in-dir).
- `loaderkit/config_stack_test.go` — tests updated to the two-layer stack; new `TestConfigStack_DeployOverlayIsNotALayer` is the R1 regression (a project bed root with a NESTED member + an overlay that persists the same member TOP-LEVEL; asserts the overlay does NOT leak into the merged project doc). `TestConfigStack_UserWinsOverSystem` → `TestConfigStack_SystemLayerFormsProject` (the packaged `/etc/charly` fallback, the feature #230 actually added).
- `loaderkit/test_main_test.go` — comment corrected; `CHARLY_DEPLOY_CONFIG` still isolated (the per-field merge path must not pick up the operator's real overlay).
