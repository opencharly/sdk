# 0.2026288.2236 — feat(storekit): the reclaim surface — an entry delete and a blob sweep

## Summary

`storekit` could WRITE a store but could not RECLAIM one. This adds the reclaim surface, **six exported symbols** — five functions and one type — all named here because A1 asks a body to account for every item in its diff:

| the export | what it is |
|---|---|
| `ReachableBlobs()` | the reference set — every digest an entry reaches, directly or through a tree manifest |
| `UnreferencedBlobs()` | what no entry reaches, with per-blob sizes — **read-only**, and the sweep's discovery half |
| **`UnreferencedBlob`** *(type)* | **one candidate as the caller receives it: the `Digest` and the `Size` its removal would free** — *the type the listing returns, so a caller never unpacks an anonymous pair* |
| `RemoveBlob(dgst)` | one caller-chosen removal, **refusing a digest an entry still reaches** |
| `DeleteEntry(key)` | drop an index pointer, under the same index lock `indexEntry` uses |
| `BlobBytes(blobs)` | the sum of a candidate list's sizes — the report line's arithmetic, so a caller does not re-derive it |

*The four functions are the surface; the type is what they hand back, and `BlobBytes` exists because a sweep reports bytes and an unreported total is a number each caller would compute differently.*

**Why it matters, in the package's own words.** `PutEntry` states its contract plainly: *"a later PutEntry with the same key REPLACES the index pointer; the previous payload stays in the store as the content-addressed blob it is (immutable, and still reachable by digest)."* So every re-put leaks bytes, and nothing here could name them. Measured on this host by the existing consumer: `charly clean --cache` reclaims **5 664 unreferenced blobs (~106 MiB)** from `spec/cache` stores, and has no equivalent to call on a `storekit` one. `opencharly/plugin-clean#14` is blocked on exactly that absence.

**The split is copied, not invented.** `OrphanedLayouts`' own doc states the contract this keeps: *"Discovery and sizing only — never deletion. Removing is the caller's, so that a sweep's destructive half stays with the surface that also reports it (`--dry-run` first, then the removal)."* Every walk here is read-only; the two removals are separate calls the caller makes deliberately.

**The one thing a first draft gets wrong, and the test that caught it.** A blob is reachable by three routes:

```
index descriptor .Digest  ->  the entry MANIFEST blob
entry.Payload             ->  one payload blob
entry.Tree                ->  the tree's MANIFEST blob -> TreeEntry.Files[*].Digest -> many blobs
```

*The third level is transitive, and the first route is invisible from `Entry` — the pointer lives in `index.json`, one level up.* A sweep reading only `Entries()` therefore calls every entry manifest unreferenced and deletes the store's own descriptors. **My first draft did exactly that**, and the test failed naming a **142-byte** blob where an **11-byte** payload was expected. It is now a named route with the reasoning in the doc comment.

**And a re-put orphans TWO blobs, not one** — the superseded payload *and* the superseded manifest — so the tests assert membership by identity rather than a count that would hide it.

`DeleteEntry` takes the **same index lock** `indexEntry` uses, so a delete racing a put cannot lose the other's write; it drops the pointer only, because freeing a payload is a reachability decision, not a delete.
