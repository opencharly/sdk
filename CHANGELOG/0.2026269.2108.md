# 0.2026269.2108 — fix(deploykit,packagekit): match a pinned package by bare name; parse a real candy charly.yml

## Summary

Fix two sdk defects exposed by pinning an exact version in a candy's
`distro: <d>. package:` list (`name=version` on pac/apt/apk,
`name-<version>-<rel>` on rpm) — the mechanism opencharly/layer-charly#10 adds so
an upstream package rebuild invalidates exactly the install layer.

**1. `deploykit.distroRepoProvidesPackage` matched a pinned entry by exact string.**
It compared the bare `packaging.name` (`charly`) against the package list with
`slices.Contains`. A pinned entry (`charly=2026.268.1917`) no longer matched, so
the localpkg-skip did not fire and the emitter produced a **redundant, UNPINNED
second install** — defeating the pin it was meant to enforce. Measured on the
`githubrunner` box: without the pin, ONE install line; with the pin, TWO
(`pacman -Syu --needed charly=2026.268.1917` + a `pacman -U …/charly-${ARCH}.pkg.tar.zst`
that pulls the latest). Match on the bare name via the ONE canonical strip
(`buildkit.PkgName`, R3) — the same helper the `{{pkgName .}}` render func uses.

**2. `packagekit.ParsePackaging` could not parse a real candy `charly.yml`.**
It decoded the whole document into a `map[string]struct{…}`; a real candy file
carries a top-level `version: <calver>` SCALAR, which fails that decode before
ever reaching the `candy:` body — so `charly generate-packages` errored on every
real candy. Its own test fixture hid this by nesting `version:` inside `candy:`.
Walk a `yaml.Node` so a top-level scalar is tolerated.

Both changes ship a unit test that FAILS without the fix; no exported API changes
beyond adding `buildkit.PkgName` (whose `TemplateFuncs["pkgName"]` behavior is
byte-identical). Five files total, all named above.
