### Why the table entry is a RETARGET, not a deletion

It is not cosmetic. `sharedCueSchema()` fail-fasts on any entry whose def is absent, so with the contract's deletion linked, the loader does not warn — it **panics at init**:

```console
panic: loaderkit: CUE kind "pod": definition #Pod not found: field not found: #Pod
  github.com/opencharly/sdk/loaderkit.init.func3(.../sdk/loaderkit/cue_schema.go:85)
  ... loaderkit.ValidateNodeDocCUE → plugin-loader.ValidateNodeDocCUE → ParseDocStream
```

and the same table feeds `loaderkit/declared_fields_floor.go` — the process-lifecycle-independent field-name set the parse consults when the served-schema channel is empty. That file's header records the live repro it exists to prevent (*distro-arch `check-agent-live`'s pod body, an `iterate:` key carrying an `agent:` kind-word key, failing `charly deploy add` with `expected a mapping value`* — **sdk#221/#223/#225**), and `TestContractDeclaredFields_Floor` pins `pod` as a NON-empty floor. **Dropping the entry re-arms exactly that bug, and this repo's own gate forbids it** — the plant below turns that test red.

So the entry names `#ResolvedPod`: the resolve-to-envelope form the contract keeps for the kind (and the reason the contract keeps `#PodSidecar`), whose field set is the authored body's plus the resolved-only `raw`. Two consequences are deliberate and written beside the table instead of being discovered later:

- the floor for `pod` gains `raw` — a field no correct document authors, and one the pod VALUE gate still rejects as `field not allowed`, so the extra name cannot admit a document;
- `env_default`'s type differs between the authored `#StrVal` and the envelope's `string`, which would matter only to a CONCRETE unify — `ValidateEntityClosedCUE("pod", …)` / `ApplyCueDefaults("pod")` — and **no caller in the tree passes `"pod"` to either**:

```console
$ grep -rn 'ValidateEntityClosedCUE("pod"\|ValidateEntityCUE("pod"\|ApplyCueDefaults("pod"' --include='*.go' .
./loaderkit/cue_schema.go:70:// to a CONCRETE unify, i.e. `ValidateEntityClosedCUE("pod", …)` / `ApplyCueDefaults("pod")`,
```

One hit, and it is the comment in this diff that NAMES the two functions — there is no call site: the only `"pod"` argument any of them receives anywhere in the tree is that sentence.
