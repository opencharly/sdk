# 0.2026328.1554 — fix(deploykit): refuse to persist a degraded per-host config load

## Summary

Closes the fixable half of opencharly/charly#1269. `SaveDeployConfig` now REFUSES to persist a
**degraded load**.

The per-host config's loader can fail OPEN: a deploy entry it cannot unify comes back as an empty or
short `DeployConfig` with no error. A writer that then saves its own `dc` erases every entry the
loader dropped. Measured on a host, 2026-11-24: `~/.config/charly/charly.yml` lost BOTH of its
deploy entries (and `system:`) in one run while the containers kept running — the overlay, which is
the source of truth for `charly config`/`status`, no longer knew about them.

The guard lives inside the same locked mutation as the existing fail-safe re-read, and compares the
**typed re-read** with the **file's own deploy-key count**:

```go
onDisk, lerr := recheck()
if lerr != nil { /* existing fail-safe refusal */ }
if onDisk != nil {
    if onFile := countDeployKeys(root); len(onDisk.Deploy) < onFile {
        return false, fmt.Errorf("refusing to write %s — it holds %d deploy entr(y|ies) but only
            %d load; this binary would erase the %d a degraded load dropped …", …)
    }
}
```

Why that comparison and not "dc is smaller than the file": a **deliberate removal** is exactly a
smaller `dc` — the caller read the same file, so the re-read and the file agree, and only `dc`
shrank. A degraded load is the case where the re-read CANNOT account for the file. `countDeployKeys`
uses `reservedDeployKeys`, the same basis `removeDeployKeys` uses, so the guard and the writer can
never disagree about what a deploy key is.

Behaviour change, deliberate and named: a writer running against a config this binary cannot fully
load now fails with an actionable message instead of silently rewriting it.
