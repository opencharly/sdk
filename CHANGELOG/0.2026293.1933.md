# 0.2026293.1933 — feat(buildkitdrive): import an OCI layout as a containerd content store (supersedes #431)

## Summary

Makes an OCI image layout importable from `sdk`, which is the half of the BuildKit leg that was missing.

**The problem, precisely.** A drive built on `buildctl` can **export** an image and cannot **import** one. `oci-layout://` is served by the client library through a buildkit session content store, not by any CLI flag — so with the exporter deleting its OCI export after `LoadExport`, a dependent solve has nothing to read.

**What this adds** (`buildkitdrive/ocilayout.go`, four exported declarations plus the `Store` method):

- `OCILayout{ID, Dir}` — one named layout, addressed by a solve as `oci-layout://<ID>`;
- `ParseOCILayoutSpec("id=/path/to/layout")` — the same form buildctl's `--oci-layout` takes, so a drive can pass the string it would have passed on the command line;
- `Store()` / `ContentStores(...)` — the layout opened as a `content.Store`, and the id→store map a buildkit session serves. Duplicate ids are an error, not a silent last-wins;
- `OcilayoutSpecError` — the typed error for a malformed specification or a directory that is not a layout, so a caller can distinguish "wrong path" from "store failed to open". My first revision of this body omitted it and said "3 exported symbols".

**One deliberate divergence from the reference.** buildkit's own parser (`cmd/buildkit/build/ocilayout.go`) calls `local.NewStore` directly. `local.NewStore` **does not validate**: pointed at an empty directory it initialises a fresh, empty layout. A typo'd path would therefore produce a solve that reads no content and reports no error. `Store()` checks for `storekit.LayoutFile` (`oci-layout`) and `index.json` first, so a wrong path fails at the boundary rather than inside a build.

## How tested

```console
$ go build ./...
build rc=0
$ go test ./buildkitdrive/ -run 'OCILayout|Store|ContentStores'
ok  github.com/opencharly/sdk/buildkitdrive  0.019s
```

Four tests, and the two that matter are structural rather than tautological:

- `TestStoreOpensARealLayout` writes the skeleton of an OCI layout (`oci-layout` marker, `index.json`, an empty `blobs/sha256/`) and opens it. It asserts only that opening succeeds — it does **not** assert rejection of a malformed layout, because `local.NewStore` would accept one. That guarantee is `Store()`'s own and is covered by the next test. My first revision of this body (and of the test's own doc comment) overstated it;
- `TestStoreRejectsANonLayout` passes a temp directory that is not a layout and **requires an error**. It failed on the first run, which is what surfaced the `local.NewStore` silent-initialise behaviour above; the validation in `Store()` exists because that test demanded it.

`TestParseOCILayoutSpec` and `TestContentStoresRejectsDuplicateIDs` cover the spec grammar (`""`, `"noequals"`, `"=dir"`, `"id="` all rejected) and duplicate-id refusal.
