# 0.2026250.650 — feat(packagekit+loaderkit): systemd units + /etc/charly config in native packages; layered config stack

## Summary

Two coupled changes from the systemd-units + /etc/charly config plan (plan/charly-mcp-systemd-config.md, §3.3 renderer + §3.5 layered config stack), consuming the spec v0.2026250.632 Packaging schema (PR #113's tag):

1. **packagekit renderer (§3.3)** — new packagekit/systemd.go + config.go, wired into BuildInfo (packagekit/nfpm_config.go), shipping in the deb/rpm/archlinux packages ONLY (apk/ipk/msix have no systemd — skipped):
   - /usr/lib/systemd/system/charly-mcp.service + /usr/lib/systemd/user/charly-mcp.service — rendered from packaging.systemd (Description/After/Wants/WorkingDirectory/ExecStart/Restart + [Install] WantedBy=multi-user.target / default.target). The NON-AUTOSTARTING contract: units are INSTALLED but never ENABLED (no post-install enable script); the preset files /usr/lib/systemd/{system,user}-preset/50-charly.preset (disable charly-mcp.service) guarantee a distro that runs systemctl preset on install (Debian's dh_installsystemd) cannot auto-enable them.
   - /etc/charly/charly.yml — rendered from packaging.config to a minimal valid project (version + a charly-mcp candy node with the bake_plugin: refs + a no-op plan), so the systemd-started MCP server resolves a local project instead of a network fallback.

2. **loaderkit layered config stack (§3.5)** — charly reads and MERGES charly.yml files in the order **system → user → in-dir**, later files winning. New loaderkit/config_stack.go:
   - system: /etc/charly/charly.yml (CHARLY_SYSTEM_CONFIG override); user: spec.DefaultDeployConfigPath() (~/.config/charly/charly.yml, per invoking user); in-dir: <dir>/charly.yml.
   - The merge happens at the RAW yaml.Node document level (top-level keys, later wins) — the raw round-trip preserves EVERY node. The typed spec.UnifiedFile parse DROPS the opaque candy bodies (json.RawMessage), proven empirically (a round-trip test shows candy=map[] after a typed parse) — the raw merge is the P1-correct implementation (any charly.yml must be capable of anything).
   - LoadUnified now feeds the merged bytes as the root document — the bootstrap phase, the early schema gate (on the merged, later-wins version), the kind-blind walk, and the validation chain all operate on the merged config. No layer at all → no project (unchanged).

3. **Tests** — loaderkit/config_stack_test.go (later-wins, user-wins-over-system, version later-wins, no-project, candy-node preservation), packagekit/render_test.go (unit + config + preset rendering, format gating deb/rpm/archlinux vs apk/ipk), loaderkit/test_main_test.go (isolates the config stack for every LoadUnified test — the real per-host ~/.config/charly/charly.yml must not leak into merged docs).
