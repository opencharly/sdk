# 0.2026322.1913 — feat(loaderkit): read the per-host `clean:` section without the deploy projection

## Summary

`spec#384` declared `clean:` as a typed per-host section and opencharly/plugin-clean reads its
ceiling from it — and NO plugin-reachable loader returned it. The mechanism is three layers deep,
and opencharly/sdk#565 carries the end-to-end measurement (three document shapes, every one
reporting the plugin's 32 GiB fallback):

1. `LoadDeployConfigViaExecutor` ends with `deploykit.ProjectDeployConfig`, which builds
   `DeployConfig{Provides, Deploy, Sidecar}` — every unnamed per-host section is dropped there;
2. `LoadHostDeployConfigViaExecutor` delegates to it, so it inherits the drop;
3. and the materialize's per-document merge (`spec/merge.MergeUnified`) does not carry the
   sections forward either — which is why reading `LoadUnifiedViaExecutor(dir).Clean` directly is
   nil too, even though the field decodes from YAML.

**This adds the narrow reader, not the widened view:**

```go
func LoadHostCleanSectionViaExecutor(ctx context.Context, ex *sdk.Executor, dir string) (*spec.CleanSection, error)
```

in `loaderkit`, beside `LoadHostDeployConfigViaExecutor`. It reads the per-host document and
returns the section WITHOUT going through `ProjectDeployConfig`.

**Why narrow rather than teaching `ProjectDeployConfig` to carry it.** That constructor is named
for the PROJECT deploy view and is what project-mode commands project; making it a merged
per-host view would make its name a lie, and every caller would silently start receiving state it
never asked for. `opencharly/spec#383` records the per-section *permission* gap one layer up — the
host service promising a plugin its own section; this is that gap's data half, and it belongs at
the section scope, not at the deploy scope.

**The contract, which is the consumer's refusal rule.** It matches §4.6's "the caller's own
section" and it is the reason a merged view could not have served:

- an absent per-host document → `(nil, nil)`;
- a document with no `clean:` → `(nil, nil)` — "unset" is a legitimate answer, and the consumer
  applies its own fallback (the 32 GiB ceiling lives in the plugin, never in the contract);
- an UNREADABLE document, a failed bootstrap leg, or an unresolvable config path → `(nil, error)`.

The last line is the whole point of the section scope: through a merged view, "absent" and "not
parsed" become the same nil, so a consumer cannot refuse an invalid ceiling without also refusing a
machine that simply never set one. Here they stay distinguishable.

**The decoding path is the loader's (R2).** `readConfigStack` is the very reader `LoadUnified` uses
(system layer → in-dir, raw document merge, retired-directive stripping), the bootstrap phase runs
in the same order, and the decode target is the same `*spec.UnifiedFile` that
`loaderkit.MaterializeLoadedProject` decodes each document's reserved directives into
(`materialize_project.go`). There is no second parser, no bespoke struct, and no duplicated file
resolution. What is deliberately NOT reused is the node-form walk + `merge.MergeUnified` +
`ProjectDeployConfig` chain — that chain is exactly what loses the section.

Not touched: no schema or wire type (the section already exists in `spec v0.2026322.1814`, which
`go.mod` already requires), no `ProjectDeployConfig` behaviour, no consumer code, no new field
anywhere. Two new files, 259 insertions.

Closes opencharly/sdk#565 (root fix option 1; option 2 — widening `ProjectDeployConfig` — is
deliberately not taken, for the reason above).

Head `cd0a679a0f37a2a921f76be26b2291f4bf1b59ad`.
