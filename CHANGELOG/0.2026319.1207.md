# 0.2026319.1207 — fix(deploykit): point a registry-image ref at the verb that works

## Summary

`RejectImageRefAsDeployName` correctly refuses a tagged registry image ref used as a deploy **name**, and its
remediation then sent the operator to a verb that cannot work:

```
charly deploy add <name> ghcr.io/org/name:tag
```

`deploy add` takes a **project box or candy ref**, so a registry image ref fails there with
`not found as a box or candy` — measured on opencharly/plugin-fleet#51. The operator's first error therefore cost
them a second one.

**The route that exists is `charly deploy from-box <ref> [<name>]`**, whose own help reads *"Full image ref (local or
registry)"*. Measured on this host:

```console
$ charly deploy from-box ghcr.io/opencharly/openwebui:2026.317.2254 f25proof
# accepts the ref and proceeds to the image's baked env inputs
# (rc=1 only because it then asks for the required WEBUI_ADMIN_EMAIL)
```

**So the defect is the SENTENCE, and this PR fixes the sentence** — the refusal itself is unchanged, and the message
now names `deploy from-box` while saying why `deploy add` does not apply.

The remediation is **asserted by its own test**, because a user-visible sentence is an artifact and this one had been
sending people to a dead end:

* `TestRejectImageRefAsDeployName_NamesTheWorkingVerb` — the message contains `charly deploy from-box <the ref>` and
  does NOT contain `charly deploy add`;
* `TestRejectImageRefAsDeployName_LeavesNamesAlone` — a plain name, a bare name with a tag (`fedora:43`) and a
  github repo ref (which pins with `@version`) are still NOT rejected.

**The live `deploy from-box` measurement above is the finding that made this a one-line fix instead of a new ref
form:** I had started implementing a fifth `RefSourceImage` in plugin-fleet, reverted it when the `from-box` help
line showed the capability already exists (R2 — one implementation per behaviour, and mine would have been a
duplicate), and confirmed it by running the verb.
