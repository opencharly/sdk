# 0.2026294.1520 — feat(deploykit)!: resolve a skill body against the owning candy's REPO ROOT

## Summary

`deploykit` now resolves a skill body against the owning candy's **REPO ROOT**, so the label and
`charly box validate` read exactly what the marketplace corpus reads. One base, one layout, two
readers.

**This reverses the base that a landed ruling chose, on direct operator instruction.** The
operator's words:

> *"Please fucking restore .agents/skills/ for all repos! That's the fucking purpose of this whole
> migration !!! And move any distro layer into separate repos like all other layers to and fix
> things properly following AGENTS.md and implement the same approach and architecture everywhere
> !!!"*

opencharly/sdk#434's SHAPE ruling stands — an image candy may not own a skill, and no such node is
legalized here. What changes is the LAYOUT base the re-home used: bodies belong at
`<repo root>/.agents/skills/<name>/SKILL.md`, not beside the candy. There is no fallback probe and
no second accepted location, because a fallback is how the dual-source state comes back.

**The defect, measured.** Two readers, two bases, one layout:

| reader | resolved |
|---|---|
| `plugin-marketplace` (`skillfile.go:88-112`) | `<entity SourceRoot>/<tree>/<name>/SKILL.md` — the REF root |
| `deploykit.CollectSkillBodies` (`skills_collect.go:189-202`, before) | `<owner candy SourceDir>/<tree>/<name>/SKILL.md` — the candy dir |

The two coincide for a `plugin-*` **subpath** ref and diverge for a `distro-*`/`layer-*`
**whole-repo** ref. At the newest tags of the ten affected refs that is **48 bodies the corpus
reader cannot reach**, and generation is fail-closed over the whole corpus, so no marketplace
refresh can be produced at all (opencharly/marketplace#522).

**What changes.** One derivation, `candyRepoRoot` (`deploykit/candy_repo_root.go`), applied by both
`readSkillFile` and the existing `remoteBuildConfigCacheRoots` helper — which re-derived the same
fact inline before, which is how the two bases drifted apart in the first place (R2). A candy's
`SourceDir` has exactly two shapes and neither needs a filesystem probe:

- `<repo>` — a root-level standalone candy: `SubPathPrefix` is `""` and `SourceDir` IS the repo root;
- `<repo>/<subpath><name>` — `SubPathPrefix` is recorded by the loader for a remote candy
  (`loaderkit`: `"candy/"`), and the same shape is recovered structurally for a local one
  (`candy/<name>`, the project loader's only candy placement), because the loader leaves
  `SubPathPrefix` empty at scan time for local candies.

A remote candy whose `SourceDir` does not end with its recorded in-repo path is now a **named
error**, not a silent miss: the identity and the on-disk path disagreeing is a finding.
