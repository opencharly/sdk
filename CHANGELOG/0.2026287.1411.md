# 0.2026287.1411 — fix(kit): expand a candy's own vars in a download destination, not only in its URL

## Summary

`kit.RenderDownloadScript` quoted the two author-authored strings **differently**, so a candy's own `var:` spelling worked in a download URL and silently did not work in a download **destination**:

| Field | Before | Effect |
|---|---|---|
| `download:` (URL) | `ShDoubleQuote` → `"…${FC_VERSION}…"` | the shell expands it — which is why the download itself succeeded |
| `to:` / `extract_include` | `ShQuoteArg` → single-quotes anything containing `$` | the shell **never** expands it; a bare name resolves against the deploy's cwd |

An author who follows the documented promise — `var:` values are emitted as `ENV`, "so every subsequent directive sees them as shell-resolvable `${VAR}` references" — gets a silently wrong destination on a `target: local` deploy while the container build path gets the right one.

**Fixed by** substituting the candy's own vars into `download`, `to` and `extract_include` **before** they are quoted — longest name first, so `${FC_VERSION}` cannot eat the head of `${FC_VERSION_DIR}` — and leaving names it does not know alone, because this is the candy's `var:` map and not the process environment. Substituting rather than unquoting keeps the injection-safe quoting for everything the author did not declare.

**Files:** `kit/render.go` (the substitution + the helper), `kit/render_test.go` (three new gates — the destination, the include filter, and the helper's longest-name-first rule).

**Second commit (review round).** Two validator findings, both correct: the body contradicted itself about the auto-export gap (fixed by FILING it — see below) and the include-filter substitution shipped without a test that fails without it (now covered, with its own control).

## How tested

Measured on a **disposable VM** first, because the symptom is a shell-visible one. A candy whose download destination was `${FC_TARBALL}` produced:

```
0  7.11M  … 100  7.11M        ← curl received the whole tarball
tar (child): /var/cache/charly/firecracker/firecracker-v1.17.0-x86_64.tgz: Cannot open: No such file or directory
```

and on the guest:

```
$ find / -maxdepth 4 -name '*FC_TARBALL*'
/home/arch/${FC_TARBALL}      ← a FILE named after the unexpanded string, in the deploy user's home
$ ls /var/cache/charly/
ls: cannot access '/var/cache/charly/': No such file or directory
```

Module gates, on the committed tree:

```
$ gofmt -l .                     → clean
$ go build ./... ; go vet ./...  → ok ; ok
$ go test -count=1 ./...         → rc=0, 15 ok packages
$ golangci-lint run ./kit/       → 0 issues
```

**Two controls**, each reverting ONE substitution:

```
--- FAIL: TestRenderDownloadScript_SubstitutesCandyVarsInDestination
      the destination kept its unexpanded ${VAR}, so the shell writes a file literally named that:

--- FAIL: TestRenderDownloadScript_SubstitutesCandyVarsInDestination   (include filter reverted)
      an include-filter entry kept its unexpanded var, so it would match nothing:
```

The include-filter case is the one worth having: a filter entry that keeps its unexpanded name selects NOTHING, so the archive extracts empty while every command in the script still "succeeds" — a silent empty install, worse than a loud failure.

**Proven live** (the changed path executed, not just rendered): the script the fixed renderer emits was run in the real guest, and it created the destination directory and fetched the artefact to the correct path with the **pinned** hash:

```
-rw-r--r-- 1 root root 43415272 … /var/lib/firecracker/kernels/5.10/vmlinux
sha256 298055d97266f3dc…
```

The same script failed before the fix with the message above.
