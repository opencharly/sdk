# feat(storekit,artifactkit): the store, its roots, and the plugin-artifact reader/verifier/materializer

## Summary

The two mechanisms that make a precompiled plugin artifact consumable, in their DESIGN homes: D-SDK-1 lists *"the store and its roots (§17)"* among the shared mechanisms an sdk package owns, D-CORE-1 has core build *"the store instance (built on the sdk store)"*, and D-SPEC-1 keeps `spec` to generated code plus behaviour methods with no mechanism. This is the concrete step of the operator's one-store mandate: **one root, one store definition, bytes once per digest.**

**`storekit`** — the four D-STORE-1 roots from one resolver (`RootConfig`/`RootCache`/`RootState`/`RootRuntime`) with the single `CHARLY_CACHE_DIR` override; `StoreDir(name)` rejects a name that is not one path element so a store cannot escape the root; `NamedStores()` is marker-based (`LayoutFile`), so a `locks/` directory is never mistaken for a store. The store itself: `PutBlob` (idempotent, atomic via a **per-call unique** temp + rename), `ReadBlob` (verifies the content address), `HasBlob` (the no-second-fetch primitive), `Blobs`; **`LinkBlob` — a view is a hard link with no cross-device fallback**, because a copy would be a second set of bytes and a fallback would hide a store that is not one filesystem, with `SameFile` and `BlobPath` so a caller asserts the sharing; `PutTree`/`ReadTree`/`MaterializeTree` for directory payloads (per-file blobs plus one manifest blob carrying the tree's own RFC 6838 media type, reconstructed as hard links, so a directory costs its bytes once rather than twice as a tar); and key-addressable entries (`PutEntry`/`LookupEntry`/`ReadEntry`/`Entries`) using `spec/cache`'s `ai.opencharly.cache.key` vocabulary, so a hit is decided by one index read before any bytes are fetched. The package doc states that the digest addresses the bytes while the key addresses the entry, and that a store tree contains no locks.

**`artifactkit`** — the reader (index → per-platform manifest → metadata config plus three layer roles), the platform selector, the verifier (artifact/config media types, all three layer roles present and distinct, every blob verified by content address, the config's platform against the descriptor that pointed at it, libc, and `runtime_requires` present), and the materializer, which verifies first and only then creates the view (`views/<leaf>@<manifest-digest>/`) as hard links to the store's own blobs.

**The selector's rule, stated exactly as the code reaches it:** an *unqualified* request selects the **baseline** entry — a deliberate conservative decision, because the host's capability is not the caller's intent and a silent upgrade is the failure this selector exists to prevent; a request *qualified* with a platform level is answered by the **exact** variant, else the baseline, else the first match — **a lower level is never substituted silently**, and **never a higher one** (which would be a SIGILL, strictly worse than a refusal). A non-match enumerates the platforms the artifact does carry.

**It validates what the artifact declares against what it is, and does not negotiate a version:** DESIGN §8 says there is no version negotiation and that compatibility is per-message validation (D-PROTO-6), so `protocol`/`calver` are optional diagnostics; `served_schema_digest` is labelled TRANSITIONAL until §8.1's CUE-module-as-data leg lands.

**THE DATA-LOSS BUG, and the strongest measurement in this module's history.** `indexEntry` did `readIndex()` → mutate → write with **no serialization**: two `PutEntry` calls for *different* keys both read the same snapshot, each appended its descriptor, and the last rename **silently dropped the other's entry**. `writeFileAtomic` made the *write* atomic and did nothing for the *operation* — **atomicity of a step is not atomicity of the operation** (rule 25: a fix to a mechanism must be checked against the OPERATION it participates in). The whole read-modify-write is now serialized by `spec/lock`'s `AcquireFileLockWithin`, on a lock file under the **runtime root** keyed by the store name — a **file** lock, because the store is shared across *processes* (loader, cache commands, plugin host), and **outside the store tree**, because a store tree contains no locks.
