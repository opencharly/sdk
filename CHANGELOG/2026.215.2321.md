# 2026.215.2321 — the sdk leg: init `depends_candy:` auto-injection

The `opencharly/sdk` leg of the init-dependency injection cutover. Declaring a `service:`
in a candy is what SELECTS an init system and assembles its config — but nothing installed
the selected init's own binary. A box composing only service candies validated clean, built
clean, baked `ai.opencharly.init="supervisord"` and a fully assembled `/etc/supervisord.conf`,
and then failed at deploy `[start]` with no `supervisord` in the image. The
`fallback_entrypoint: [sleep, infinity]` did not mask it.

## What lands

- **NEW `deploykit/init_depends.go`** — `InjectInitDependsCandy(boxes, layers, initCfg)`,
  the ONE shared pass (R3). It mirrors `ComputeIntermediates`'s `(boxes, layers)` shape and
  lives beside it because the decision needs BOTH the box set and the candy graph: which
  candies trigger which init is a whole-composition question, so it cannot live in
  `buildkit.ResolveBox`, which resolves ONE box in isolation and deliberately carries no
  candy map.

  **Target-awareness is structural, not a flag.** The active init comes from
  `InitConfig.ResolveInitSystem` — the SAME resolution that decides `ai.opencharly.init` and
  drives the render. A container composition resolves to `supervisord` (its `depends_candy`
  is injected); a `preserve_user`/bootc machine-venue composition resolves to `systemd`,
  which declares NO `depends_candy`, so nothing is added. A blanket `require: supervisord`
  on every service candy would be the WRONG fix for exactly that reason: target-blind, it
  would install supervisord onto systems that already have an init.

  Two properties the pass must have, both pinned by tests: it is IDEMPOTENT (so it can run
  at every chokepoint without double-injecting), and it injects the candy's own MAP KEY
  rather than its bare name — `BareCandyRef` strips only the `@` and the `:version` suffix,
  so a REMOTE candy is keyed by its full repo path (`github.com/opencharly/charly/candy/
  supervisord`) while the init vocabulary names it `supervisord`. Resolving by key alone
  silently no-opped on every distro submodule, where the init candy is always a remote ref.

- **`loaderkit/resolve_project.go`** — call the pass in `ProjectResolvedProject`'s fresh-box
  path, which feeds the validate / inspect / bundle-deploy envelope. The fresh arm now
  projects its views in a SECOND pass, because the injection rewrites `img.Candy` and
  `ProjectResolvedBox` copies that list into the view. The pre-resolved arm needs no pass —
  the build path already injected before render-prep filled those caches.

- **`deploykit/spec_box_resolve.go`** — call the pass in `FillNamespaceBoxViews`. This is the
  THIRD box-composition path: an import namespace's boxes are resolved from the namespace's
  OWN config there, so they reach NEITHER of the other two seams. Without it a namespaced box
  would have its init RESOLVED by the following `RenderPrepBox` (baking `ai.opencharly.init`)
  while its init candy was never added — the very defect this pass closes.

  The injection's presence check is scoped to the box's OWN resolved candy order, not its base
  chain (`ResolveCandyOrder` runs with a nil `parentCandies`), so a child whose BASE installs the
  init candy still gains it. That is invisible in the artifact — `GlobalOrderForBox` filters a
  base-provided candy back out at render — but it does mean `rp.Boxes[child].Candy` can name a
  candy the child itself does not install, which the doc comment now states outright.

## Completeness

`buildkit.ResolveBox` is the ONLY place a box's `Candy` list is set, so every composition
path funnels through one of: `ResolveAllBox`'s returned map (injected by candy/plugin-build's
`resolveBuildEngine`, which also covers the `pullNamespacedBox`/`resolveNamespacedBases`
entries that land in that same map), `ProjectResolvedProject`'s fresh-box loop, or
`FillNamespaceBoxViews`. All three are wired.

`ResolveSpecBox` / `ResolveAllSpecBoxes` / `WrapSpecBoxes` have no production consumers and are
therefore not wired. They are NOT left as an open question: they are dead surface, and their
deletion is scoped to the **dead-code batch cutover**.

That batch also carries the stale prose that still describes them as live — which is in the SPEC
schema, not in charly:

| Surface | Stale claim |
|---|---|
| `spec/schema/resolvedproject.cue:331-332` (+ generated twin `spec/spec/cue_types_gen.go:5489`) | names `ResolveAllSpecBoxes` in the present tense |
| `spec/schema/buildwire.cue:238` (+ twin `:3036`) | names `ResolveSpecBox` |
| `WrapSpecBoxes`' own doc comment | claims charly's `toDeploykit` uses it, though `charly/` has been at zero sdk mechanism-kit references since the #55 terminus |

An earlier revision of this entry cited `charly/kernel_manifest_floor_test.go` as that rider. **That
file does not exist** — it was deleted from superproject `main` at `21ab450b`, about an hour before
this PR's first commit, and `charly/import_purity_test.go:6` records the deletion. The citation was
false when written.

The correction strengthens the separability argument rather than weakening it: the real residue is
cross-repo, so deleting the three here would drag a `spec` schema sweep plus `task cue:gen` into the
middle of a four-repo chain. Deleting them here would widen a deploy fix into an API removal with a
separate blast radius, and this cutover's R10 neither exercises nor is changed by their removal.

## Tests

`deploykit/init_depends_test.go` — what the pass DECIDES: both directions (container injects,
machine venue does not), the remote-key case, idempotence, transitive-`require:` satisfaction,
the unreachable-candy no-op, and the namespaced-box path. Verified to FAIL with the
implementation stubbed out.

`loaderkit/resolve_project_test.go` — that `ProjectResolvedProject` actually CALLS it. The
decision tests above all run the pass directly, so they stay green if this seam silently
no-ops — and this seam is not the build path: it feeds the validate / inspect / bundle-deploy
envelope, whose consumers read `rp.Boxes[...]` to decide what a deploy installs. The test runs
the genuine resolve → inject → project chain through the real `buildkit.ResolveBox` and asserts
the PROJECTED view carries the init candy, so it seals both halves of the wiring: the call, and
the second-pass projection ordering the call forced. Verified to FAIL under both mutations —
the call replaced by a no-op, and the projection moved back into the resolve loop.

## R10

Two beds, both on the tree as it stands after catching this branch up to `main` — not on the
tree the header was written against.

`check-tutorial-shell` is the bed that PROVES the change: its box composes no supervisord
candy at all, and `[program:sshd]` is still present in the assembled `/etc/supervisord.conf`
of the built image. That check fails without the injection.

```
charly check run check-tutorial-shell: PASS (steps=13)
```

`check-migrate-local` is the bed that proves nothing ELSE moved — the pass runs inside
`ProjectResolvedProject`, which every validate / inspect / bundle-deploy path goes through,
so a regression there would surface as a deploy that no longer reaches steady state.

```
charly check run check-migrate-local: [update] PASS after 31.319s
charly check run check-migrate-local: [cleanup] PASS after 21.755s
charly check run check-migrate-local: PASS (steps=6)
BED EXIT=0
```

Zero warnings in both runs.
