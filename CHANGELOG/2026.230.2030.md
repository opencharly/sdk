# 2026.230.2030 — the explicit-override contract, pinned to what actually resolves

## Why

`opencharly/spec#39` narrows `ResolveInitSystem`'s explicit-override branch: an override is honored
only when it names a **viable candidate** — an init some candy triggers whose `requires_capability:`
is satisfied — instead of any key of `ic.Init`.

`buildkit.InitConfig` is a pure type alias (`type InitConfig = spec.InitConfig`), so
`buildkit/init_config_test.go` exercises **that** method, not a copy. One landed subtest pinned the
old contract by name:

> `explicit override wins outright, bypassing auto-detect`

It called `ResolveInitSystem(nil, nil, "systemd")` with no layers at all, so under the new rule the
override is not a candidate and resolution returns `("", nil)`. **A landed test asserting a revoked
contract is part of that contract**, and it has to move in the same cutover as the producer.

## What changed

The subtest is rewritten and renamed to **`explicit override selects among triggered inits`** — it
now supplies a candy that triggers `systemd`, which is what "honored" means under the new rule.

A second subtest is added, **`explicit override naming an untriggered init falls through`**, pinning
the contract narrowing explicitly: an override could previously **introduce** an init no candy
triggers, because the branch consulted `ic.Init` directly. It can now only **select among** inits
already triggered. That was an undeclared behaviour change riding along with the capability fix; it
is now asserted rather than implied.

Both are the coherent extension of a rule already in this file: the pre-existing subtest *"explicit
override naming an unknown init falls through to auto-detect"* is unchanged and still green. The new
rule extends "not honorable" from *unknown* to *unknown-or-non-viable*; it does not invent a
fallthrough that was not already there.

## The first version of this coverage was vacuous — mutation-proven

The renamed subtest originally used a single triggered init and overrode to that same init. Deleting
the **entire** explicit-override branch from `spec` (`_ = explicit`) left it green: with one
candidate, auto-detect's fallback returns the identical `(systemd, want)`, so the assertion could not
tell "override honored" from "auto-detect agreed". The subtest's *name* asserted a selection the
fixture could not observe.

It now triggers **two** inits and overrides to the one auto-detect would not pick — supervisord is
preferred for container images — and opens with a **control assertion** on the no-override path, so
if the preference rules change it fails loudly rather than quietly ceasing to discriminate.

```
against the mutant (override branch deleted):
  --- FAIL: .../explicit_override_selects_among_triggered_inits
      ResolveInitSystem(explicit) = ("supervisord", …), want (systemd, …)
```

A/B with an identical `sdk` tree, only the `spec` module swapped via a workspace overlay:

```

MUTANT     override branch deleted        ->  FAIL
  --- FAIL: .../explicit_override_selects_among_triggered_inits
```

The new subtest fails against the old producer, so it pins the narrowing rather than restating it.

Full `go test ./...` green against the PR head; `gofmt -l buildkit/` empty; `go vet` clean.

## Landing order

`opencharly/spec#39` lands **first** (producer), then this leg with the `spec` pin bump, then the
superproject gitlinks. `sdk` pins `spec` by version in `go.mod` with no `replace`, so `sdk/main`
stays green on the old pin until this leg moves it — but the superproject `go.work` carries
`use ./sdk` + `use ./spec`, so the workspace goes red the moment the gitlinks bump without this.
