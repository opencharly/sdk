# 0.2026317.1437 — fix(deploykit)!: name a namespaced deploy's container from the split pair, not the dotted address

fix(deploykit)!: name a namespaced deploy's container from the split pair, not the dotted address

## Summary

`ResolveContainer` derived the container name from the **unsplit** box argument, so a
ROOT-namespaced deploy addressed `<ns>.<name>` produced the name `charly-<ns>.<name>` — while the
pod lifecycle CREATES it from the **split** pair as `charly-<ns>-<name>` (`ContainerNameInstance`
maps `/` to `-`, and never sees a dot). The resolver then reported

```
charly: error: command "check": container charly-openclaw.check-openclaw-pod is not running
```

for a container that WAS running. Measured on the OpenClaw cutover's bed: `[config] PASS`,
`[start] PASS`, then `[check-live] FAIL 1m21.342s` — the deploy up, the probe insisting it was not.

**This round's change, on top of the branch's original split of `ResolveContainer`:**

1. **The split is ONE helper, and it now covers BOTH resolvers.** `ResolveSidecarContainer` carried
   the same defect: a sidecar container is named `ContainerNameInstance(<ns>, <rest>) + "-" +
   <sidecar>`, so resolving it from the dotted key reported a running sidecar as missing. One
   mechanism, one helper, both call sites — not a second copy of the logic.
2. **The engine input is part of the change, not a side effect to hide.**
   `ResolveBoxEngineForDeploy` is now called with the SPLIT pair, so the per-deploy engine lookup key
   moves from `(<dotted>, "")` to `(<ns>, <rest>)` — from the config key
   `openclaw.check-openclaw-pod` to `openclaw/check-openclaw-pod`. It is asserted by a test (below).
   The earlier body claimed only the container name changed; that claim was wrong and is corrected
   here.
3. **The gofmt gap is closed** — `"strings"` sits in import order (`context`, `fmt`, `strings`).
4. **Discriminating coverage exists**, which the blocked head did not have at all.

  deployment needs to be re-created (or, to go back, the consumer must pin the sdk tag from before
  this merge). Unnamespaced names and explicit instances are unaffected: they resolve exactly as
  they did.
