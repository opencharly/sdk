# 0.2026314.2159 — fix(loaderkit)!: refuse a project whose import namespace is also a top-level node name

## Summary

`DESIGN.md` §12.4 states **D-VAL-4**: *"Namespaces and top-level node names are disjoint."* The design
proves the rule on its own examples — `design/example/rules.cue` emits it
(`namespace <a> is also a top-level node name`) and `design/negative/namespace-is-node.yaml` is its
negative case — and names **core** as the owner. The loader enforced nothing.

**What the premise measured to.** `TODO.md` 3.17 says the two "can clash". The tree says something
stronger: a project that imports `tools` as a namespace **and** defines a top-level node `tools`
loaded **clean**, in all three shapes the walk can produce a top-level node from — the same document,
a flat import that appends to the same project, and a discovered manifest. So `tools.ripgrep`
resolved through the namespace while a bare `tools` named the node: one word, two meanings, silently.
Three red tests on pristine `origin/main`, pasted in **How tested** §1.

**Why no CUE definition can see it.** `#NodeDoc` is closed, but `import:` is a list of `alias: ref`
pairs — an alias is a *value inside an element*, never a key the closed struct could unify against the
document's own top-level keys. That is exactly why the design files the rule under §12.4 (rules the
schema cannot express) instead of in `DESIGN.cue`.

**What this change does.** `checkNamespaceNodeDisjoint` runs **last** in `walkProject`, because the
scope the rule speaks about is the **project**: the root document, every flat import that appends to
the same `spec.LoadedProject`, and every discovered manifest (`DESIGN.md` §11.1 Read: *"the project
root, its `discover:` documents and its `import:` closure"*). It judges those node names against
`nsByAlias` — the walk's own namespace index, the ONE place the aliases are recorded — so the check
reads the scope resolution reads rather than re-deriving it. A per-file check misses the flat-import
and discover cases; a namespaced import's own project is a *separate* scope, checked by its own walk.
The refusal is `import namespace "tools" is also a top-level node name — a namespace and a top-level
node name are disjoint (DESIGN.md §12.4 D-VAL-4); rename one`, naming the alias, the node and the
document that declares it.

This is `TODO.md` item **3.17** ("Import namespaces and top-level node names can clash … *Add the
disjointness check to core*"), tracking issue **opencharly/opencharly#975**, the `sdk` leg of the
campaign sequence (`opencharly/opencharly#950`). It adds no row to the D-PAT census
(`opencharly/opencharly#945`) and moves none.

## Change classification

Library change inside the plugin contract module (`github.com/opencharly/sdk`, package `loaderkit`);
no binary and no image is built here.

- **What changes for a consumer:** a project that declares an `import:` namespace AND a top-level node
  of the same name now fails to load, naming the alias, the node and the document that declares it.
  Every other project loads exactly as before: the check only ever refuses a name collision, and the
  scan in **How tested** §2 finds none in 2047 manifests, so no authored config in the org needs a
  migration.

**Breaking change + rollback:** it breaks exactly one class — a project whose import namespace is also
a top-level node name, which today loads into an ambiguity (`ns.ref` resolving through the namespace
while the bare name resolves to the node) and now fails loudly. That class is empty in the org's tree
(0 of 2047 manifests; the one repo whose `charly.yml` moved since its checkout re-measured at
`origin/main` with 0 clashes), which is why no consumer breaks on the pin bump. Rollback is the
previous module tag: pin `require github.com/opencharly/sdk` back to the tag before this merge, or
revert this commit — the check has no on-disk state, no schema field and no migration to undo.
