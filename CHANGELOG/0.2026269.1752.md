# 0.2026269.1752 — fix(ledger): accumulate reverse ops for a shared candy (charly#687)

## Summary

Fix **opencharly/charly#687**: a candy's `reverse_ops` were **overwritten** by each
deploy that used it, so a shared candy leaked all but the last deploy's teardown.

A candy record is **shared** by every deploy that uses it — it is refcounted by
`DeployedBy` — and its `reverse_ops` are replayed **only when the refcount empties**
(`TeardownHostDeploy` → `RunReverseOps(candyRec.ReverseOps)`). But
`AddCandyDeployment` let each deploy's `update` callback do
`rec.ReverseOps = <this deploy's ops>` — a **replacement**, so the second deploy of
a candy **clobbered the first's** ops.

For `deploy:kindcluster`, the op is **per-cluster**
(`kind delete cluster --name <that deploy's cluster>`), and every kindcluster deploy
attributes it to the **shared `plugin-kube` provider candy**. Two kindcluster
deploys (a root + its member) therefore left **one cluster running** on teardown.

## The fix — accumulate, don't replace

`AddCandyDeployment` (and its executor-routed twin `AddCandyDeploymentVia`) now
**snapshot** the record's ops before the callback and merge the callback's declared
ops over them with `MergeReverseOps` — the **union** across all contributing
deploys, deduped **by content** (`reflect.DeepEqual`; `ReverseOp` carries an `Extra`
map so `==` cannot compare it). Dedup makes a re-run of the same deploy idempotent.

The callback's `rec.ReverseOps = …` is unchanged — its meaning is now "declare THIS
deploy's ops", which the ledger accumulates. `recordDeploy` (the only setter) already
sets exactly that.

### LIVE proof — the leak, and its cure

Built `charly` against **this** sdk (+ `plugin-fleet`), then ran the minimal repro: a
kindcluster root + a deploy-level kindcluster member (two deploys sharing the
`plugin-kube` candy).

**Before** (current `main`): only the member's op is recorded, so the **root cluster
survives** `deploy del`:

```
ledger:  reverse_ops: [ kind delete cluster --name 'lk-member' ]     ← lk-root's op was clobbered
$ deploy del lk-root
Removed external deploy 746b… (kindcluster)   # lk-root
Removed external deploy c83d… (kindcluster)   # lk-member
$ kind get clusters
check-kc
lk-root            ← LEAKED
```

**After** (this PR): both ops are recorded, and teardown deletes **both** clusters:

```
ledger:  2 reverse ops:  kind delete cluster --name 'lk-root'
                         kind delete cluster --name 'lk-member'
$ deploy del lk-root
Removed external deploy c83d… (kindcluster)
Removed external deploy 746b… (kindcluster)
$ kind get clusters
check-kc           ← only another session's cluster remains; no leak
$ grep -cE 'lk-root|lk-member' ~/.config/charly/charly.yml
0
```
