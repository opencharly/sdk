# 0.2026327.1653 — fix(builder): pin HOME and PIXI_HOME in the pixi stage so the env lands where the image expects it

## Summary

The emitted pixi builder stage set only `USER {{.UID}}` and `WORKDIR {{.Home}}`. `pixi install` puts its environment under **`$PIXI_HOME` (default `$HOME/.pixi`)**, not the project directory, and `USER`/`WORKDIR` do **not** set `HOME` — it is read from the base image's passwd for that uid. When a rebuilt base moved uid 1000's home, the environment landed outside the box's home, and the final stage's

```
COPY --from=<candy>-pixi-build --chown=<uid>:<gid> <home> <home>
```

carried no `.pixi`. Every image check that reads `<home>/.pixi/envs/default/bin/python` then failed (measured: `opencharly/pod-comfyui#49`'s composed bed — `image-build` PASS 33m, then `comfyui-pinned-packages`/`comfyui-manager-version` exit 127 "No such file or directory"; filed as **opencharly/pod-comfyui#51**).

This is the same defect class the codebase already fixed for npm, and it takes the same cure:

```
// npmStageTemplate (unchanged, for contrast)
# Override NPM_CONFIG_PREFIX from the builder image so npm writes to
# the TARGET image's HOME (not the builder's /home/user). Without this,
# uid=0 target images silently get an empty payload.
ENV NPM_CONFIG_PREFIX={{.Home}}/.npm-global
```

## Fix

```diff
 USER {{.UID}}
 WORKDIR {{.Home}}
+ENV HOME={{.Home}} PIXI_HOME={{.Home}}/.pixi
 ...
-RUN … {{.InstallCmd}} && rm -f {{.Manifest}} pixi.lock
+RUN … {{.InstallCmd}} && test -d {{.Home}}/.pixi && rm -f {{.Manifest}} pixi.lock
```

(the assertion is in both RUN arms — with and without a `build.sh`), so a home mismatch fails the **build** instead of surfacing as a red runtime check in every consumer.
