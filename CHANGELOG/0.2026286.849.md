# 0.2026286.849 — fix(kit): persist RemoveVmSshStanza removals while sibling stanzas exist

## Summary

`kit.RemoveVmSshStanza` never persisted a removal while any sibling stanza remained, so
`charly vm destroy` (and a `vm:` deploy's teardown) reported `Destroyed VM <name>` yet left
the managed `Host` alias behind in `~/.config/charly/ssh_config`.

**Root cause.** `saveStanzas` re-merged the caller's map into a **fresh** `loadStanzas(path)`
read. That merge is upsert-only, so the just-deleted alias was re-added from disk whenever
another stanza existed — only the single-stanza `len==0 → os.Remove(frag)` arm hid it.

**Fix.** `WriteVmSshStanza` and `RemoveVmSshStanza` now do their read-modify-write **under**
the fragment file lock (`lockStanzas`) and write the authoritative set (`writeStanzasLocked`,
no re-merge). The concurrency guarantee that motivated the merge (no lost alias under N
concurrent writers — the measured 16-lane check-run stalls) is preserved by loading **under**
the lock instead of re-merging without it.

Closes #370.

Live evidence that motivated the fix (host `no`, 2026-10-13): on a 20-stanza fragment,
`charly vm destroy ubuntu-ci --disk` printed `Destroyed VM charly-ubuntu-ci` and removed the
libvirt domain, the ~116 GiB disk and the `vm:ubuntu-ci` deploy entry — but
`grep charly-ubuntu-ci ~/.config/charly/ssh_config` still matched after the run; the fragment
mtime advanced (a rewrite happened) yet the alias survived, i.e. the removal was written and
then resurrected by the re-merge.
