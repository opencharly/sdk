# 2026.210.0550 — #55 Phase A2 (sdk leg): consume the published `github.com/opencharly/spec` module; delete the moved wire/IR/schema dirs

The IMPORT-PURITY phase (#55) extracts the kernel↔plugin wire contract — the
generated param structs, the protobuf transport, the CUE ingress schema, and the
shared schema-concatenation helper — into its OWN module,
`github.com/opencharly/spec`, published in Phase A1 (spec `main`
`11dcd6d2`, tag `v0.2026210.518`). This is the sdk half of Phase A2: the sdk
contract module stops OWNING those packages and becomes a CONSUMER of the spec
module, exactly as every other repo now does.

## What moved OUT of sdk

Deleted wholesale (they now live in the spec module, byte-identical):

- `spec/` — the generated param structs (`cue_types_gen.go`, `vocab_gen.go`,
  `version_gen.go`) + the hand-written union / state / method / const siblings.
- `proto/` — the gRPC transport model (`plugin.proto`, `plugin.pb.go`,
  `plugin_grpc.pb.go`).
- `schema/` — the CUE ingress schema (`*.cue`) + its `//go:embed` FS (`schema.go`).
- `schemaconcat/` — the shared `ConcatSchema` contract.
- `protocol/schema/` — the wire-model CUE (`plugin.cue`, `schema.cue`).
- `internal/schemagen/` + `internal/wiregen/` — the generators that produce the
  above. Generation is now owned by the spec module's own `Taskfile.yml`
  (`task cue:gen` / `task wire:gen`).
- `Taskfile.yml` — every task in it was gen machinery for the moved dirs; with
  those dirs gone the sdk repo has nothing to generate, so the whole file is
  removed. The pinned-cue-CLI / protoc bootstrap now lives in the spec module.

## What changed IN the kept sdk packages

Every kept package — `kit`, `deploykit`, `buildkit`, `loaderkit`, `agentkit`,
`enginekit`, `targetkit`, `vmshared`, `proclifecycle`, the root `sdk` package —
had its imports repointed:

```
github.com/opencharly/sdk/{spec,proto,schema,schemaconcat}
  → github.com/opencharly/spec/{spec,proto,schema,schemaconcat}
```

(243 `.go` files.) `go.mod` gains `require github.com/opencharly/spec
v0.2026210.518` with **NO replace directive** — because the sdk contract module
is consumed STANDALONE (the sdk pr-validator clones it in isolation and runs
`GOWORK=off go build`); a `replace ../spec` would break that standalone clone
(no sibling `spec/` tree), whereas require-only proxy-fetches the published,
go.sum-verified module. In the superproject the `go.work use ./spec` directive
overrides to the local tree anyway, so the require version only ever matters to
out-of-tree consumers.

## Verification (sdk standalone, RDD-proven)

- `GOWORK=off go build ./...` — clean.
- `GOWORK=off go vet ./...` — clean.
- `GOWORK=off go test ./...` — every package `ok`.
- `golangci-lint run ./...` — 0 issues.

The require-only-standalone hypothesis was proven on a live throwaway build
FIRST (an empty module requiring `spec@v0.2026210.518` with no replace, on this
host's `GOPRIVATE`-empty env, fetched + go.sum-verified + built clean),
de-risking the whole approach before the bulk repoint.
