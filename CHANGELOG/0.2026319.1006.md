# 0.2026319.1006 — fix(loaderkit): a gate that imports the schema module now compiles

## Summary

A gate whose served source **imports the spec schema module** can now resolve. This is the last knot of the schema-ownership mechanism: the host already threaded the gates, the plugin already declared its def, and the fill still failed with

```
kind "vm": gate source does not compile: package "github.com/opencharly/spec/schema" imported but not defined
```

**The mechanism.** `kindDefFor` prepended the concatenated base to a bare `CompileString`. A string compile has no module context, so an `import "github.com/opencharly/spec/schema"` resolves to nothing — and the base's own files carry no package clause, so prepending them could not help. The base is loaded as a **module** everywhere else (`composeBaseSchema`); the gate path was the one place that wasn't.

**The fix.** `compileGateSource` loads the gate's source as a file of its **own package** (`./gate`) in the assembled module — the embedded schema, its `cue.mod` declaration, and the gate file — so its imports resolve exactly as they do at build time. It must sit *outside* the package it imports: the first attempt put it inside `./schema` and CUE refused the import cycle, which the test below pins.

`TestKindDefForCompilesAGateThatImportsTheSchemaModule` is the coverage: it fails with the previous string compile ("imported but not defined") and passes now. The three existing `kindDefFor` tests all still pass.
