# 0.2026240.2049 — feat(cargo): build library crates, and stop building inside the read-only mount

## Summary

**B5 — the cargo library/artifact mode**, plus a pre-existing defect it uncovered on the binary
path.

The cargo builder ran `cargo install --path /ctx`, which installs **binaries only**. On a crate
declaring no `[[bin]]` it fails with *"no binaries to install"* — so any candy shipping a Rust
**library** (a cdylib GStreamer plugin, a staticlib, a `.so` for `LD_PRELOAD`) could not use this
builder at all. `layer-gst-wayland-display` is exactly that shape.

## Where the branch lives, and why

In the **template**, not in Go. The discriminator is the crate's own `Cargo.toml`, which exists
only inside the build context; a shell test needs no new schema, no new input field and no
authored `external_builder:` — detection stays detection.

Cargo's binary detection is **three** rules, not one: an explicit `[[bin]]` section,
`src/main.rs`, or any `src/bin/*.rs`. All three are tested for — treating a binary crate as a
library would build it and then install nothing.

## Where the artifacts go

`/usr/local/lib/charly/<candy>/`, not a flat `/usr/local/lib`. The install is then
**identifiable and therefore reversible**: `BuilderReverse` removes exactly that directory,
where a flat install would leave charly unable to tell its own `.so` files from anyone else's.

A per-candy directory is invisible to the dynamic loader, so an `/etc/ld.so.conf.d` drop-in is
written with it and `ldconfig` run. The two are installed together and removed together —
leaving the drop-in behind would point the loader at a directory that no longer exists.

A library crate that produces no cdylib/staticlib **fails loudly**, with a message naming the
fix. A glob matching nothing and an install quietly doing nothing is the exact silent no-op this
builder already avoids on the aur path.

## The pre-existing defect this uncovered

A Containerfile `--mount=type=bind` is **read-only**, and cargo writes into the crate directory:

```
cargo build   → failed to write /ctx/Cargo.lock: Read-only file system
cargo install → Read-only file system (os error 30) at path "/ctx/targetIg7IED"
```

The second is **not something the library branch introduced** — `cargo install --path` writes
its intermediate artifacts beside the source, so the container cargo path could never have
worked. It went unnoticed because **no production candy uses this builder**: the only
`Cargo.toml` beside a `charly.yml` in the corpus is charly's own `cargo-tool` test fixture, so
this path had never actually run.

Copying the source out **once, before the branch**, fixes both modes. Blocking rather than
separable: the library branch shares this RUN with the binary one, and shipping a builder whose
other half cannot execute while claiming to have extended it would be misleading.

## How tested

Both defects were found by **running** the rendered script against real crates in a container —
neither is visible from reading it, and neither would have been caught by a string-matching test
alone.

On the **final committed tree**, from a fresh clone:

```
$ git clone --branch feat/cargo-library-mode --depth 1 …/sdk.git
$ go test ./... -count=1
suite exit=0
$ golangci-lint run
0 issues.
```

### The end-to-end proof — three real crates, in a container, over a read-only mount

Fixtures: a `crate-type = ["cdylib", "staticlib"]` library, a `src/main.rs` binary, and a
default-`rlib` library (which must be rejected).

```
$ podman run --rm -v <crate>:/ctx:ro rust:1-slim sh -c '<the rendered script>'
libcrate   exit=0
bincrate   exit=0
rlibcrate  exit=1        # produces no .so/.a — must fail, and does
```

```
$ # library crate, inside the container afterwards
$ ldconfig -p | grep charly_fixture
        libcharly_fixture.so (libc6,x86-64) => /usr/local/lib/charly/gwd/libcharly_fixture.so
$ ls /usr/local/lib/charly/gwd/
libcharly_fixture.a
libcharly_fixture.so
```

`ldconfig -p` resolving the library is the point: it proves the drop-in works, not merely that a
file was copied somewhere.

```
$ # binary crate, same script
Installing /tmp/cargohome/bin/charly-fixture-bin
$ /tmp/cargohome/bin/charly-fixture-bin
hi
$ ls /usr/local/lib/charly
ls: cannot access '/usr/local/lib/charly': No such file or directory
```

The binary runs, **and** the library directory is absent — the two modes are mutually exclusive,
not merely both present. On the library crate the converse holds: no binary is installed.

### Unit-level guards

```
--- PASS: TestCargoInline_CarriesBothModes
--- PASS: TestCargoInline_DetectsAllThreeBinaryShapes
--- PASS: TestCargoInline_EmptyLibraryBuildIsFatal
--- PASS: TestCargoInline_NeverBuildsInTheReadOnlyMount
--- PASS: TestBuilderReverse_CargoLibrary
--- PASS: TestBuilderReverse_CargoBinaryAndLibraryCoexist
```

`TestCargoInline_NeverBuildsInTheReadOnlyMount` asserts `/ctx` appears **only** as the mount
target and the copy source — never as a build, install or target-dir path — so the defect above
cannot silently return. `TestCargoInline_EmptyLibraryBuildIsFatal` additionally asserts the
fragment contains no `|| true`, which is how the loud failure would decay back into a silent one.

## Rulebook compliance

- **R0** — `/charly-internals:cutover-policy` and `/charly-internals:strict-policy` loaded.
- **R1** — both failures were root-caused (read-only bind mount; cargo writing beside the
  source) by running them, and the second was traced to why it had never been observed.
- **R2** — nothing deferred. The read-only fix is blocking and rides here, not in a follow-up.
- **R3** — one `renderBuilderStageData` render serves every builder; the cargo branch wraps the
  input rather than adding fields the other three never use. The lib-dir path is one function,
  `CargoLibDir`, used by both the resolve and the reverse leg.
- **R4** — no workaround: no `|| true`, no swallowed exit, no glob that may match nothing.
- **R5** — the old single-line template is replaced, not kept beside the new one.
- **R6** — `git status` checked; branch off fresh `main`; no force-push, no bypass.
- **R7** — the gate ran on the final committed tree from a fresh clone, and the container proof
  was re-run against **that** tree, not the working copy.
- **R8** — the emitted artifact is the Containerfile fragment; it is rendered, syntax-checked
  (`sh -n`, `bash -n`) and then executed.
- **R9/R10** — the container run over a read-only mount IS the disposable gate here, and it
  discriminates: the same script exits 0, 0 and 1 on the three fixtures.
- **B12** — every test fails without the change (the library branch does not exist; `/ctx` build
  paths are present).

## Change classification

- **Class:** runtime/code change — build-time Containerfile fragment + the builder's

- **Verification gate:** module suite (fresh clone) + lint + an end-to-end container build of

- **Attribution tier:** `analysed on a live system` — the rendered script was executed against

## A correction to the plan

The plan's stated B5 gate — *"pixelflux repointed off its `build.sh` cdylib compile onto the
builder"* — **must not be attempted**, and the plan has been updated to say so.
`pixelflux/setup.py` builds its cdylib through **`setuptools_rust.RustExtension`**: pixelflux is
a *Python package whose wheel embeds a Rust cdylib*, not a Rust crate that happens to build a
library. Its `.so` must land **inside the `pixelflux` Python package directory** for the module
to load it, and `pod-selkies/build.sh` additionally patches the crate source (the NVENC preset
API) and its `Cargo.toml` before building. Repointing it here would discard the Python
packaging, setuptools-rust's platform handling and the patch path — a regression wearing a
migration's clothes.

The disposable three-crate container gate above replaces it, and it discriminates on exactly the
behaviour that matters.

## Not covered

- **The host-deploy phase** (`charly.yml`'s `builder.cargo.phase.install.host`, which runs
  `cargo install --path /work --root "$CARGO_HOME"`) still has no library branch. It is a
  different repo's file and a different execution venue — `/work` is writable there, so it does
  **not** carry the read-only defect — and no consumer needs a host-deployed Rust library today.
  Named as the next member of this theme rather than parked; WP1 is a container layer.
- **The binary leg's `binaries` reverse context is still never populated** by any producer, so
  `cargo-uninstall` teardown remains dead for binary crates. Pre-existing and untouched here;
  the library leg's teardown, by contrast, is fully derivable and now works.
