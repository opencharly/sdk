# 0.2026318.2225 — fix(deploykit): LoadDeployFile reads the name-first node form and fails loudly on nothing

## Summary

`charly deploy import <file>` reported success and imported **nothing** for any file in the shape charly
itself writes:

```
$ charly deploy import /tmp/openwebui-lab.yml
Imported 1 file(s) into /home/atrawog/.config/charly/charly.yml     # success line
$ grep -n 'openwebui-lab' /home/atrawog/.config/charly/charly.yml
(no match)                                                          # nothing landed
```

**Cause.** `LoadDeployFile` was a raw `yaml.Unmarshal` into `DeployConfig`, whose `Deploy` field is tagged
`yaml:"deploy"` — the **wrapped** shape — with **flat** values. The per-host file and every project
`charly.yml` are **name-first** with an **edge kind** (`<name>: {pod: …}`). The kind key matched no struct
field, so bodies vanished silently; the verb then printed `len(files)` as "Imported N file(s)".

**Fix, two halves:**
1. **Read both shapes.** Wrapped first (what `DeployConfig` marshals to), then the name-first fallback: unwrap
   each entry's substrate key and stamp the loader-derived `Target` from it, so a `vm`/`local` entry cannot
   be dispatched as `pod` by `ClassifyTarget`'s default. The per-host non-deploy sections
   (`provides`/`sidecar`/`cache`/`ledger`/`system`) are skipped.
2. **Fail loudly on nothing.** A file that contributes no deploy entry is an error naming both accepted shapes.

The substrate key is read through ONE **ordered precedence list** (`pod`, `vm`, `kubernetes`, `local`,
`android`, `group`), not by ranging a map — an entry carrying two of them must resolve to the same kind on
every run (round-2 non-blocking note, fixed in `0943e8c`).

Refs sdk#517 (RCA). The verb's own message (plugin-fleet counting files rather than entries) is the second half
of that issue and lands producer-first after this tags.
