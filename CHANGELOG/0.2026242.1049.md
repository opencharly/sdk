# 0.2026242.1049 — feat(vmshared): attach an installer ISO and boot the disk first

## Summary

`source.kind: iso` (spec#71) needs the guest to boot a distro's official installer once and
then never again. `VmRuntimeParams` gains `InstallerISOPath`, and the qemu renderer attaches
it as a **second cdrom** beside the answers volume, with `-boot order=cd`.

### The boot order *is* the mechanism, and it is what both design passes got wrong

Both earlier passes assumed the installer had to be **ejected or detached** once it finished,
and designed machinery to detect that moment — a guest-agent poll, a marker file, a
post-install reboot hook.

None of it is needed. In qemu's letter vocabulary `c` is the first hard disk and `d` the
first cdrom, so `order=cd` means **disk-then-cdrom**:

1. First boot: the disk is empty and not bootable, so the firmware falls through to the
   installer.
2. The installer writes the disk and powers off.
3. Every boot after: the disk boots. The ISO is never reached again.

Both cdroms stay attached forever, nothing has to notice the install finished, and the
"installer loops forever reinstalling" failure mode is **unreachable** rather than defended
against. This is also upstream Omarchy's own documented Proxmox recipe
(`--boot order='scsi0;ide2'` — the empty disk first, deliberately).

Reversed (`order=dc`) the guest would re-enter the installer on every boot and reinstall
over itself indefinitely. There is a test asserting against exactly that string.

### Why a separate field and not a reuse of `SeedISOPath`

An iso VM attaches **both**: the installer ISO, and on its own cdrom the answers volume that
makes the install unattended. An installer with no answers sits at its first prompt forever
with nobody at the keyboard. A test covers the case where one is dropped in favour of the
other, because that substitution is the natural mistake and it fails silently — the VM
simply never finishes installing.

### `-boot` is emitted only when an installer is present

`cloud_image`, `bootc` and `bootstrap` VMs render **byte-identical argv** to before. A
boot-order change leaking into every existing VM would be a serious regression hiding
inside a feature addition, so it has its own test rather than resting on inspection.

## Rulebook compliance

- **R1 — RCA every anomaly.** The eject/detach machinery was not carried forward on
  authority; it was root-caused to an incorrect assumption about boot order and removed
  from the design. The `gofmt` failure was traced to `main` rather than assumed to be mine,
  and then fixed instead of parked.
- **R3 — no duplication.** The installer rides the existing cdrom-attachment path; nothing
  about disk attachment is reimplemented.
- **R4 — no workarounds.** No sleeps, no polling for an install to finish, no marker files.
  The boot order makes the terminating condition structural.
- **R5 — delete legacy completely.** Nothing to delete: this is additive, and the
  no-installer test proves the existing paths are untouched.
- **R7 — prove the gate.** Full `-count=1` suite pasted above from the committed tree.
- **R10 — fresh disposable proof.** All three negative controls were run against
  deliberately-broken trees restored from backups; every result above is from the committed
  state.
