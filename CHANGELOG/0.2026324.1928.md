## Summary

`spec/storeroot` now reads the charly-only overrides (opencharly/spec#411, tag
`v0.2026324.1914`). This leg carries that into the mechanism layer, which **re-exports** the
resolver rather than computing anything: `spec v0.2026324.1630` → **`v0.2026324.1914`**.

- **Re-export arm.** `TestCacheRootHonoursTheCacheOverrides` proves *through `sdk/storekit`*
  that `CHARLY_CACHE_HOME` beats the kept `CHARLY_CACHE_DIR` for both `CacheDir()` and
  `StoreDir()`. At the previous pin the same arm failed; that failure is pasted below, so the
  arm is a control rather than a restatement of the contract module's own test.
- **Claim sweep.** No live "single/ONE override" or "four roots" claim survives in `storekit`,
  `kit` or `loaderkit`. Where a sentence needed a replacement it names the cache root's own
  overrides (`CHARLY_CACHE_HOME`, then the compatibility `CHARLY_CACHE_DIR`); the root list is
  named without a count, because the count drifted once already (the resolver has resolved the
  data root since #407 while `roots_test.go` still said "all four roots").
- **Test isolation (D-STORE-8).** Every test that pins a cache override now also clears
  `CHARLY_CACHE_HOME`, and `pinRootsEnv` clears all seven `CHARLY_*` inputs, so no developer
  environment decides a result.

Both sweeps are run against `origin/main` (**before** the leg) and against the working tree
(**after** it), so the dispositions cannot drift from the grep the way a hand-written table can.
