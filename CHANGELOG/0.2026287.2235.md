# Drop the variant family's mutual `Replaces` — it makes a routine `pacman -Syu` unresolvable

## Summary

The variant family (`charly`, `charly-full`, `charly-minimal`, …) is a set of mutually-exclusive packages over a SHARED file set, so the emission gave every member `Provides <base>` + `Conflicts` **+ `Replaces`** every OTHER member. The `Conflicts` are right; the `Replaces` are not, and they break **upgrades**, not swaps:

```console
$ charly check run check-githubrunner-pod        # opencharly/distro-cachyos, its own gate, tree cd5de3f
charly check run check-githubrunner-pod: [image-build] FAIL after 2m20.588s: exit 1
$ tail -4 .check/check-githubrunner-pod/2026.287.2218/image-build.log
:: Replace charly with charly/charly-full? [Y/n]
:: Replace charly with charly/charly-minimal? [Y/n]
error: unresolvable package conflicts detected
:: charly-full-2026.279.2144-1 and charly-minimal-2026.279.2144-1 are in conflict
```

For each **installed** member an upgrade asks which repo packages declare `Replaces` on it, and the answer must be **at most one**. Declaring every member a replacer of every other gives each installed member two candidates, so the transaction cannot resolve — and it fails in whatever consumer happens to upgrade, not in an explicit swap. Filed as `opencharly/charly-arch#13` (blast radius: *every* composition that installs `charly` from that repo and later runs `pacman -Syu`).

**The change:** emit `Provides <base>` + `Conflicts` every sibling, and **no `Replaces`**. A swap stays supported and explicit — the `Conflicts` entry makes `pacman -S <other-variant>` prompt to remove the installed one, and remove-then-install works unconditionally (which is what `charly-arch`'s own `check-arch-repo` bed already does). A variant is no longer silently replaced by the default on upgrade, which is the point of a flavour: `charly-minimal` exists to ship fewer plugins, and an upgrade must not quietly undo that choice.

**The comment this change deletes cited a precedent that contradicts it (R5).** `nfpm_config.go` justified the mutual replace as *"the canonical Arch family pattern (nvidia / nvidia-dkms / nvidia-open)"*, and the canonical member that does the replacing declares a **version-bounded migration** replace instead:

```console
$ curl -s https://archlinux.org/packages/extra/x86_64/nvidia-open/json/
provides:  ['NVIDIA-MODULE']
conflicts: ['nvidia']
replaces:  ['nvidia<=580.119.02-2']
```

So the canonical pattern is `Provides` + `Conflicts`-every-sibling + a **bounded** migration `Replaces`, and the comment is rewritten in this same cutover to say that and to record why the mutual form cannot resolve an upgrade — so the next reader does not reintroduce it "to match the canonical pattern". `packagekit/variants.go`'s doc comment said the same thing and is corrected with it.
